## 案の要旨

CI は「ローカル Hook で速いチェックを先に潰し、リモートでは**すべての必須チェックを必ず自分で実行する**」二層構成にする。ローカル結果はリモートの判定根拠に一切使わない（初稿の「証明書による再実行省略」は撤回した）。計算削減は、起動後の仕事量を減らす手段（古い実行の中止・段階実行・変更範囲での絞り込み・キャッシュ）で得る。CD は環境ごとに「方式・トラフィック段階・待機時間・判定閾値」をプロファイルとして宣言し、閾値を超えたら自動ロールバック、prod の初回拡大と状態を伴う変更だけ人間が承認する。

## 設計

### 1. CI: 7種の配置表

「コミット毎」とは、ブランチへの push 毎にリモートCIが起動することを指す。起動後に何を走らせるかを段階で分ける。

| 処理 | ローカル Hook | リモート: 全 push（コミット毎） | リモート: マージキュー/main |
| --- | --- | --- | --- |
| Format | 編集後 Hook で自動修正 | 差分検査のみ（未整形ならfail）。必須 | 実行しない（push時に済み） |
| Lint | 編集後 Hook（変更ファイルのみ） | 必須。変更ファイルのみ | 全体 |
| 静的解析（型検査含む） | コミット前 Hook（増分） | 必須。影響範囲 | 全体 |
| ビルド | タスク終了時 Hook | 必須。キャッシュ有効 | 本番成果物のビルドはここで1回だけ行い、以後の環境へ同一成果物を昇格 |
| UT | コミット前に影響範囲のテストのみ | 必須。影響範囲選択 + 並列（軽量段階通過後） | 全UT |
| SAST | 実行しない（時間が長い） | 変更ファイル増分、重要度high以上でfail（軽量段階通過後） | 全体 |
| SCA | 実行しない | **ロックファイル/依存定義を最新の脆弱性DBで照合する軽量スキャンを毎 push 実行**（コード解析を伴わないため短時間） | 全体 + 毎日の定期実行 |

SCA は前提事実6のとおり、コードが同じでも結果が変わるため、「依存定義が変わったときだけ」には絞らない。ただし照合対象は依存定義のみなので、毎 push でも安い、という仮定を置く（未検証）。

### 2. コミット毎の実行を保ったまま削減する手段

起動はするが、起動後の仕事量を減らす。

1. **古い実行の自動キャンセル**: 同一ブランチに新コミットが来たら前の実行を中止する。エージェントが数分間隔で連続 push する場合、重いジョブの完走回数が push 回数の 1/3〜1/5 程度になる想定（仮定: 連続 push 3〜5回に1回しか最後まで走らない）。人間が間隔を空けて push する場合は効かない。
2. **段階実行（軽量→重い）**: Format/Lint/型検査（数十秒）が通るまで UT・SAST を起動しない。失敗コミットの比率が 30% なら、失敗コミットで重いジョブ分の計算を節約できる。失敗がほぼ無いブランチでは効かず、直列化で待ち時間が数十秒増える。
3. **変更範囲での絞り込み**: パスフィルタと影響範囲に基づくテスト選択。変更がドキュメントや一部モジュールに限られるコミットでは UT・SAST の対象が縮む（概算: 変更が全体の 1 割未満なら対象も同程度まで縮むと仮定）。依存関係が広いモジュール（共通ライブラリ）の変更には効かない。
4. 補助: 依存キャッシュ、マージキュー（main に入る直前の統合結果だけ全UTを回す）。

### 3. ローカルHookの迂回を前提にした扱い

- **強制はリモート側のみ**: ブランチ保護で、必須チェック（`gate-lite`＝Format/Lint/型検査/改ざん検査、`build`、`ut`、`sast`、`sca`）の通過とマージキュー経由を必須にする。
- **ローカル結果の再利用は行わない。** リモートが再実行する。ローカル Hook は「早く失敗して往復を減らす」補助に位置づけ、通過の根拠にしない。署名なしの証明書は偽造でき、後続チェックの成否から偽造も検知できないため、再利用条件は「該当なし」とする。
- **ローカル結果を再検証に使える唯一の場面**: ローカルが失敗した場合は push 前に修正されるので、リモートの失敗コミット比率（手段2の効果）が下がる。これはリモート判定の省略ではなく、無駄な push の削減として効く。
- Format/Lint を毎 push リモートでも走らせる分の計算は残る。数十秒で決定的なので、手段1・2で他の重いジョブが減る分で吸収する、というトレードを受け入れる。

### 4. エージェントによる改ざんの検出・防止

- **保護パス**: `.github/workflows/`、Hook 設定、CD プロファイル、`CODEOWNERS`、リンタ設定、テスト設定に加え、**ビルド/テストの実行定義（ビルドスクリプト、テストランナー設定、テストヘルパのうち実行を制御するもの）**を CODEOWNERS で人間必須にする。エージェントのトークンには保護パスへの書込を与えず、保護パスを含む PR は自動マージ不可。
- **テスト弱体化検査（`gate-lite` 内、決定的）**: 差分から、テスト関数の削除、`skip`/`xfail`/`only` の追加、期待値の緩和（等値→真偽値など）、カバレッジ閾値の低下を検出し、検出時は fail させて人間レビューを要求する。**アサーション数の減少は fail ではなく警告**とし、PR に「アサーション整理の理由」ラベルが付いている場合のみ許可する（正当なリファクタの誤検知を避ける）。
- **ミューテーション抜き打ち**: 日次で少数のミューテーションを注入し、テストが検出するかを見る。検出率が下がったらアラート。

### 5. CD: 環境別プロファイル

| 環境 | 方式 | 自動調整するパラメータ | 昇格/ロールバック条件 |
| --- | --- | --- | --- |
| dev | 全置換 | レプリカ1、待機なし | ヘルスチェック失敗でロールバック |
| stg | Blue Green | レプリカ=prodの25%、切替前にスモーク+負荷テスト | スモーク失敗、エラー率>1%、p95レイテンシがベースライン+30%超でロールバック |
| prod（通常） | カナリア | トラフィック 1%→5%→25%→100%。各段の待機は「最低リクエスト数1000件を観測するまで」または10分の長い方 | エラー率が旧版+0.5ポイント超、p95がベースライン+20%超が2回連続でロールバック |
| prod（低トラフィック） | ダークカナリア→Blue Green | 複製トラフィックで検証後に切替。1000件に達しない場合は時間を延長 | 複製側のエラー率が旧版を+0.5ポイント超で上回る、または**応答差分率が1%（副作用のない読み取り系の想定。非決定的なフィールドは比較から除外）**を超えたら中止 |
| prod（状態を伴う変更） | 人間承認後にBlue Green | DBは前方互換の分割リリース | 手動ロールバック手順を必須化 |

**方式の選択基準**: 状態変更なし＋十分なトラフィック→カナリア。トラフィック少 or 副作用のない読み取り系→ダークカナリア。即時切戻しが必須で環境2倍が許容できる→Blue Green。

**閾値の決め方（実測がない場合を含む）**: 旧版の過去7日の実測があればそこから導出する。**実測がない（新サービス・導入初期）場合は上の仮置き値を使わず、その環境の自動昇格を無効にして人間承認にフォールバックする。**実測が7日分たまった時点で自動判定を有効化する。「状態を伴う変更」の検出は、マイグレーションファイルの有無とスキーマ差分検査で行い、検出できない変更は prod で人間承認を要求する側に倒す。

### 6. 導入手順

1. リモートに必須チェックとブランチ保護、キャンセル、キャッシュを入れる（Hook 無しで効果が出る）。
2. 保護パスと `gate-lite`（改ざん検出）を入れる。
3. ローカル Hook（Format/Lint）を入れ、リモートの失敗コミット比率の低下を計測する。
4. 段階実行・パスフィルタ・マージキューを入れる。
5. CD: dev/stg の自動化（stg で実測を貯める）、次に prod カナリア（実測が貯まるまでは人間承認）、最後にダークカナリアを入れる。

### 7. 人間と自動の境界

自動: CI の全判定、dev/stg/prod の通常リリースと自動ロールバック（実測が貯まった環境のみ）。人間承認: 保護パスの変更、状態を伴う変更、実測のない環境の prod 昇格、prod 初回の100%拡大（新サービスのみ）、閾値の変更。レビュアーが見るのは「機械が見られないこと」（設計意図、仕様適合）のみにする。

## 評価基準への適合

- **c1**: 配置表で7種すべての場所と、コミット毎（全 push）・マージ時のタイミングを定めた。
- **c2**: キャンセル、段階実行、変更範囲絞り込みの3手段に前提付き概算と効かない場面を書いた。
- **c3**: ブランチ保護の必須チェックを定め、ローカル結果の再利用は行わない（再検証=リモート再実行）と明記した。
- **c4**: 環境別表で方式・パラメータ・ロールバックの指標と閾値、実測なしの場合のフォールバックを示した。
- **c5**: 保護パス、テスト弱体化の差分検査、ミューテーション抜き打ちを定めた。
- **c6**: 5段階の導入順を示した。
- **c7**: トレードオフと失敗モードを下に記す。
- **c8**: 自動と人間承認の境界を節7に書いた。

## トレードオフ

- ローカル結果を再利用しないため、Format/Lint の計算が毎 push 残る。決定的で短いので、安全性（偽造不能）と引き換えに計算削減の一部を捨てた。
- テスト弱体化検査は誤検知を生み、人間レビューが一部増える。アサーション数は警告に留めて緩和したが、ゼロにはならない。
- SAST をローカルで実行しないため、セキュリティ指摘のフィードバックが push 後まで遅れる。
- 実測のない環境では prod の自動判定が使えず、導入初期は人間承認が増える。

## 想定される失敗モード

1. **自動キャンセルで失敗の原因コミットが特定できない**: 発生条件は、連続 push の途中のコミットが壊れていた場合。緩和策は、マージキューで最終状態のみ全チェックし、失敗時は二分探索で原因を特定すること。
2. **カナリア判定が低トラフィックで揺れる**: 発生条件は、段階のリクエスト数が少なく、エラー率が偶然閾値を超える場合。誤ロールバックが続く。緩和策は、最低リクエスト数の待機条件と、2回連続での判定。
3. **保護パスの回避**: 発生条件は、保護パスの外にゲートの無効化を仕込まれる場合。緩和策は、実行定義を保護対象に含め、保護パスの定義を定期的に棚卸しすること。
4. **毎 push の SCA/Lint がボトルネック化**: 発生条件は、エージェントが秒単位で連続 push し、軽量ジョブでも並列枠を食い潰す場合。緩和策は、自動キャンセルの徹底と、軽量ジョブ専用の並列枠の確保。

## 前提と未確認事項

- 連続 push の頻度、失敗コミット比率、各チェックの所要時間、影響範囲選択での縮小率は未確認で、削減幅の概算はすべて仮定である。
- SCA の軽量スキャンが「毎 push でも短時間」という前提は未検証。
- 閾値（エラー率+0.5ポイント、p95+20%、1000件、応答差分率1%など）は一般的な値の仮置きで、実測導出に置き換える。
- ミューテーション抜き打ちのコストと有効性は未検証。
- ローカル Hook をエージェントにどこまで強制できるかは基盤に依存し未確認。

## 改稿で変えた点

1. **証明書による再実行省略を撤回した。** 署名なしの証明書は偽造でき、後続チェックの成否からは偽造を検知できない、という指摘が当たっている。リモートは Format/Lint を毎回再実行し、ローカル結果はリモート判定に使わない設計に変えた。c2 の3手段目は「証明書」から「変更範囲での絞り込み」に差し替えた。
2. **配置表に「全 push（コミット毎）」列を設け**、SCA も毎 push の軽量スキャンに変更した（日次・マージ時のみに寄せない）。
3. **閾値の決め方を明示した。** 実測がない環境では仮置き値を使わず自動昇格を無効にして人間承認へ落とす。ダークカナリアの応答差分率にも具体値（1%）を置いた。
4. **保護パスにビルド/テスト実行定義を最初から含め、**アサーション数減少は fail から警告＋ラベル許可に緩和した。

## 反論

- 「後続チェックが落ちても Lint の不正スキップは観測できない」という指摘は当たっているが、これは証明書を撤回したことで解消したため、反論ではなく受け入れた。
- 「Format がマージ時に『実行しない』のは未整形コードが main に入る」: 改稿後は全 push で Format を必ず検査するので、マージ時に再実行しなくても main に入る内容は検査済みである。ただし push 後にベースが進んだ場合の整合は、マージキューの統合結果ビルドと Lint 全体実行で担保する。
- 「状態を伴う変更を通常の自動フローから除外する検出条件が不足」は部分的に受け入れ、マイグレーション差分検査と、検出不能時は人間承認に倒す方針を書いた。完全な検出は保証しない。
