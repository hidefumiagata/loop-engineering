## 案の要旨

CIは「ローカルHookは早期フィードバック、リモートCIは強制力のある品質ゲート」と分け、コミット毎のリモート実行は維持しつつ、影響範囲選択・段階実行・古い実行のキャンセルで待ち時間を抑える。  
CDは同じ成果物をdev→stg→prodへ昇格し、環境ごとにレプリカ数・トラフィック段階・判定閾値・待機時間を自動調整する。  
本案ではローカル結果を信頼しすぎず、PR時・マージ時・本番昇格時に人間承認を残す。

## 設計

### 全体像

```
AI Agent
  ├─ file edit hook: format/lint quick feedback
  ├─ pre-commit hook: affected UT/static quick feedback
  └─ task-end hook: build/security quick feedback
        │  ※迂回されてもよい前提。成功しても通過扱いにはしない。
        ▼
Remote CI on every pushed commit
  ├─ integrity gate
  ├─ fast gate: format/lint/static
  ├─ affected gate: build/UT/SAST/SCA decision
  └─ annotations for reviewer
        ▼
PR full gate before human review / merge
        ▼
Merge queue gate on merged tree
        ▼
CD: dev → stg → prod
```

### CIの実行規則

リモートCIは、AIエージェントの各pushコミットで必ず起動する。ローカルHookは開発効率のために使うが、必須ゲートではない。

| 対象 | ローカルHookでの実行 | リモートCI：コミット毎 | PR時 | マージ時 |
|---|---|---|---|---|
| ビルド | タスク終了時に、変更されたパッケージ・サービスのみビルド。失敗時はエージェントに修正させる。 | 変更パスと依存関係から影響を受ける単位だけビルド。ビルド定義・共通ライブラリ変更時は広めに実行。 | 全ビルド、または影響範囲選択が保守的に全体と判定した場合は全体ビルド。 | マージキュー上の最終ツリーで、デプロイ成果物をリモート側で再ビルド。 |
| UT | pre-commitで変更ファイルに対応するUT、変更されたテスト自身を実行。 | 影響範囲UTを必須実行。テスト追加・削除・skip変更がある場合は該当コンポーネントのUTを拡大。 | 全UTを必須実行。時間が長い場合も品質ゲートとして残す。 | マージ後ツリーで少なくとも影響範囲UT、PR full gateから差分があれば全UT。 |
| Lint | ファイル編集後またはpre-commitで変更ファイルに対して実行。 | 変更ファイルと、lint設定変更時は全対象に実行。 | lint設定変更時は全体、通常は変更範囲。 | マージキュー上で変更範囲を再実行。 |
| Formatチェック | ファイル編集後に自動整形、pre-commitで差分チェック。 | 変更ファイルに対してformat checkを必須実行。formatter設定変更時は全体。 | 全体または影響範囲。formatter設定変更時は全体。 | マージキュー上で再実行。 |
| SAST | タスク終了時に軽量ルールのみ任意実行。 | 変更ファイルに対する差分SASTを必須実行。認証・入力検証・シリアライズ等の高リスク領域変更時は範囲拡大。 | 全体SASTを必須実行。 | マージ候補ツリーで、少なくとも差分SAST。前回fullからCI設定・SAST設定変更があれば全体。 |
| SCA | 依存定義・lockfile変更時にローカルで確認。 | 毎コミットでSCA判定ジョブを起動。依存定義・lockfileが変わった場合、または脆弱性DB結果の鮮度が所定時間を超えた場合にスキャン。変化なしなら直近のリモート結果を参照し、skip理由を記録。 | freshな脆弱性DBでSCAを必須実行。 | マージ直前にSCA結果が古ければ再実行。 |
| 静的解析 | pre-commitで型検査・簡易解析を変更範囲に実行。 | 影響範囲の型検査・静的解析を必須実行。解析設定変更時は全体。 | 全体静的解析を必須実行。 | マージキュー上で差分または全体を再実行。 |

リモート必須チェックは少なくとも以下に分ける。

1. `ci-integrity`  
   テスト削除、skip追加、assertion弱体化、Hook/CI/CD設定変更を検出する。
2. `ci-fast`  
   Format、Lint、静的解析の軽量部分を実行する。
3. `ci-build-ut`  
   影響範囲のビルドとUTを実行する。
4. `ci-security`  
   SAST差分、SCA判定またはSCA実行を行う。
5. `ci-full-pr`  
   PR時の全体ビルド、全UT、全体SAST、fresh SCA、全体静的解析。
6. `ci-merge-queue`  
   マージ候補ツリーで最終確認し、デプロイ用成果物を作る。

ブランチ保護では、少なくとも最新コミットの `ci-integrity`、`ci-fast`、`ci-build-ut`、`ci-security`、PRの `ci-full-pr`、マージキューの `ci-merge-queue` を必須にする。

### ローカルHook結果の扱い

ローカルHookは迂回・無効化されうるため、成功結果をリモートの合格根拠にはしない。リモート側では次の条件で扱う。

- Format、Lint、静的解析、UT、ビルド、SAST、SCAはいずれも、リモートで再検証する。
- ローカル失敗ログが渡せる場合は、リモートCIの注釈や失敗箇所の優先実行に使ってよいが、pass判定には使わない。
- ローカル結果を補助情報として使う条件は、対象コミットSHA、ツリーhash、依存lock hash、CI設定hash、ツール設定hashが一致する場合のみ。
- 一致しない、またはHook/CI/CD設定・依存定義・テスト基盤が変更された場合は、ローカル情報を無視する。

### CI時間削減策と概算

概算のため、基準モデルを置く。1コミットで全チェックを毎回フル実行すると、直列換算で18分、内訳はFormat/Lint/静的解析2分、UT5分、ビルド4分、SAST4分、SCA3分とする。実測値ではない。

1. 変更パスと影響範囲による選択  
   平均的なコミットが全体の20〜40%のコンポーネントに閉じるなら、UT・ビルド・SAST・静的解析の実行量は18分から6〜8分程度まで下がる想定。効かない場面は、共通ライブラリ、ビルド設定、CI設定、依存定義、横断的リファクタの変更時で、この場合は全体実行に倒す。

2. 軽量チェックから重いチェックへの段階実行  
   まず2分程度のFormat/Lint/静的解析を実行し、失敗したらUT・ビルド・SAST・SCAを開始しない。AIコミットの30%が軽量チェックで落ちる前提なら、重い処理16分の30%、約4〜5分/コミットを節約できる。効かない場面は、ほとんどのコミットが軽量チェックを通る場合、または失敗がUT・SASTでしか見つからない場合。

3. 同一ブランチの古い実行の自動キャンセル  
   AIが短時間に連続pushする場合、同じブランチの古い未完了CIをキャンセルし、最新コミットだけ完走させる。例えば15分内に5コミットpushされ、各CIが6分かかるなら、古い4本の途中実行を止めることでブランチ単位のrunner時間を40〜70%程度減らせる可能性がある。効かない場面は、push頻度が低い場合、mainやマージキューのように全実行を残したい場合。

4. 依存キャッシュと並列化  
   依存取得、ビルド中間成果物、SCAの依存解決結果を、lock hashと設定hashをkeyにキャッシュする。lockfileが変わらない前提ならビルド・SCA周辺の時間を20〜50%削減し、wall clockも並列実行で短縮する。効かない場面は、lockfile変更、キャッシュcold start、テストが逐次実行しかできない場合。

### テスト弱体化と設定改変への対策

`ci-integrity`で以下を検査する。

- テストファイル削除、テストケース数減少、skip/disabled/todo/onlyの追加を差分検出する。
- assertion削除、期待値の空化、常にtrueになる条件、例外握りつぶしなどを言語別パターンで検出する。
- 変更コンポーネントのテスト数またはcoverageが、基準ブランチから一定以上低下した場合はfailまたは人間承認必須にする。
- Hook、CI、CD、ビルド、テストランナー、SAST/SCA設定ファイルの変更は保護パス扱いにし、通常のCI成功だけではマージできない。
- CI設定を変更したPRでは、変更後CIだけでなく、保護された最小メタチェックを必ず実行する。

### CD設計

CDはマージキューで作られた同一成果物を、dev、stg、prodへ昇格する。環境ごとに以下を自動調整する。

| 環境 | 方式 | 自動調整するパラメータ | 決め方 | ロールバック条件 |
|---|---|---|---|---|
| dev | Blue Green | レプリカ数、切替待機時間、smoke対象 | レプリカ数は最小1を基本に、直近dev負荷があれば `ceil(観測RPS / 目標RPS)`。待機は5分またはsmoke完了まで。 | smoke失敗、error率10%以上、p95 latencyが旧版または基準値の3倍超。 |
| stg | ダークカナリア後にBlue Greenまたは小カナリア | レプリカ数、複製トラフィック割合、可視トラフィック段階、待機時間 | レプリカ数はprod想定の一部または最小2。ダークカナリアは読み取り・副作用なしリクエストを最大100%複製。可視段階は10%→50%→100%、各10〜15分。 | ダーク比較の不一致率1%超、error率2%以上または旧版比+1pt超、p95 latency 1.5倍超。 |
| prod | 原則カナリア。可能なら事前にダークカナリア。条件が合う場合のみBlue Green | レプリカ数、初期カナリア割合、拡大段階、各段階の待機時間、判定閾値 | レプリカ数は直近7日程度のp95負荷を基準に、余裕率を加えて算出。可視トラフィックは1%→5%→25%→50%→100%。待機は各15分以上か、最低リクエスト数に達するまで。低トラフィック時は自動拡大せず人間判断。 | candidateのerror率が1%以上かつ旧版比+0.5pt超、p95 latencyが旧版比20%超悪化、リソース飽和85%超、重大アラート、ダーク比較不一致0.1%超。 |

方式選択基準は次の通り。

- Blue Greenは、環境を二重に持てて、DBスキーマ等の状態変更が後方互換で、即時切戻しできる場合に使う。
- カナリアは、prodのように実トラフィックで段階判断したい環境で使う。ただし統計的に十分なトラフィックがない場合は待機時間を延ばすか人間承認に止める。
- ダークカナリアは、複製トラフィックで副作用を出さず比較できる場合に使う。書き込みや外部通知など副作用が抑制できない処理には使わない。
- DB破壊的変更、非互換スキーマ変更、戻せないデータ変換は自動ロールバック対象にせず、expand/contract型の段階移行と人間承認を必須にする。

### 導入手順

1. 既存のビルド、UT、Lint、Format、SAST、SCA、静的解析のコマンドを一覧化し、リモートCIでコミット毎に起動する最小パイプラインを作る。
2. ローカルHookを追加し、Format/Lint/影響範囲UTをAIエージェントに早期実行させる。ただし必須ゲートにはしない。
3. ブランチ保護に `ci-integrity`、`ci-fast`、`ci-build-ut`、`ci-security` を設定する。
4. 影響範囲選択、キャッシュ、古い実行のキャンセル、段階実行を入れる。
5. PR full gateとマージキューgateを追加し、全体チェックと最終成果物生成を分離する。
6. devへのBlue Green自動デプロイを開始する。
7. stgでダークカナリアと小カナリアを導入する。
8. prodは最初は人間承認後にカナリアを開始し、メトリクスと閾値が安定してから自動拡大範囲を広げる。

### 人間と自動化の責任分界

自動化は、機械的チェック、影響範囲選択、CI合否、dev/stgデプロイ、prodカナリアの段階拡大・停止までを担当する。  
人間は、PRの意味的レビュー、テスト弱体化・設定変更の承認、prod開始承認、DBなど不可逆変更の承認、品質ゲートのoverride判断を担当する。  
最終責任は、コードのマージはレビュー承認者、prod反映はリリース承認者に残す。

## 評価基準への適合

- c1: 7種すべてについて、ローカルHook、リモートCIのコミット毎、PR時、マージ時の実行内容を表で定義した。SCAも毎コミットで判定ジョブを起動し、条件に応じて実スキャンまたはリモート結果参照を行う。
- c2: 影響範囲選択、段階実行、古い実行のキャンセル、キャッシュ・並列化を示し、18分基準モデルで削減幅と効かない場面を明記した。
- c3: ローカルHookは迂回可能とし、リモート必須チェックをブランチ保護に残した。ローカル結果は合格根拠にせず、hash一致時のみ補助情報として使い、リモートで再検証する。
- c4: dev/stg/prodごとに、レプリカ数、トラフィック段階、閾値、待機時間の決め方を定義した。Blue Green、カナリア、ダークカナリアの選択基準とロールバック条件も示した。
- c5: テスト削除、skip追加、assertion弱体化、coverage低下、Hook/CI/CD設定改変を `ci-integrity` で検出し、保護パスは人間承認必須にした。
- c6: 最小リモートCIから始め、Hook、保護設定、削減策、PR full gate、CDのdev→stg→prodへ段階導入する順序を示した。
- c7: トレードオフを複数明記し、失敗モードは発生条件と緩和策の組で記述した。
- c8: 自動化する範囲と、人間が承認・責任を持つ範囲を分けた。

## トレードオフ

- ローカルHookの成功を信用しないため、同じ種類のチェックをローカルとリモートで重複実行する。速度だけを見ると無駄が残るが、迂回・無効化を前提に強制力を優先する。
- コミット毎のリモートCIでは影響範囲選択を使うため、すべてのコミットで常に全体UT・全体SASTを走らせるわけではない。代わりにPR full gateとマージキューgateで補完する。
- prodのカナリアは即時100%リリースより遅い。メトリクス収集と待機時間を重視するため、リリース速度を一部犠牲にする。
- テスト弱体化やCI/CD設定変更を保護パス扱いにするため、正当なテスト整理やパイプライン改善でも人間承認が増える。
- DBなど状態を伴う変更は自動ロールバックしないため、完全自動CDの範囲を限定する。

## 想定される失敗モード

1. 発生条件: 影響範囲選択が依存関係を取りこぼし、必要なUTやビルドを実行しない。  
   緩和策: 共通ライブラリ、設定、依存定義変更時は全体実行に倒す。PR full gateとマージキューgateで全体確認を行う。

2. 発生条件: prodのトラフィックが少なく、カナリアのerror率やlatencyが統計的に判断できない。  
   緩和策: 最低リクエスト数に達するまで待機を延ばす。達しない場合は自動拡大せず、人間承認に切り替える。

3. 発生条件: AIが検出パターンをすり抜ける形でテストを弱体化する。例えばassertionを残したまま意味のない期待値に変える。  
   緩和策: テスト数・skip・coverage・assertion差分の機械検出に加え、テスト変更をレビュー注目差分として提示し、保護パス承認を要求する。

4. 発生条件: DBスキーマ変更やデータ変換が非互換で、Blue Greenやカナリア後に旧版へ戻せない。  
   緩和策: expand/contract型の後方互換移行を必須にし、破壊的変更は自動ロールバック対象外として人間承認と個別手順に切り出す。

## 前提と未確認事項

- リポジトリ構成、言語、テストフレームワーク、実際のCI時間は不明である。18分の基準モデルと削減幅は、設計比較のための仮定であり実測ではない。
- 影響範囲選択に必要な依存グラフを正確に作れるかは未確認である。難しい場合は、より保守的に全体実行へ寄せる必要がある。
- 各環境の実トラフィック量、メトリクスの種類、既存の監視精度は不明である。CDの閾値は初期値であり、実測に基づく調整が必要になる。
- ダークカナリアで副作用なしにトラフィック複製できるかは未確認である。外部通知、決済、書き込み処理がある場合は対象を限定する必要がある。
- ブランチ保護、マージキュー、必須チェック、古いCIのキャンセル、キャッシュ機構が利用できる前提を置いたが、具体的なCI/CD製品は指定していない。
- coverageやassertion数の検出は言語・テストフレームワーク依存であり、汎用パターンだけでは誤検知・見逃しが起こりうる。
