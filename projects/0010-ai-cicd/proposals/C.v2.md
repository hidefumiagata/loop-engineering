## 案の要旨

CIは「ローカルHookは早期フィードバック、リモートCIは強制力のある品質ゲート」と分ける。AIエージェントのコミットごとにリモートCIは必ず起動するが、全コミットで全量チェックを完走させるのではなく、影響範囲選択、軽量チェック先行、古い実行のキャンセル、PR/マージ段の実行回数制御で待ち時間を抑える。

CDは同一成果物を dev → stg → prod に昇格し、環境ごとにレプリカ数、トラフィック段階、判定閾値、待機時間を自動調整する。ただし低トラフィック環境では統計判断を信用しすぎず、最低リクエスト数に満たない場合は自動拡大・自動ロールバック判定を限定し、人間承認へ倒す。

本案ではローカルHookの成功を合格根拠にしない。PR時、マージ時、本番開始時、不可逆変更時には人間承認を残す。

## 設計

### 全体像

```
AI Agent
  ├─ file edit hook: format/lint quick feedback
  ├─ pre-commit hook: affected UT/static quick feedback
  └─ task-end hook: build/security quick feedback
        │  ※迂回されてもよい。成功しても合格扱いにしない。
        ▼
Remote CI on every pushed commit
  ├─ integrity gate
  ├─ fast gate: format/lint/static
  ├─ affected gate: build/UT/SAST/SCA decision
  └─ annotations for reviewer
        ▼
PR full gate on latest PR head
        ▼
Merge queue gate on merged tree
        ▼
CD: dev → stg → prod
```

### CIの実行規則

リモートCIは、AIエージェントの各pushコミットで必ず起動する。ローカルHookは開発効率のために使うが、必須ゲートではない。

| 対象 | ローカルHookでの実行 | リモートCI：コミット毎 | PR時 | マージ時 |
|---|---|---|---|---|
| ビルド | タスク終了時に変更パッケージ・サービスのみビルド。 | 変更パスと依存関係から影響範囲のみビルド。ビルド定義・共通ライブラリ変更時は全体寄せ。 | 最新PR headで全ビルド、または影響範囲判定が保守的に全体とした場合は全体。 | マージキュー上の最終ツリーでデプロイ成果物をリモート再ビルド。 |
| UT | pre-commitで変更ファイル対応UTと変更されたテストを実行。 | 影響範囲UTを必須実行。テスト削除・skip追加・assertion変更があれば該当コンポーネントを拡大。 | 最新PR headで全UT。古いPR full実行はキャンセル。 | マージ後ツリーで影響範囲UT。base差分が大きい、依存・テスト基盤変更がある場合は全UT。 |
| Lint | 編集後またはpre-commitで変更ファイルに実行。 | 変更ファイルに実行。lint設定変更時は全体。 | 通常は変更範囲、lint設定変更時は全体。 | マージキュー上で変更範囲を再実行。 |
| Formatチェック | 編集後に自動整形、pre-commitで差分チェック。 | 変更ファイルに必須実行。formatter設定変更時は全体。 | 通常は変更範囲、設定変更時は全体。 | マージキュー上で再実行。 |
| SAST | タスク終了時に軽量ルールを任意実行。 | 変更ファイルへの差分SASTを必須実行。認証・入力検証・シリアライズ等の高リスク領域変更時は範囲拡大。 | 最新PR headで全体SAST。 | マージ候補ツリーで差分SAST。SAST設定変更時は全体。 |
| SCA | 依存定義・lockfile変更時に確認。 | 毎コミットでSCA判定ジョブを起動。依存定義・lockfile変更時、または最後に成功したリモートSCA結果のDB鮮度が所定SLOを超えた時だけ実スキャン。変化なしなら直近リモート結果を参照し、skip理由を記録する。外部DB照会はコミットごとに行わず、取得済みDB snapshotの時刻で判定する。 | freshなDB snapshotでSCAを必須実行。取得不能ならholdまたはfail。 | マージ直前にSCA結果が古ければ再実行。 |
| 静的解析 | pre-commitで型検査・簡易解析を変更範囲に実行。 | 影響範囲の型検査・静的解析を必須実行。解析設定変更時は全体。 | 最新PR headで全体静的解析。 | マージキュー上で差分または全体を再実行。 |

リモート必須チェックは論理的には以下に分ける。

1. `ci-integrity`  
   テスト削除、skip追加、assertion弱体化、Hook/CI/CD設定変更を検出する。
2. `ci-fast`  
   Format、Lint、静的解析の軽量部分を実行する。
3. `ci-build-ut`  
   影響範囲のビルドとUTを実行する。
4. `ci-security`  
   SAST差分、SCA判定またはSCA実行を行う。
5. `ci-full-pr`  
   最新PR headで全体ビルド、全UT、全体SAST、fresh SCA、全体静的解析を行う。
6. `ci-merge-queue`  
   マージ候補ツリーで最終確認し、デプロイ成果物を作る。

ただしブランチ保護上の物理ステータスは増やしすぎない。通常は `ci-commit-required`、`ci-pr-required`、`ci-merge-required` の3つに集約し、それぞれの中で上記フェーズの失敗を表現する。保護パス変更時だけ、独立した最小メタチェックを追加必須にする。

### ローカルHook結果の扱い

ローカルHookは迂回・無効化されうるため、成功結果をリモートのpass判定には使わない。使うのは最適化と注釈だけである。

- Format、Lint、静的解析、UT、ビルド、SAST、SCAはいずれもリモートで再検証する。
- ローカル結果から再利用してよいのは、失敗ログ、失敗テストID、影響範囲候補、キャッシュkey候補、レビュー注釈である。
- コミット前HookではコミットSHAが未確定なので、照合条件はツリーhash、依存lock hash、CI設定hash、ツール設定hash、対象ファイル集合とする。push後は対象コミットSHAとツリーhashを対応づける。
- 上記hashが一致しない場合、またはHook/CI/CD設定・依存定義・テスト基盤が変更された場合は、ローカル情報を無視する。
- ローカル生成成果物はデプロイ成果物にしない。マージキュー上のリモートCIで作った成果物だけをCDに渡す。

### CI時間削減策と概算

概算のため、1コミットで全チェックを直列フル実行すると18分と置く。内訳はFormat/Lint/静的解析2分、UT5分、ビルド4分、SAST4分、SCA3分である。実測値ではない。

1. 変更パスと影響範囲による選択  
   平均的なコミットが全体の20〜40%のコンポーネントに閉じるなら、UT・ビルド・SAST・静的解析は18分から6〜8分程度まで下がる想定。効かない場面は、共通ライブラリ、ビルド設定、CI設定、依存定義、横断的リファクタ変更時で、この場合は全体実行に倒す。

2. 軽量チェックから重いチェックへの段階実行  
   まず2分程度のFormat/Lint/軽量静的解析を実行し、失敗したらUT・ビルド・SAST・SCAを開始しない。AIコミットの30%が軽量チェックで落ちる前提なら、重い処理16分の30%、約4〜5分/コミットを節約できる。効かない場面は、ほとんどのコミットが軽量チェックを通る場合、または失敗がUT・SASTでしか見つからない場合。

3. 同一ブランチの古い実行の自動キャンセル  
   AIが短時間に連続pushする場合、最新コミットだけを完走対象にする。古い実行は、可能なら `ci-integrity` と `ci-fast` だけ完走させ、重い段階をキャンセルする。15分内に5コミットpushされ、各CIが6分かかるなら、古い4本の重い処理を止めることでrunner時間を40〜70%程度減らせる可能性がある。効かない場面は、push頻度が低い場合、mainやマージキューのように全実行を残したい場合。

4. 依存キャッシュと並列化  
   依存取得、ビルド中間成果物、SCAの依存解決結果を、lock hashと設定hashをkeyにキャッシュする。lockfileが変わらない前提ならビルド・SCA周辺の時間を20〜50%削減し、wall clockも並列実行で短縮する。効かない場面は、lockfile変更、cache cold start、テストが逐次実行しかできない場合。

5. PR/マージ段の回数制御  
   `ci-full-pr` は各pushごとに完走させず、最新PR headだけを対象にし、古いfull実行はキャンセルする。10コミットのPRで毎回18分fullを走らせると直列換算180分だが、本案ではコミット段の選択実行に加え、PR fullは最後の1回18分を基本にする。マージキューは統合ツリー差分が小さい場合6〜10分程度、base差分や設定変更がある場合18分相当と見積もる。効かない場面は、PR headが頻繁に更新され続ける場合、base更新が大きく毎回全体実行になる場合である。

### テスト弱体化と設定改変への対策

`ci-integrity`で以下を検査する。

- テストファイル削除、テストケース数減少、skip/disabled/todo/onlyの追加を差分検出する。
- assertion削除、期待値の空化、常にtrueになる条件、例外握りつぶしなどを言語別パターンで検出する。
- 変更コンポーネントのテスト数またはcoverageが基準ブランチから一定以上低下した場合はfailまたは人間承認必須にする。
- Hook、CI、CD、ビルド、テストランナー、SAST/SCA設定ファイルの変更は保護パス扱いにする。
- CI設定を変更したPRでは、PR内で変更されたCI定義だけを信じない。基準ブランチ側にある独立した最小メタチェックで、保護パス変更の検出、必須ジョブ削除、必須条件緩和を検査する。
- 保護パス変更は、通常CIが成功しても自動マージしない。人間承認を必須にする。

### CD設計

CDはマージキューで作られた同一成果物を、dev、stg、prodへ昇格する。

| 環境 | 方式 | 自動調整するパラメータ | 決め方 | ロールバック条件 |
|---|---|---|---|---|
| dev | Blue Green | レプリカ数、切替待機時間、smoke対象 | 低トラフィック前提で、レプリカ数は最小1を基本とする。RPS由来の自動増減は、継続的な制御リクエストまたは観測量がある場合だけ使う。待機はsmoke完了または最大5分。 | デプロイ失敗、health check失敗、smoke失敗。error率・p95 latencyは、ラベル付けされたsmoke/制御リクエストが最低件数に達した場合のみ判定し、単発アクセスでは自動ロールバックしない。 |
| stg | 条件付きダークカナリア後にBlue Greenまたは小カナリア | レプリカ数、複製トラフィック割合、可視トラフィック段階、待機時間 | レプリカ数は最小2を基本に、prod想定の一部。ダークカナリアは副作用を抑制できる読み取り系・比較可能処理に限定し、複製割合は10%から最大100%まで段階化する。可視段階は10%→50%→100%、各10〜15分、かつ最低リクエスト数に達するまで待つ。 | ダーク比較の不一致率1%超、error率2%以上または旧版比+1pt超、p95 latency 1.5倍超。ただし比率判定は最低リクエスト数到達後のみ。 |
| prod | 原則カナリア。可能なら事前にダークカナリア。条件が合う場合のみBlue Green | レプリカ数、初期カナリア割合、拡大段階、各段階の待機時間、判定閾値 | レプリカ数は直近負荷のp95相当を基準に余裕率を加える。可視トラフィックは1%→5%→25%→50%→100%。各段階15分以上、かつcandidate/control双方の最低リクエスト数に達するまで待つ。低トラフィック時は自動拡大せず人間判断。 | candidateのerror率が1%以上かつ旧版比+0.5pt超、p95 latencyが旧版比20%超悪化、リソース飽和85%超、重大アラート、ダーク比較不一致0.1%超。比率系は最低リクエスト数到達後のみ判定し、ダーク0.1%判定は十分な比較件数に達しない限り参考値にする。 |

方式選択基準は次の通り。

- Blue Greenは、環境を二重に持てて、DBスキーマ等の状態変更が後方互換で、即時切戻しできる場合に使う。
- カナリアは、prodのように実トラフィックで段階判断したい環境で使う。ただし統計的に十分なトラフィックがない場合は待機時間を延ばすか、人間承認に止める。
- ダークカナリアは、複製トラフィックで副作用を出さず比較できる場合にだけ使う。書き込み、外部通知、決済など副作用が抑制できない処理では使わない。
- DB破壊的変更、非互換スキーマ変更、戻せないデータ変換は自動ロールバック対象にしない。expand/contract型の段階移行と人間承認を必須にする。

### 導入手順

1. 既存のビルド、UT、Lint、Format、SAST、SCA、静的解析のコマンドを一覧化し、リモートCIでコミット毎に起動する最小パイプラインを作る。
2. ローカルHookを追加し、Format/Lint/影響範囲UTをAIエージェントに早期実行させる。ただし必須ゲートにはしない。
3. ブランチ保護に `ci-commit-required` を設定し、内部で `ci-integrity`、`ci-fast`、`ci-build-ut`、`ci-security` を実行する。
4. 影響範囲選択、キャッシュ、古い実行のキャンセル、段階実行を入れる。
5. `ci-full-pr` と `ci-merge-queue` を追加し、最新PR headとマージ候補ツリーだけを完走対象にする。
6. devへのBlue Green自動デプロイを開始し、smoke中心で判定する。
7. stgで副作用を抑制できる範囲からダークカナリアと小カナリアを導入する。
8. prodは最初は人間承認後にカナリアを開始し、メトリクスと最低リクエスト数の条件が安定してから自動拡大範囲を広げる。

### 人間と自動化の責任分界

自動化は、機械的チェック、影響範囲選択、CI合否、dev/stgデプロイ、条件を満たすprodカナリアの段階拡大・停止までを担当する。

人間は、PRの意味的レビュー、テスト弱体化・設定変更の承認、prod開始承認、DBなど不可逆変更の承認、品質ゲートのoverride判断を担当する。

最終責任は、コードのマージはレビュー承認者、prod反映はリリース承認者に残す。

## 評価基準への適合

- c1: 7種すべてについて、ローカルHook、リモートCIのコミット毎、PR時、マージ時の実行内容を表で定義した。
- c2: 影響範囲選択、段階実行、古い実行のキャンセル、キャッシュ・並列化、PR/マージ段の回数制御を示し、概算と効かない場面を明記した。
- c3: ローカルHookは迂回可能とし、リモート必須チェックを残した。ローカル結果は合格根拠にせず、hash一致時のみログ・対象候補・キャッシュkey候補として使い、リモートで再検証する。
- c4: dev/stg/prodごとに、レプリカ数、トラフィック段階、閾値、待機時間の決め方を定義した。低トラフィック時の最低リクエスト数条件、方式選択基準、ロールバック条件も示した。
- c5: テスト削除、skip追加、assertion弱体化、coverage低下、Hook/CI/CD設定改変を `ci-integrity` で検出し、保護パスは人間承認必須にした。
- c6: 最小リモートCIから始め、Hook、保護設定、削減策、PR full gate、CDのdev→stg→prodへ段階導入する順序を示した。
- c7: トレードオフを複数明記し、失敗モードは発生条件と緩和策の組で記述した。
- c8: 自動化する範囲と、人間が承認・責任を持つ範囲を分けた。

## トレードオフ

- ローカルHookの成功を信用しないため、同じ種類のチェックをローカルとリモートで重複実行する。速度だけを見ると無駄が残るが、迂回・無効化を前提に強制力を優先する。
- コミット毎のリモートCIでは影響範囲選択を使うため、すべてのコミットで常に全体UT・全体SASTを走らせるわけではない。代わりにPR full gateとマージキューgateで補完する。
- 古いCIをキャンセルするため、中間コミットの重いチェック結果は残らないことがある。最新コミットの品質保証とrunner時間削減を優先する。
- prodのカナリアは即時100%リリースより遅い。メトリクス収集、最低リクエスト数、待機時間を重視するため、リリース速度を一部犠牲にする。
- テスト弱体化やCI/CD設定変更を保護パス扱いにするため、正当なテスト整理やパイプライン改善でも人間承認が増える。
- DBなど状態を伴う変更は自動ロールバックしないため、完全自動CDの範囲を限定する。

## 想定される失敗モード

1. 発生条件: 影響範囲選択が依存関係を取りこぼし、必要なUTやビルドを実行しない。  
   緩和策: 共通ライブラリ、設定、依存定義変更時は全体実行に倒す。PR full gateとマージキューgateで全体確認を行う。

2. 発生条件: devやprod初期カナリアのトラフィックが少なく、error率やlatencyが統計的に判断できない。  
   緩和策: devはsmoke中心にし、比率判定は最低件数到達後だけ使う。prodは最低リクエスト数に達するまで待機し、達しない場合は自動拡大せず人間承認に切り替える。

3. 発生条件: AIが検出パターンをすり抜ける形でテストを弱体化する。例えばassertionを残したまま意味のない期待値に変える。  
   緩和策: テスト数・skip・coverage・assertion差分の機械検出に加え、テスト変更をレビュー注目差分として提示し、保護パス承認を要求する。

4. 発生条件: CI/CD設定変更PRで、変更後のCI定義が必須チェックを消す。  
   緩和策: PR内の変更後定義だけを信じず、基準ブランチ側の独立した最小メタチェックで保護パス変更と必須条件緩和を検出する。

5. 発生条件: 古いCI実行をキャンセルした結果、中間コミットの失敗フィードバックが返らない。  
   緩和策: `ci-integrity` と `ci-fast` は可能な限り完走させ、重い段階だけをキャンセルする。キャンセル理由を注釈し、最新コミットで同種チェックを必ず再実行する。

6. 発生条件: DBスキーマ変更やデータ変換が非互換で、Blue Greenやカナリア後に旧版へ戻せない。  
   緩和策: expand/contract型の後方互換移行を必須にし、破壊的変更は自動ロールバック対象外として人間承認と個別手順に切り出す。

## 前提と未確認事項

- リポジトリ構成、言語、テストフレームワーク、実際のCI時間は不明である。18分の基準モデルと削減幅は、設計比較のための仮定であり実測ではない。
- 影響範囲選択に必要な依存グラフを正確に作れるかは未確認である。難しい場合は、より保守的に全体実行へ寄せる。
- 各環境の実トラフィック量、メトリクスの種類、既存の監視精度は不明である。CDの閾値と最低リクエスト数は初期値であり、実測に基づく調整が必要になる。
- ダークカナリアで副作用なしにトラフィック複製できるかは未確認である。外部通知、決済、書き込み処理がある場合は対象を限定または不採用にする。
- ブランチ保護、マージキュー、必須チェック、古いCIのキャンセル、キャッシュ機構が利用できる前提を置いたが、具体的なCI/CD製品は指定していない。
- coverageやassertion数の検出は言語・テストフレームワーク依存であり、汎用パターンだけでは誤検知・見逃しが起こりうる。

## 改稿で変えた点

1. devのCD判定を、RPS・error率・p95 latency中心から、health checkとsmoke中心に変更した。低トラフィック時は比率判定を使わず、最低リクエスト数に達した場合だけ統計的指標を見るようにした。
2. ローカルHook結果の再利用を具体化した。成功結果をpass判定に使わず、失敗ログ、対象候補、キャッシュkey候補、注釈だけに限定し、コミット前はコミットSHAではなくツリーhash等で照合するようにした。
3. PR full gateとマージキューgateの計算量を抑えるため、最新PR headだけを完走対象にし、古いfull実行をキャンセルする規則と概算を追加した。
4. SCA判定で外部DBへコミットごとに照会する前提をやめ、リモート側の取得済みDB snapshotの鮮度で実スキャン要否を判定する設計にした。
5. CI/CD設定変更の自己参照問題に対して、PR内の変更後CI定義だけを信じず、基準ブランチ側の独立した最小メタチェックで検出する規則を追加した。

## 反論

- ローカルHookの成功結果をリモートpass判定に使うべき、という含意は受け入れない。前提事実としてローカルHookは迂回・無効化されうるため、成功結果を品質ゲートの根拠にすると強制力が失われる。再利用はログ、対象候補、キャッシュkey候補などの最適化に限定し、合否はリモートで再検証する。
- PR full gateとマージキューgateを削るべき、という方向にはしない。品質ゲートを消して速度を稼ぐ案は制約上不可であり、AIがテストやCI設定を弱体化しうる前提では、PR時の全体確認とマージ候補ツリーでの確認が必要である。ただし、全pushでfullを完走させるのではなく、最新PR headとマージ候補ツリーに限定して計算量を抑える。
- ダークカナリア自体が常に不成立、という指摘は受け入れない。前提事実上、ダークカナリアは「実ユーザーに見せない形で挙動を検証する」方式として選択可能である。ただし、副作用を抑制できない処理には使わない条件を明確にし、既定で最大100%複製する扱いはやめた。
