## 議論したいこと

AIエージェントがコーディングを人間に代わって実施する時代に、CI（コミット毎の機械的チェック）とCD（環境に応じた自動パラメータ調整つきデプロイ）をそれぞれ具体的に何をどう実施するかを決め、現時点の結論を出す。
結論は、CI と CD それぞれの各処理について「何を・どこで・いつ・どの条件で」実施するかが分かる粒度にする。

## 制約

- CI は、人間がレビューする前に機械的に検査できることを検査するためのものであり、コミット毎に実行する。この前提は変えない。
- CI の対象は、ビルド、UT、Lint、Formatチェック、SAST、SCA、静的解析とする。
- CD は環境に合わせてパラメータを自動調整してデプロイする。デプロイ方式は Blue Green、カナリアリリース、ダークカナリアリリース等から選択できる。
- 特定ベンダーの製品導入を前提にしない。GitHub Actions のような一般的な CI/CD を想定してよい。
- 品質ゲートを消すことで速度を稼ぐ案は不可。
- 提案者は実行環境にもWebにも触れない。このブリーフが唯一の事実源である。

## 前提事実

出典: Issue #10 本文（2026-10-04 取得）と、一般に知られた技術的性質。実測値ではない。

1. （Issue 記載）AIエージェントの Hook 機能により、ファイル編集後・コミット前・タスク終了時などに自動発火が可能になった。そのため CI で行いたい Linter や UT を、リモートリポジトリに push しなくても実行できる。
2. （Issue 記載）AIエージェントは大量のコミットを発行するため、CI の発火頻度が大量になり、CI のコンピューティング時間が増大し、CI 待ち時間がボトルネックになる。
3. ローカル（エージェントのサンドボックス）とリモートCIでは環境差がある。OS、依存バージョン、シークレット、外部サービス接続、実行時間制限が異なり、ローカルで通ってもCIで落ちることがある。
4. ローカル Hook は設定次第で迂回・無効化されうる（エージェント自身が回避する可能性を含む）。強制力があるのはリモート側（ブランチ保護・必須チェック）である。
5. CI の一般的な削減手段として、変更パスに応じたフィルタ、影響範囲に基づくテスト選択、依存キャッシュ、並列化、同一ブランチの古い実行の自動キャンセル、マージキュー、軽量チェックから重いチェックへの段階実行がある。
6. 各チェックの性質は異なる。Lint・Format・型検査は数秒から数十秒で決定的。UT は数十秒から数分。SAST・SCA・広範な静的解析・ビルドは数分以上かかることがあり、SCA は依存の脆弱性DBの更新によりコードが同じでも結果が変わりうる。
7. AIが書いたコードには、テストが通るように見せる変更（テストの削除・スキップ・アサーション弱体化）が混ざりうる。Hook / CI 設定自体の改変も同様に検出対象になる。
8. CD のデプロイ方式の一般的な性質: Blue Green は新旧2環境を用意して切り替え、即時にロールバックできるが環境が2倍必要。カナリアは一部の実トラフィックに新版を流して段階的に拡大し、メトリクスで可否を判断する。ダークカナリアは新版へ実ユーザーに見せない形（複製トラフィック等）でリクエストを流し、影響を出さずに挙動を検証する。DBスキーマ変更など状態を伴う変更はロールバックが難しい。
9. CD の自動判断（環境ごとのパラメータ調整、カナリアの拡大や中止）は、メトリクス（エラー率、レイテンシ等）と閾値に依存する。トラフィックが少ない環境では統計的に判断しにくい。

## 検討の対象外

- 特定ツール・製品の比較と選定
- デプロイ先インフラの具体設計、コスト金額の試算
- 組織・採用・評価制度

## 基準の批評で採用しなかった指摘

- 「CI/CD実行環境（コンテナイメージ・ランナー仕様）の定義」を基準 c9 として追加する提案: 採用しない。実行環境の具体設計は特定インフラの話であり、制約（ベンダー非依存）と対象外（デプロイ先インフラの具体設計）に反する。重み3の件数にも余裕がない。
- c1 の網羅範囲の曖昧さ: 採用済み。対象7種すべてと明記した。
- c2 / c7 / c4 の検証可能性: 採用済み。概算の明記、条件と緩和策の組、環境=デプロイ先環境と定義した。
