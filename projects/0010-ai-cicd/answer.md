## 結論

- CI は二層に分ける。ローカル Hook は「早く失敗させて往復を減らす補助」とし、通過の根拠にはしない。リモートは**全 push で7種すべてを自分で実行**し、ブランチ保護の必須チェックとマージキューで強制する。
- ローカル結果は合否に再利用しない。再利用してよいのは失敗ログ、対象候補、キャッシュ key 候補などの最適化情報に限る。
- 計算時間と待ち時間は、起動後の仕事量を減らす手段（古い実行のキャンセル、軽量から重いへの段階実行、変更範囲の絞り込み、キャッシュ、PR/マージ段の完走回数制御）で削る。コミット毎の起動は削らない。削減幅はすべて仮定値である。
- エージェントの改ざんは、保護パス（CODEOWNERS 必須）、テスト弱体化の差分検査、基準ブランチ側の独立したメタチェックで防ぐ。
- CD は同一成果物を dev → stg → prod に昇格し、環境ごとに方式・段階・待機・閾値を宣言する。**実測がない環境、低トラフィック、状態を伴う変更は自動判定を止めて人間承認に倒す。**

## 本論

### 1. CI の配置（c1）

「コミット毎」は、ブランチへの push 毎にリモート CI が起動することを指す。起動後に何を走らせるかを段階で分ける。

| 処理 | ローカル Hook | リモート: 全 push | PR 時 | マージキュー（統合ツリー） |
| --- | --- | --- | --- | --- |
| Format | 編集後に自動整形 | 変更ファイルの差分検査。未整形なら fail。必須 | 設定変更時のみ全体 | 再検査（決定的で数十秒） |
| Lint | 編集後、変更ファイルのみ | 変更ファイル。設定変更時は全体。必須 | 最新 head で変更範囲 | 再実行 |
| 静的解析・型検査 | コミット前、増分 | 影響範囲。必須 | 最新 head で全体 | 差分または全体 |
| ビルド | タスク終了時、変更分 | 影響範囲、キャッシュ有効。必須 | 最新 head で全体 | 統合ツリーで本番成果物を1回だけビルドし、以後はその成果物を昇格 |
| UT | コミット前、影響範囲のみ | 影響範囲選択＋並列（軽量段階通過後）。必須 | 最新 head で全 UT | 全 UT。基盤変更時は必ず全体 |
| SAST | 任意（軽量ルール） | 変更ファイルの差分。high 以上で fail。高リスク領域は範囲拡大 | 最新 head で全体 | 差分。設定変更時は全体 |
| SCA | 依存定義変更時のみ確認 | **毎 push で SCA ジョブを必ず走らせる**（下記） | 最新の脆弱性 DB で全量 | 結果が古ければ再実行。日次定期実行も行う |

SCA は前提事実6のとおり、コードが同じでも結果が変わる。そのため「依存定義が変わったときだけ」には絞らない。毎 push のジョブでは、ロックファイル／依存定義を、リモート側が保持する脆弱性 DB のスナップショットで照合する。スナップショットが鮮度 SLO を超えていれば更新してから照合する。PR 時は最新 DB での全量スキャンを必須にする。コミット毎の軽量照合が「短時間」で済むかは未検証の仮定である。

ブランチ保護の必須ステータスは増やしすぎない。例えば `ci-commit-required` / `ci-pr-required` / `ci-merge-required` の3つに集約し、内部のフェーズ（改ざん検査、軽量、ビルド・UT、セキュリティ）の失敗を各ステータスで表現する。

### 2. 計算時間・待ち時間の削減（c2）

以下の概算は、3案がそれぞれ置いた仮定による。実測値ではなく、重なる部分があるので単純合算はできない。

| 手段 | 前提と概算 | 効かない場面 |
| --- | --- | --- |
| 古い実行の自動キャンセル | 5コミットを1分間隔で push、CI 1回5分の場合、25分が約9分になる（約64%減）。別の置き方では、15分内5 push・各6分で runner 時間が40〜70%減 | push 間隔が CI 完了時間を超える場合、main やマージキュー |
| 軽量→重いの段階実行 | 失敗コミットが30%、重い処理が16分の場合、約4〜5分/コミットを節約 | ほぼ全コミットが軽量段を通る場合。失敗が UT・SAST でしか見つからない場合。直列化で待ちが数十秒増える |
| 変更範囲での絞り込み | 変更が全体の20〜40%に閉じるなら、18分が6〜8分。1割未満なら対象も同程度に縮む | 共通ライブラリ、ビルド設定、CI 設定、依存定義、横断リファクタ（全体実行に倒す） |
| 依存キャッシュ・並列化 | lockfile 不変の通常コミット（約80%と仮定）で約42%減、またはビルド・SCA 周辺で20〜50%減 | lockfile 変更、共通型定義の変更、cold start、逐次実行しかできないテスト |
| PR/マージ段の回数制御 | 10コミットの PR で毎回18分の full を走らせると180分。最新 head のみ完走させれば最後の1回18分が基本 | PR head が頻繁に更新され続ける場合。base 更新が大きく毎回全体実行になる場合 |

パスフィルタは、ドキュメントと見なす範囲を拡張子やディレクトリ名だけで決めてはならない。ドキュメント生成物や API 仕様がビルド・SAST の入力になるリポジトリでは、抑止がゲートの削除になる（レビューで指摘された）。

キャンセルの副作用への対策は次のとおり。

- 古い実行でも改ざん検査と軽量段は完走させる。
- キャンセル理由を注釈に残す。
- 同一ブランチで3回連続キャンセルされたら、最新ジョブを強制同期する。
- エージェント側に直前 push の CI 完了を待つバックオフを設ける。
- マージキューで最終状態を全チェックし、失敗時は二分探索で原因コミットを特定する。

### 3. ローカル Hook の迂回を前提にした扱い（c3）

- 強制力はリモートだけに置く。必須チェックの通過とマージキュー経由をブランチ保護で必須にする。
- ローカルの成功結果は合否に使わない。リモートは同一コミットで7種すべてを再実行し、リモートの終了コードだけを合格条件にする。
- ローカル結果から再利用するのは失敗ログ、失敗テスト ID、影響範囲候補、キャッシュ key 候補、レビュー注釈に限る。照合にはツリー hash、依存 lock hash、CI 設定 hash、ツール設定 hash を使う。コミット前は SHA が未確定のため SHA は使わない。hash が不一致、または Hook/CI/CD 設定・依存定義・テスト基盤が変わった場合は、ローカル情報を無視する。
- ローカル生成の成果物はデプロイしない。マージキュー上のリモートビルドの成果物だけを CD に渡す。
- 署名なしの「証明書」による再実行の省略は採らない（後述「崩れた主張」）。

### 4. エージェントによる改ざんの検出・防止（c5）

- **保護パス**を CODEOWNERS で人間必須にし、保護パスを含む PR は自動マージ不可にする。対象は次のとおり。
  - CI ワークフロー、Hook 設定、CD プロファイル、CODEOWNERS、Lint/Format/SAST/SCA 設定、テスト設定
  - ビルド/テストの実行定義（ビルドスクリプト、テストランナー設定、実行を制御するテストヘルパ）
- エージェントのトークンには保護パスへの書込権限を与えない。
- **テスト弱体化の差分検査**は改ざん検査ジョブの最前段に置き、決定的に行う。検出対象は次のとおり。
  - テスト関数の削除、skip/xfail/only/todo の追加、アサーションのコメントアウト
  - 常に真になる条件への置換、例外の握りつぶし、期待値の緩和
  - カバレッジまたはテスト数の基準ブランチからの低下
- 検出時は fail または人間承認を要求する。
- **自己参照の対策**として、CI 設定を変更する PR では変更後の定義だけを信じない。基準ブランチ側の独立した最小メタチェックで、保護パス変更、必須ジョブの削除、必須条件の緩和を検出する。
- 日次のミューテーション抜き打ちで、テストの検出力の低下を監視する。ただし効果とコストは未検証。

### 5. CD の環境別プロファイル（c4）

CD はマージキューで作った同一成果物を昇格する。閾値は初期値であり、デプロイ先の旧版の過去7日の実測から導出して置き換える。3案の数値には幅があったため、幅を併記する。

| 環境 | 方式 | 自動調整するパラメータ | ロールバック条件 |
| --- | --- | --- | --- |
| dev | 最小構成の Blue Green、または全置換 | レプリカ1〜2、待機はスモーク完了まで（最大5分程度） | デプロイ失敗、`/health` 3回連続失敗、スモーク失敗。エラー率・レイテンシの比率判定は、ラベル付きのスモーク/制御リクエストが最低件数に達した場合だけ使い、単発アクセスでは発火させない |
| stg | 副作用を抑制できる読み取り系はダークカナリア、その後 Blue Green または小カナリア | レプリカは prod の20〜50%（案により25%または最小2）。複製割合は段階化。可視段階は10→50→100%、各10〜15分かつ最低リクエスト数まで待機 | スモーク失敗、エラー率が0.5〜1%超または旧版比 +1pt 超、p95 がベースライン +30% 超（案により1.5倍）、応答差分率1%超。比率判定は最低件数到達後のみ |
| prod（通常） | カナリア | 1%→5%→25%→（50%）→100%。各段は「最低リクエスト数（例: 1000件）到達」または10〜15分の長い方 | エラー率が旧版比 +0.5pt 超、p95 が +10〜20% 超（2回連続で判定）、リソース飽和85%超、重大アラート |
| prod（低トラフィック） | ダークカナリア→Blue Green、または自動拡大を止めて人間判断 | 複製トラフィックで検証後に切替。件数不足なら待機を延長 | 複製側エラー率が旧版を +0.5pt 超で上回る、応答差分率1%超（非決定的フィールドは比較から除外）、例外率 0.5% 以上 |
| prod（状態を伴う変更） | 人間承認後に Blue Green | DB は expand/contract の前方互換の分割リリース | 自動ロールバック対象外。手動ロールバック手順を必須化 |

方式の選択基準は次のとおり。

- 状態変更なしで十分なトラフィックがあるなら、カナリアを使う。
- 低トラフィック、または副作用なしに複製できる読み取り系なら、ダークカナリアを使う。書込・外部通知・決済など副作用を抑制できない処理には使わない。
- 即時切戻しが必須で、環境2倍を許容でき、スキーマ変更が後方互換なら、Blue Green を使う。

実測のない環境（新サービス、導入初期）では、仮置き値を使わず、その環境の自動昇格を無効にして人間承認にフォールバックする。7日分の実測がたまった時点で自動判定を有効にする。状態を伴う変更の検出は、マイグレーションファイルの有無とスキーマ差分検査で行う。検出できない変更は、人間承認を要求する側に倒す。マイグレーション内の非互換変更（カラム削除、NOT NULL の直接追加）は CI の静的解析で自動ブロックする。

### 6. 導入手順（c6）

1. 既存の7種のコマンドを一覧化し、リモートに必須チェック、ブランチ保護、古い実行のキャンセル、キャッシュを入れる。Hook なしで効果が出る。
2. 保護パス、CODEOWNERS、改ざん検査、基準ブランチ側のメタチェックを入れる。
3. ローカル Hook（Format/Lint/影響範囲 UT）を入れ、リモートの失敗コミット比率の低下を計測する。
4. 段階実行、パスフィルタ・影響範囲選択、PR full gate、マージキューを入れる。
5. CD は dev、stg（実測を貯める）の順に自動化する。次に prod カナリアを入れる。実測が貯まるまでは人間承認で開始する。最後にダークカナリアを入れる。

### 7. 自動と人間の境界・トレードオフ・失敗シナリオ（c7, c8）

自動化の範囲は次のとおり。

- CI の全判定
- dev/stg のデプロイ
- 実測のある環境での prod カナリアの段階拡大と自動ロールバック

人間が承認・責任を持つ範囲は次のとおり。

- 保護パスの変更
- テスト弱体化検出への例外承認
- 状態を伴う変更
- 実測のない環境の prod 昇格
- 閾値の変更
- 品質ゲートの override

レビュアーが見るのは、機械が見られないこと（設計意図、仕様適合）に絞る。

**トレードオフ**

- ローカルと同種のチェックをリモートで再実行するため、計算の重複が残る。偽造できないことと引き換えに、Format/Lint の二重実行を受け入れる。
- テスト弱体化検査と保護パスにより、正当なテスト整理やパイプライン改善でも人間承認が増える。
- 古い実行をキャンセルするため、中間コミットの重い検査結果は残らない。
- SAST を主にリモートで実行するため、セキュリティ指摘のフィードバックは push 後まで遅れる。
- prod カナリアは即時100%より遅く、導入初期は人間承認が増える。

**失敗シナリオ（発生条件 → 緩和策）**

1. 影響範囲選択が依存を取りこぼす。発生条件は、依存グラフが不正確、または共通部分の変更である。緩和策は、共通部分・設定・依存定義の変更を全体実行に倒すこと、PR full gate とマージキューで全体確認すること。
2. 連続 push で先行 CI が次々キャンセルされ、エージェントが結果を得ないまま誤った推論でコミットを重ねる。緩和策は、バックオフ制御、3回連続キャンセルで強制同期、改ざん検査と軽量段の完走。
3. 低トラフィックでカナリア判定が揺れる、または不具合を検出できない。発生条件は、深夜帯など件数不足の段である。緩和策は、最低件数の待機条件、2回連続判定、件数不足時は自動拡大を止めて人間判断かダークカナリアへの縮退。
4. 検出パターンをすり抜けるテスト弱体化、または保護パス外へのゲート無効化の仕込み。例えばアサーションを残したまま意味のない期待値に変える。緩和策は、テスト変更をレビュー注目差分として提示すること、実行定義を保護対象に含めること、保護パス定義の定期的な棚卸し。
5. DB の非互換変更で、ロールバックした旧版が新スキーマを扱えない。緩和策は、expand/contract の強制、破壊的変更の自動ロールバック対象外化、人間承認と手順の個別化。
6. 毎 push の SCA/Lint が、秒単位の連続 push で並列枠を食い潰す。緩和策は、キャンセルの徹底と、軽量ジョブ専用枠の確保。

## 3者が一致した点

独立に書かれ、互いに攻撃され、それでも残った合意。結論のうち最も信頼できる部分である。

- **ローカル Hook の成功を合格根拠にしない。** リモートが同一コミットで再検証し、強制力はブランチ保護の必須チェックに置く。3案とも最終稿で一致した。
- **7種すべてを全 push のリモート CI に載せる。** 削減は「起動しない」ではなく「起動後の仕事量を減らす」ことで得る。
- **古い実行の自動キャンセルと、軽量→重いの段階実行を削減手段に含める。** 3案とも前提付きの概算と効かない場面を書いた。
- **CI/Hook/CD 設定、テスト設定、ビルド/テスト実行定義を保護パスとして CODEOWNERS で人間必須にする。** テスト削除、skip 追加、アサーション弱体化、カバレッジ低下を差分検査で検出する。
- **CD は環境別プロファイル。** 低トラフィックでは統計判定を過信しない。最低リクエスト数を待つか、自動判定を止めて人間判断またはダークカナリアへ倒す。
- **状態を伴う変更（DB など）は自動ロールバックの対象外。** expand/contract と人間承認を要求する。
- **導入順は、リモート必須チェックと保護を先に入れ、CD は dev → stg → prod の順に入れる。**
- **閾値と削減幅は仮定値であり、実測で置き換える。**

## 攻撃に耐えた主張

- **ローカル結果を再利用せず、リモートで全再検証する（A、B、C）。** 「再利用側が空で c3 に弱い」「二重実行でコスト面が弱い」という指摘があったが、3案とも曲げなかった。根拠は次のとおり。
  - 前提事実4により、ローカル結果は迂回・偽造されうる。
  - 制約により、品質ゲートを消して速度を稼ぐ案は不可である。
  - c3 の文面は「再利用または再検証する条件」なので、再検証条件を明確にすれば満たす。
  - 計算削減は、キャンセルとキャッシュなど安全性を損なわない手段で担う。
  - 2つのレビューが、この方針を各案の最強点として挙げた。
- **PR full gate とマージキューを残す（C）。** 「CI 時間を悪化させる」という指摘に対し、全 push で full を完走させず最新 PR head と統合ツリーに限定すると反論した。AI がテストや CI 設定を弱体化しうる前提では、統合結果の確認が必要である。完走回数の制御は概算にも反映された。
- **ダークカナリアを選択肢として残す（C）。** 「常に成立しない」という指摘に対し、前提事実8が定義する方式であると反論した。副作用を抑制できない処理には使わない条件を明記し、既定で最大100%複製する扱いはやめた。
- **概算の前提をモデルケースとして置く（B）。** 「前提がブリーフ外の仮定」という指摘に対し、c2 は前提を明記した概算を求めていると反論した。ただし、仮定値であることは本結論でも明示する。
- **Format のマージ時再実行を省略できる、という A の論点。** 全 push で検査済みであり、統合結果はマージキューのビルドと Lint 全体実行で担保するという反論は、論理としては通る。ただし C はマージキューで再実行する設計であり、この点は割れた論点として残した。

## 攻撃で崩れた主張

- **署名なし「証明書」で Lint/Format のリモート再実行を省略する（A初稿、致命的）。** 2人のレビュアーが独立に指摘した。偽造できると認めながら省略の根拠にするのは自己矛盾である。また「後続チェックが落ちたら偽造を疑う」は、フォーマット違反だけのコミットなど後続が落ちない典型例を観測できない。A は撤回し、リモート再実行に改めた。この形の再利用は採らない。
- **SCA を「依存定義変更時のみ」またはコード変更時スキップにして日次補完に寄せる（A初稿、B初稿）。** 前提事実6と矛盾する。この指摘は3つのレビューにまたがり、`reviewer_notes` でも統合時の注意点として挙げられた。両案とも毎 push の SCA に改めた。
- **A初稿の配置表が「コミット毎」の列を欠いていた。** 制約と c1 に反する。全 push の列を追加して改稿した。
- **dev を「直接更新・閾値なし」とする設計（B初稿）。** ロールバック条件がなく c4 に反する。最小 Blue Green とヘルスチェック条件に改稿した。
- **dev の統計的判定（C初稿）。** error率10%、p95 の3倍などの比率判定は、低トラフィックの dev で手動アクセス数回の単発エラーで誤ロールバックを起こす。スモーク/ヘルスチェック中心に改稿し、比率判定は最低件数到達後のみとした。
- **ダークカナリアの応答差分率が「閾値超」で値なし（A初稿）。** 1% という値を置いた。ただし副作用のない読み取り系という想定付きである。
- **実測のない環境の閾値導出（A初稿）。** 「旧版の過去7日の実測から導出」だけでは導入初期に詰まる。仮置き値を使わず、自動昇格を無効化して人間承認へフォールバックするよう変えた。
- **人間承認境界の表現の揺れ（B初稿）。** 要旨の「全展開時のみ」と責任分界の「25%超から」が食い違っていた。表現は統一されたが、境界の位置そのものは割れたまま（次節）。
- **ローカル結果を hash 一致時に使うが何が変わるか空（C初稿）。** ログ・対象候補・キャッシュ key 候補に用途を限定して改稿した。ただし「コミット前は SHA が未確定」という指摘は残る。本結論では SHA ではなくツリー hash 等で照合する形のみを採った。
- **アサーション数の減少を即 fail にする（A初稿）。** 正当なリファクタを誤検知する。A は警告＋ラベル許可に緩和した。この点は次節でも割れている。

## 見解が割れた点

無理に一本化しない。

1. **prod で人間が承認する位置。**
   - A: 通常リリースは実測のある環境なら完全自動。人間承認は、状態を伴う変更、実測のない環境、新サービスの初回100%拡大。
   - B: 25%の自動判定後、100%公開の直前に人間承認を固定する。
   - C: 初期は prod 開始時に人間承認し、メトリクスと最低リクエスト数が安定してから自動拡大範囲を広げる。
   - 判断に必要な情報は、サービスの障害影響度、メトリクス基盤の遅延、承認待ちの間のカナリア滞留を誰が監視するか。B は滞留の監視者が未定義だと指摘された。
2. **SCA の毎 push の実行形態。**
   - A: 毎 push で軽量スキャンを必ず実行（時間は未検証）。
   - B: 毎 push はキャッシュ済み DB の差分スキャン。最新 DB の全量は PR 時と日次。
   - C: SCA ジョブは毎 push で起動するが、実スキャンは依存定義変更時またはスナップショット鮮度 SLO 超過時のみ。スキップ理由を記録する。
   - 判断に必要な情報は、SCA 照合の実測所要時間、脆弱性 DB の取得頻度と外部レート制限、許容できる検知遅延。B の方式は最大で日次同期までの検知遅延を認めている。C の方式にはレート制限の前提への指摘があった。本結論は A と C の中間（毎 push でジョブ起動、鮮度 SLO で実スキャン要否を決定）を暫定とするが、確定ではない。
3. **テスト弱体化検出の強さ。**
   - A: アサーション数の減少は警告、「理由」ラベルがあれば許可。
   - B: アサーション数の純減は即 fail。人間の承認フラグがあれば通す。
   - C: テスト数やカバレッジの低下は fail または人間承認。
   - 誤検知による人間レビュー増と、見逃しによる品質低下のどちらを重く見るかの問題。誤検知率の実測が要る。
4. **CD の閾値の数値。** prod のエラー率は、A が旧版比 +0.5pt、B が絶対値 0.1% 以上、C が 1% 以上かつ旧版比 +0.5pt 超と割れた。レイテンシは +10〜20%。dev/stg の方式も違う（B は stg をダークカナリア、A は stg を Blue Green、C は条件付きダークカナリア）。いずれも仮置き値であり、旧版の実測で決めるしかない。
5. **マージキューでの再実行範囲。** A は Format を省略し、C は Lint/Format も再実行する。B はマージキューに触れていない。本結論は決定的で安価な Format/Lint の再実行を暫定とするが、省略しても main に入る内容は検査済みという A の論理は成立する。
6. **PR 時の full gate の要否。** C は必須とし、A は PR 時を増分に留めてマージキューで全体を取る。B は PR 時に全 UT。計算量の総量見積りは3案とも十分ではない（C は指摘を受けた）。

## この結論の限界

- **どの案も踏み込まなかった論点。** 2人のレビュアーが `reviewer_notes` で独立に指摘した。エージェントが短時間に連続 push する運用そのもの（タスク終了時にまとめて push する規約など）を抑える手段は、どの案にもない。リモート CI の発火回数とキュー待ちは、この手段なしには根本解決しにくい。
- **閾値・削減幅の校正手順。** すべて仮定値である。導入後の実測で調整する手順（校正）は3案とも弱く、実測が貯まるまでの運用ルールは「自動判定を止めて人間承認」以外に書かれていない。
- 次の論点もレビューで指摘されたが、改稿後の案が十分に扱ったとは確認できない。
  - 日次 SCA で見つかった脆弱性を、進行中 PR の必須ステータスに反映する方法
  - テスト弱体化検査ジョブ自体の抜けを突く回避への継続的な棚卸し条件
  - ダークカナリアで副作用を遮断できないリクエストが混ざったときの自動停止条件
  - 承認待ちの間のカナリア滞留を誰が監視するか
- 前提の確認が残っている。
  - アプリの構成（モノリスかマイクロサービスか、ステートレスかステートフルか）、エージェントの push 頻度、ローカル実行環境のスペックは不明。
  - メトリクス収集の遅延は不明。
  - ローカル Hook をエージェントにどこまで強制できるかは基盤依存。
  - ダークカナリアで副作用なしにトラフィックを複製できるかは未確認。
  - ミューテーション抜き打ちの効果とコストは未検証。
  - coverage やアサーション数の検出は言語・フレームワーク依存で、誤検知と見逃しがありうる。
- Gemini と OpenAI は実行環境のファイル・コマンド・Web に触れていない。両者の案と批評は brief.md の記述のみに基づく。この結論も、brief.md の前提事実と3案の記述の範囲を出ていない。
- **`synthesis-check.json` の warnings。** 本作業には渡されておらず、確認できていない。呼び出し元が `synthesis-check.mjs` で寄与比率を算出した結果に warnings があれば、全件をここへ追記すること。
- 外部の事実確認、ツール選定、インフラの具体設計、コスト金額の試算は対象外（brief.md の「検討の対象外」による）。

## 付録: 経緯

**3案の1行要約（改稿後）**

- A: 二層構成でローカル結果は一切再利用せず、全 push で必須チェック。環境別プロファイルを持ち、実測のない環境は人間承認に落とす。
- B: ローカルを信頼境界の外に置き、Stage 0 のメタ整合性検査と CODEOWNERS で防壁を作る。CD は dev/stg/prod で方式を分け、100%公開前に人間承認を固定する。
- C: 全 push の必須 CI に加え、PR full gate とマージキューを置く。ローカル結果はヒント用途に限る。CD は最低リクエスト数と人間承認で低トラフィックに対応する。
