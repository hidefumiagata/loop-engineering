## 案の要旨

本案は、レガシーVM・Excel設計書・Zabbix監視が混在する中規模〜大規模システム群（50〜200システムを想定）に対し、「実環境ディスカバリによる現況逆引き」と「インシデント履歴主導の局所Markdown化」を中核としたSRE×AI運用横展開戦略である。システム全面の近代化や全ドキュメントの再整備を排し、頻発アラート・過去障害の上位20%に紐づく運用情報・監視ログのみを最小粒度のAI可読形式へ変換する。これにより、1システムあたりの初期導入工数を圧縮し、段階的SREプラットフォームへ順次接続して運用自動化を果たす。

---

## 設計

### 1. 対象規模と構造化要件（AI可読Markdownの定義）

- **想定対象規模**: 1事業者またはSIerが保守・運用を担う既存エンタープライズシステム群のうち、50〜200システム（VM総数500〜3000台規模を想定）。
- **AI可読Markdownの構造化要件**:
  - ドキュメント単位ではなく「運用コンテキスト単位（Runbook / Architecture Node / Metric Semantics）」で1ファイル1責務に分割。
  - フロントマター（YAML形式）に `system_id`, `component_name`, `alert_trigger_ids`, `dependency_nodes` などの固定スキーマを必須付与。
  - 本文はセクション構造（`## 概要`, `## 前提条件`, `## 調査手順（CLI/ログ）`, `## 復旧手順`, `## エスカレーション先`）を厳格に固定し、自然言語の装飾や図形依存の表現を排除。

```
[レガシー資産]
├─ Excel設計書/手順書 ─── (差分・頻出部のみ) ─┐
├─ Zabbix監視/VM実態  ─── (構成逆生成/エージェント) ─┼─> [変換パイプライン]
└─ 障害履歴/チケット  ─── (頻出アラート特定) ─┘        │
                                                        ▼
                                              [標準Markdownリポジトリ]
                                              (Runbook / Node / Metrics)
                                                        │
                                                        ▼
                                              [SRE×AI分析エンジン]
                                              (一次切り分け・原因推定)
```

### 2. 成熟度別の段階定義と適用施策（基準c1）

対象システムを以下の4段階に分類し、適用施策を定義する。

| 成熟度レベル | システム状態の定義 | 適用するSRE施策 | AI活用範囲 | 次段階への移行条件 |
| :--- | :--- | :--- | :--- | :--- |
| **Level 0 (Dark)** | ドキュメント更新停止、Zabbix死活監視のみ、手動復旧 | 基本SLI（外形監視）の定義、インシデント起票ルールの標準化 | 過去チケットからの頻出障害パターンの分類・要約 | 外形SLI計測開始、インシデント台帳の構造化記録 |
| **Level 1 (Observed)** | VM稼働、Zabbixでリソース収集済、Excel手順書あり | Zabbixアラート整理、SLO設定（暫定値）、運用RunbookのMarkdown化 | アラート受信時の関連Runbook引き当て、手順提示 | アラートノイズ半減、上位障害のRunbook Markdown化完了 |
| **Level 2 (Structured)** | 構成情報が実機から自動収集済、主要RunbookがMarkdown化 | ポストモーテム文化の導入、エラーバジェット運用、ログ集約 | ログ・メトリクスとRunbookを突き合わせた一次切り分け・原因推定 | 一次切り分けのAI正答率が検証基準（KPI）を満たすこと |
| **Level 3 (Autonomous SRE)** | OpenTelemetry等のモダン観測性、CI/CD・IaC一部適用 | トイル削減自動化、変更管理連携、カオスエンジニアリング検証 | 調査コマンド自動実行結果の解釈、復旧手順の提案・半自動実行 | 恒常的なトイル削減率の維持、障害復旧時間（MTTR）の短縮 |

| **Phase 0: 準備・標準化** | 1〜2か月目 | 標準Markdownスキーマ定義書、変換ツールプロトタイプ、SRE運用ガイドライン | 変換スクリプト動作検証完了、パイロット選定基準の合意 |

### 5. 具体プロセス（基準c4）

```
[1. アセスメント] ──> [2. AI可読化] ──> [3. 観測性整備] ──> [4. AI運用導入]
```

1. **アセスメント（適格性判定と優先度づけ）**
   - **入力**: 過去1年間のインシデント台帳、Zabbixアラート一覧、システム一覧表。
   - **手順**: (a) アラート頻度・障害対応工数のパレート分析、(b) ログ出力状況と設計書の存在確認、(c) 導入難易度×効果マトリクスによる分類。
   - **出力**: システム成熟度スコアシート、導入優先度マップ、SLO設計ドラフト。
   - **担当**: Lead SRE。
2. **情報のAI可読化（Runbook・構成情報の整備）**
   - **入力**: 対象システムのExcel手順書、VM接続情報（読み取り権限）。
   - **手順**: (a) 実機ディスカバリによる構成Markdown生成、(b) 頻出障害（上位20%）に対応する手順書を切り出し、標準スキーマMarkdownへ変換・検証。
   - **出力**: 構造化Runbook群、システム構成インベントリMarkdown。
   - **担当**: SRE Engineer、ドキュメント自動化スクリプト。
3. **観測性整備（データパイプライン構築）**
   - **入力**: Zabbix接続情報、ログ転送設定（Syslog等）。
   - **手順**: (a) Zabbix Webhook/API経由でのアラートイベント連携設定、(b) ログ集約基盤へのOS/ミドルウェアログ転送、(c) アラートとRunbookメタデータのマッピング。
   - **出力**: ログ・アラート集約基盤、イベント中継パイプライン。
   - **担当**: Cloud/Infrastructure Engineer。
4. **AI運用の段階的導入（一次切り分けと評価）**
   - **入力**: アラート発火イベント、収集された関連ログ、構造化Runbook。
   - **手順**: (a) AIによるアラート・ログ解析と一次切り分け仮説生成、(b) 運用担当者への通知とサジェスト提示、(c) 担当者のフィードバック収集。
   - **出力**: AI切り分けレポート（チケット連携）、精度改善ログ。
   - **担当**: SRE運用チーム、AIシステム管理者。

### 6. 横展開の仕組みとコスト低減（基準c5）

- **仕組み**:
  1. **標準Markdownスキーマ集**: Runbook、ノード構成、エラー定義のフォーマットを固定。
  2. **実機ディスカバリ自動化CLI**: SSH/Ansible等でOS・ミドルウェア構成を吸い上げ、Markdownを自動出力。
  3. **Excel構造化抽出パイプライン**: 表形式ブロックの半自動切り出しツール。
- **コスト低減の見立て（新規開発型アプローチとの比較）**:
  - *比較対象*: 「システム全体の設計書を網羅的にMarkdown再作成し、ソースコード全計装を実施する新規開発型アプローチ」。
  - *対象工程*:
    - **設計書解析・整備工程**: 全網羅を排し、頻出障害の上位20%のRunbookのみを対象化することにより、文書化工数を約70%削減（要検証）。
    - **監視・計装設計工程**: コード改修を伴うAPM導入をスキップし、既存Zabbix＋OSログ転送の標準テンプレートを適用することで、導入設計工数を約60%削減（要検証）。
    - **総合導入コスト**: 1システムあたりの初期導入工数を従来型 full-scratch アプローチ比で約50〜60%削減（要検証）。

### 7. レガシー資産のAI可読化工数と自動化の限界（基準c8）

- **文書種別ごとの変換工数目安（1文書あたりの概算）**:

| 文書種別 | 前提状態 | 推奨変換アプローチ | 工数目安（人日/件） |
| :--- | :--- | :--- | :--- |
| **運用手順書（Excel表形式）** | 行列ベースの手順リスト | スクリプト抽出＋LLMによるMarkdownスキーマ整形 | 0.2〜0.5人日（要検証） |
| **運用手順書（Excel方眼紙・図入り）** | スクリーンショット、吹き出し、結合セル多用 | マルチモーダルLLMによる一次変換＋人間によるレビュー | 1.0〜2.0人日（要検証） |
| **詳細設計書（パラメータシート）** | OS/DB等の設定値一覧 | 抽出不要（実機から直接コンフィグをディスカバリ） | 0.1人日（検証のみ）（要検証） |
| **モノリスソースコード** | COBOL、レガシーJava等 | 障害箇所のスタックトレースに該当する関数周辺のみ局所プロファイリング | 0.5〜1.5人日/機能（要検証） |

- **自動化が困難な領域（限界範囲）**:
  - Excel図形オブジェクト（オートシェイプ、矢印）で組まれた業務フロー・論理アーキテクチャの因果関係把握。
  - 手順書外に存在する「現場の暗黙知」（例:「このアラートは毎朝9時に出るが無視してよい」「復旧しない場合は担当者Aに電話」等の口頭伝承）。
  - ソースコード内の非標準ライブラリや独自フレームワークが吐き出す固有エラーコードの意味解釈。

### 8. リスクと緩和策（基準c6）

| リスク分類 | 具体的内容 | 緩和策 |
| :--- | :--- | :--- |
| **データ主権・セキュリティ** | 顧客ポリシーにより、顧客ログや設計情報を外部SaaS LLMへ送信できない。 | ローカル/プライベートクラウド環境でホスト可能な閉域型LLMの採用、および個人情報・IPマスキングプロキシの常時介在。 |
| **AIの誤判断（ハルシネーション）** | 不正確な切り分け結果を信じたオペレータが誤った対応を行い、障害を拡大させる。 | AIの出力を「推論根拠となったログ行」「参照Runbookの該当章」のリンク付き提示に限定。コマンド実行は人間の手動承認を必須化。 |
| **資産情報の乖離** | 変換元の設計書が古く、実環境と不整合を起こしてAIが誤推論する。 | 実機ディスカバリによる「現況データ」を優先度最高（Single Source of Truth）として扱い、古い文書情報は補助メタデータに降格。 |
| **SRE運用体制の不足** | 顧客側のSRE理解が乏しく、SLO設定やポストモーテムの運用が定着しない。 | 当初はベンダー側が「SRE as a Service」として運用代行・ファシリテーションを巻き取り、定例会を通じて顧客組織へ徐々に移管。 |

### 9. 事業面・提供モデル（基準c7）

- **提供形態**:
  - **初期アセスメント＆セットアップ（固定額）**: 優先システムの特定、監視コレクタ導入、上位RunbookのMarkdown化。
  - **月額サブスクリプション（SRE運用支援＋AIプラットフォーム利用料）**: 監視中継エージェント・AI切り分け基盤の提供と、月次のSLOレビュー・ポストモーテム支援、Runbook継続改修を含むマネージド型提供。
- **投資とコストの考え方**:
  - 共通テンプレートと変換パイプラインへ初期投資を集中させ、システム追加時の限界費用を逓減させる。
- **顧客への価値の示し方**:
  - 「システムの全面刷新（莫大な投資）」を要求せず、「レガシーの延命・安定稼働」と「属人化解消・障害復旧時間（MTTR）短縮」を短期KPIとして提示する。

### 10. AI分析精度の評価KPI（基準c9）

PoCおよび実運用における評価指標を以下のように定める。

| KPI項目 | 定義 | 測定方法 | 合格基準（目標値） |
| :--- | :--- | :--- | :--- |
| **一次切り分け正答率 (Top-3 Accuracy)** | AIが提示した上位3つの原因仮説の中に、真の原因が含まれていた割合。 | 事後ポストモーテム時に、一次対応ログとAI推論結果を人間（Lead SRE）が照合。 | パイロット時: ≥70%、実運用時: ≥85%（要検証） |
| **Runbook特定率** | アラート発火時に、対応すべき適切なMarkdown Runbookを正しく引き当てられた割合。 | アラート起票後のインシデントチケットに自動リンクされたRunbookの妥当性を評価。 | 実運用時: ≥90%（要検証） |
| **誤検知・ハルシネーション率** | AIが「存在しないログ」や「矛盾した手順」を生成・引用したインシデントの割合。 | 切り分けサジェストに対する現場オペレータのBadフィードバック（フラグ付け）集計。 | 実運用時: ≤5%（要検証） |
| **初動時間削減率 (MTTA改善)** | アラート検知から一次切り分け（原因特定と復旧方針決定）完了までの時間の削減幅。 | チケットシステムのタイムスタンプ（検知〜対応方針決定）を導入前後で比較。 | 導入前比 30〜50%短縮（要検証） |

## トレードオフ

1. **ドキュメント網羅性の放棄（パレート則の採用）**:
   - 既存の全Excel設計書・全ソースコードをAI可読化することは最初から放棄し、過去障害・頻出アラート上位20%に直結する資産のみを構造化する。結果として、数年に1回しか起きない未知のレア障害に対してはAIは全く役に立たず、従来型の手動調査に頼ることになる。
2. **完全自動復旧（Autonomous Remediation）の除外**:
   - 誤判断時の本番障害リスクおよび企業の変更管理統制を最優先し、AIによる自動コマンド実行・自動パッチ適用はスコープ外とした。常に人間の承認（Human-in-the-Loop）を挟むため、MTTRの極小化（秒単位での復旧）は達成できず、人間の介在時間がボトルネックとして残る。
3. **高カーディナリティ分析・分散トレーシングの妥協**:
   - モノリスコードの改修を行わないため、DatadogやOpenTelemetryの真価である「コードレベルの分散トレース」は得られない。OSログや既存Zabbixメトリクスの粗い相関分析にとどまるため、AP層内部の深い競合問題等の原因究明精度は限定的になる。

## 想定される失敗モード

1. **実機ディスカバリ情報の陳腐化による推論破綻**:
   - *破壊プロセス*: 静的なRunbookや構成Markdownを初期に生成した後、顧客現場が手動でVM設定やミドルウェア設定を無断変更（構成ドリフト）。AIが古い構成Markdownを前提に誤った復旧コマンド案を提示し、現場オペレータがそれを鵜呑みにして実行、サービス停止に至る。
2. **アラートストームによるコンテキストウィンドウのパンクと誤判定**:
   - *破壊プロセス*: 大規模障害時にZabbixから大量の二次アラートが短時間に同時発火。AIのプロンプト/コンテキストに大量のログが一度に流し込まれ、根本原因（Root Cause）を見失い、表層的な症状（CPU枯渇など）のみを原因と誤認して無関係なRunbookを提示する。
3. **現場エンジニアのサボタージュと形骸化（フィードバックループの途絶）**:
   - *破壊プロセス*: 運用現場がAIの提示するサジェストを「確認する手間が増えた」と捉え、フィードバック（正答/誤答のフラグ付け）を行わなくなる。精度向上のためのデータが集まらず、RunbookのMarkdownも更新されず、最終的に誰もAI出力を参照しなくなる。

## 前提と未確認事項

- **前提（本案が置いた仮定）**:
  - 対象システム群は最低限SSHやWinRM、エージェント経由での構成情報吸い上げ（読み取り専用権限）が技術的・契約的に許可されること。
  - Zabbix環境から外部（集約基盤やWebhook中継サーバ）へのイベント通知・APIポーリングが可能であること。
  - 顧客社内規程において、マスキング処理済みのログデータまたは閉域網内LLMであればAIによるデータ処理が許可されること。
- **未確認事項（検証が必要な事項）**:
  - Excel方眼紙形式の設計書・手順書に対するマルチモーダルLLMの抽出精度（セル結合や手書き風矢印の認識精度）が実用に耐えうるか（要検証）。
  - 「頻出アラート上位20%」の対応で、現場の障害対応稼働のどれほどの割合を真にカバーできるかの実測値（要検証）。
  - パイロット環境で設定した「正答率70%」「工数50〜60%削減」等の定量的目標が、レガシーOS（古いLinuxカーネルやWindows Server）において達成可能かどうか（要検証）。
