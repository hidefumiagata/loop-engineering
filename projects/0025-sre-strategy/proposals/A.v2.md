## 案の要旨

全システムに同じ水準を求めず、「AI可読化の深さ」を3段階（L1 観測の入口 / L2 構成と手順の復元 / L3 コード理解を含む一次切り分け）に分け、システムごとに到達段階を決めて進める。構成の把握は**実態からの逆生成を主、既存Excelの変換を従**とするが、**逆生成の権限が取れない場合の迂回経路（P2-b）を最初から設計に含める**。横展開は「標準アセスメント＋共通テンプレート＋変換パイプライン」で1件あたりの人手を減らし、「全システムでL3」は目指さない。

## 設計

### 1. 想定規模と段階定義（前提）

対象は 50〜200 システム（要検証・仮定）。18か月で到達を約束するのは**最大でも30〜40システム**とし、残りは第3波以降（本案のスコープ外）として明示する。AIが分析可能な形式とは、次の最小セットを指す。

| 成果物 | 形式 | 最小粒度 |
| --- | --- | --- |
| システム概要 | `system.md` | 目的・構成要素・依存先・担当・業務時間帯・**業務影響度（停止時に止まる業務と時間帯）** |
| 構成情報 | `infra/*.md` + 可能なら YAML | ホスト/プロセス/ポート/接続先。取得元（実態/設計書/ヒアリング）と取得日を必ず付す |
| ランブック | `runbooks/*.md` | 症状→確認コマンド→判断→エスカレーション |
| 監視定義 | `monitoring/*.md` | アラート名・閾値・意味・過去の対応・**形骸化フラグ（直近N日で対応実績なし）** |
| 障害履歴 | `incidents/*.md` | 症状・原因・対処（直近1〜2年分） |
| コード索引 | `code-map.md` | モジュール単位の責務・入出力・主要バッチ（L3のみ） |

| 段階 | 状態 | 得られる運用 |
| --- | --- | --- |
| L0 | 未着手 | なし（人手運用） |
| L1 | ログ/Zabbixアラートを集約、SLO草案、アラート整理 | AIによるアラート要約・重複排除・過去事例検索 |
| L2 | L1 + 構成情報（実態逆生成またはP2-b）+ ランブックのMarkdown化 | 一次切り分け支援（「どのコンポーネントを疑うか」の提示） |
| L3 | L2 + コード索引 + 重要設計書の構造化 + 既存ログ・Zabbix履歴からの時系列相関（**新規トレース計装は前提にしない**。計装できる場合のみ追加） | 原因分析の仮説提示、変更影響の推定 |

L3昇格条件: ①L2のシャドウ運用でKPI閾値を満たす ②コード閲覧が契約上許可されている ③障害履歴に当該システム起因が一定数ある。満たさなければL2で止める。

### 2. 具体プロセス

**P1 アセスメント（1システム 2〜3日、2名）**
- 入力: 契約・データ送信可否の確認、既存資料、担当者ヒアリング（60分×2）
- 手順: 標準スコアカード（データ送信制約 / 構成情報の有無 / 監視のエクスポート可否 / 障害頻度 / ビジネス影響 / 資料の質 / **本番への読み取り権限の取得見込み**）で採点
- 出力: 目標段階と見積もり。判定は担当者の裁量に任せず、**スコアカードの閾値と、データ送信・権限の判定は上長（導入責任者）承認**を要する
- 注記: 2〜3日でできるのは「段階判定」までで、暗黙知の網羅ではない。暗黙知はP2・P5の過程で障害ごとに追加ヒアリングして補う

**P2-a 構成ディスカバリ（権限が取れる場合。L2の主経路）**
- 入力: 読み取り専用アカウント（顧客承認済）
- 手順: エージェントレス収集スクリプトを実行し、LLMで要約・Markdown化。設計書との差分を「乖離リスト」として提示
- 出力: `infra/*.md`、乖離リスト。担当: 導入SRE。顧客側は乖離リストのレビューのみ（**レビュー滞留は第2波以降の制約として、顧客あたり同時レビュー件数の上限を置く**）
- 限界: 得られるのはIP・ポート・プロセス等の物理関係であり、「なぜ必要か」「どの業務に紐づくか」は取れない。業務影響度は`system.md`にヒアリングで別途記入する

**P2-b 権限が取れない場合の迂回経路**
- 顧客自身が実行して結果だけを渡す方式（顧客が収集スクリプトを自環境で実行、出力ファイルのみ受領）、または既存の構成管理DB・Zabbixのホスト/アイテム定義・既存Excelの重要シートからの再構成。
- 精度は低くなるため、この経路で作る`infra/*.md`は取得元を「設計書/ヒアリング」と明記し、AIが根拠として使う際の信頼度を下げる。どちらも不可なら**L1止め**。

**P3 観測性の並走整備**
- 担当: 導入SRE。入力: Zabbix API利用可否・ログ出力先。手順: API/エクスポートでメトリクスとアラート履歴を取得し、ログは顧客の変更管理が許す範囲で並走送信（Zabbix停止は目標にしない。変更管理が通らなければ**エクスポートの定期取得のみ**）
- 出力: アラート定義書（形骸化フラグ付き。形骸化アラートはAI入力から除外またはノイズ扱い）、SLO草案（可用性・レイテンシの2〜3指標）。完了判定: アラート履歴が30日分以上取得できていること

**P4 資料の変換パイプライン**
- 担当: 変換は内製ツール、レビューは導入SRE（図形シートは顧客担当者併用）。入力: Excel設計書一式
- 手順: ①シート単位でPDF/画像化 ②マルチモーダルLLMで表・図を構造化 ③人が差分レビュー ④Markdownへ。レビュー合格基準は「重要シート（構成図・IF定義・運用手順）は全数、他はサンプル10%で誤り率が閾値内」。閾値超過なら当該ブックを差し戻し
- 工数目安（要検証）: 方眼紙形式Excel 1シートあたり 変換10分＋レビュー20〜40分。罫線表中心は半分程度。**図形主体のシート比率が5割を超えるブックは自動変換の対象外とし、手作業再作成または対象外とする**（この閾値は仮置き。M1で実測）
- 1システムあたりの総量は、シート数分布（要検証）× 上記を重要シートに限定して見積もる
- ソースコード: 全量ではなくバッチ・IF境界・障害履歴に出たモジュールから索引化（L3のみ）

**P5 AI運用の段階導入**
1. シャドウ運用: 実障害でAIが出した一次切り分けを人の判断と並べて記録（**期間は固定せず、障害10件に達するまで**。件数が集まらないシステムは過去障害の再現評価で代替）
2. 助言運用: オペレータへ提示、人が採否を記録
3. 限定自動化: 読み取り専用の確認コマンド実行までを自動化。**変更系の自動修復はスコープ外**
- ラベル品質: 正解ラベルは担当SREと2人目で一定割合を二重判定し、不一致率をKPI報告に併記する
- 情報の鮮度: 構成情報は四半期ごとの再ディスカバリ（P2-a）または変更チケット連動で差分更新する。鮮度が切れた`infra/*.md`は根拠として使わない

### 3. マイルストン（組織全体、18か月の目安）

| 期間 | 成果物 | 完了判定 |
| --- | --- | --- |
| M0 0〜2か月 | 標準アセスメント、テンプレート、変換・ディスカバリの内製ツール試作、パイロット3システム選定 | 試作ツールが1システムで一周し、乖離リストが顧客レビューを通る |
| M1 3〜6か月 | パイロット3件をL2へ。シャドウ運用開始 | 障害または再現評価10件以上でAI一次切り分けを人手正解と照合、KPI測定可。工数・権限取得率・図形シート比率を実測 |
| M2 7〜12か月 | 第1波 10〜20システムをL1〜L2 | 1件あたり導入工数がパイロット比で計測でき、目標内 |
| M3 13〜18か月 | 第2波 10〜20システム（累計30〜40）。L3は条件を満たす数システムに限定 | KPI基準を満たすシステムのみ助言運用へ昇格。残りシステムの第3波計画とM1実測に基づく工数モデルの更新版を提出 |

### 4. リスク表（c6）

| リスク | 検知条件 | 緩和策 | 責任 |
| --- | --- | --- | --- |
| データ送信制約 | P1スコアカードで判定 | 閉域内LLM（追加コストと精度低下は事業判断として顧客に提示）またはL1止め | 導入責任者 |
| 本番権限が取れない | P1で見込み評価、P2-aが拒否された時点 | P2-bへ切替、不可ならL1止め。計画上、権限取得率は仮に5割と置き、M1で実測 | 導入SRE |
| AIの誤判断 | KPI（誤誘導率） | シャドウ→助言止まり、閾値未達は昇格しない | 運用責任者 |
| 情報整備の精度・陳腐化 | 乖離リストの再発、取得日の経過 | 四半期再ディスカバリ、鮮度切れ情報の不使用 | 導入SRE |
| 体制不足 | 第1波の1件あたり工数が計画超過 | 段階を絞る、第2波の件数を減らす | 事業責任者 |
| 顧客レビュー滞留 | 乖離リストの未レビュー日数 | 同時レビュー件数の上限 | 導入SRE |

### 5. 横展開の仕組みとコスト見立て（要検証）

比較対象は「各システムを新規導入プロジェクト並みに個別手作業で整備した場合」。減らせる工程は構成調査（P2-aのスクリプト化）、資料のMarkdown化（P4のパイプライン化）、ランブック雛形作成（テンプレート化）。減らせない工程は顧客ヒアリング、乖離のレビュー、障害履歴の整理。仮説としてL2到達までの工数を個別手作業比で 40〜60%減とするが、**P2-aが使えないシステム（P2-b）では20〜30%減程度に留まる**と見る（いずれも要検証、パイロットで実測して置き換える）。

### 6. 提供モデル（c7）

L1/L2/L3ごとに「定額オンボーディング＋運用サブスク」の2層とする。価格は原価（段階別の工数、閉域LLM利用時の追加費用）から逆算し、顧客には「一次切り分け所要時間の短縮」「重複アラート削減率」をKPI報告として示す。具体価格は対象外（ブリーフ上、個別契約・価格の確定は検討対象外）。

### 7. KPI（c9）

- 一次切り分け正答率: 人が確定した原因コンポーネントをAIの上位3候補が含む割合。昇格閾値は仮置きで60%以上（M1で見直し）
- 危険な誤誘導率: 誤った確信的断定の割合（5%未満を仮置き）
- 切り分け所要時間の短縮、アラートの重複/不要率の低減
- 測定: 事後ラベルの障害台帳と照合。二重判定の不一致率を併記

## 評価基準への適合

- c1: L0〜L3の段階定義、L3昇格条件、各段階の施策（P1〜P5）を示した。
- c2: M0〜M3の期間・成果物・完了判定。第2波の件数と、18か月で扱わない残りの扱いを明記した。
- c3: 可能: L1〜L2の一次切り分け支援、構成の逆生成（権限があれば）、アラート整理。不可能/非現実的と理由・代替: ①全システムでの全量コード理解（コード量とドメイン知識の制約→障害履歴起点の索引） ②変更系の自動修復（誤判断時の影響が大きく検証できない→読み取り確認まで） ③設計書Excelの無人変換（図形主体は精度が低い→重要シート全数レビュー、閾値超は手作業） ④暗黙知のヒアリング抜きの復元（→障害ごとの追加ヒアリング） ⑤権限なしの実態逆生成（→P2-b、不可ならL1止め）。
- c4: P1〜P5に入力・手順・出力・担当、P3〜P4には完了判定・合格基準を追記した。
- c5: 比較対象と減らせる工程、P2-a/P2-bで分けた低減幅を示した（要検証）。
- c6: リスク表を独立節として設けた。
- c7: 段階別2層モデルと価値の示し方を記述（価格確定は対象外）。
- c8: 文書種別ごとの工数目安と、自動化不可の範囲（図形主体シート、暗黙知、コード）、図形比率の閾値を示した。
- c9: 正答率・誤誘導率・所要時間・測定方法とラベル品質管理を示した。

## トレードオフ

- 全システムの均質な高水準化を捨てたため、L1止まりの顧客には「一次切り分けまで」が約束できない。
- 18か月で扱う件数を30〜40に絞ったため、50〜200システム全体の完了時期はこの案では約束しない。
- 設計書Excelの全面変換を捨てたため、設計意図（なぜそうなっているか）は復元できず、ヒアリング依存が残る。
- Zabbix併用を許すため、新規計装を伴う高度な分析（分散トレース等）は、計装が許される一部に限られる。
- 価格・提供形態は原価の考え方までで、具体設計はしない。

## 想定される失敗モード

1. **権限が取れるシステムが少ない**: P2-aが拒否され多数がP2-bまたはL1止めになる。M1で権限取得率を実測し、低ければ第1波の対象を権限取得見込みの高いシステムに絞る。
2. **変換品質が低くレビュー工数が下がらない**: 図形主体のExcelが多く、コスト低減が実現しない。M1の実測で早期に判明させ、計画を見直す。
3. **AIの切り分けが運用で信用されない**: 誤誘導が数回出ると現場が使わなくなる。昇格ゲートで管理するが、閾値自体が仮置き。
4. **パイロット3件が代表的でない**: 想定外の構成（メインフレーム連携、パッケージ製品）が多数を占める。

## 前提と未確認事項

- 対象規模（50〜200）、18か月、30〜40システム、工数目安、40〜60%の低減、正答率60%などの数値はすべて仮定であり、パイロットでの実測が必要。
- 組織の人員規模と既存のツール資産が不明。M0の内製が可能かは未確認。要員計画は本案では置いていない。
- 顧客が外部LLMへのデータ送信を許可する割合、本番権限の取得率は不明。閉域内LLMを使う場合の精度・コストは未確認。
- Zabbixの版・保有データ期間・API利用可否は顧客ごとに異なり、確認していない。
- 価格・提供形態の市場受容性は検証していない。

## 改稿で変えた点

1. **権限が取れない場合の経路P2-bを追加**し、権限拒否で全体が止まる構造を解消。コスト低減幅もP2-a/P2-bで分けた。
2. **第2波の件数と18か月の到達上限（30〜40）を明記**し、残りの扱いをM3の成果物に入れた。
3. **リスク表を独立節に**し、検知条件・責任者を付けた。P3〜P5に担当・完了判定・合格基準を足した。
4. 「トレース相当」を削除し、L3を既存ログ・Zabbix履歴の相関と定義。昇格条件も追加。
5. シャドウ運用を期間固定から件数基準へ、ラベル二重判定、構成情報の鮮度管理、形骸化アラートの除外、業務影響度の記入を追加。

## 反論

- 「アセスメント2〜3日では判定しきれない」は部分的にのみ受け入れた。2〜3日は段階判定に限ると明記し、暗黙知の網羅は期待しない設計にした（工数自体は変えていない。網羅を目的にしていないため）。
- 「事業面がほぼ放棄されている」は部分的に受け入れた。原価と価値の示し方は書いたが、具体価格はブリーフが検討対象外としているため踏み込まない。
- 「ログ並走送信が変更管理で許容されない」は、変更管理が通らない場合の縮退（定期エクスポートのみ）をP3に入れて対応した。
