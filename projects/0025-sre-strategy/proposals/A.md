## 案の要旨

全システムに同じ水準を求めず、「AI可読化の深さ」を3段階（L1 観測の入口 / L2 構成と手順の復元 / L3 コード理解を含む一次切り分け）に分け、システムごとに到達段階を決めて進める。文書の手動整備ではなく、**実態からの逆生成（構成ディスカバリ・ログ/メトリクスの並走収集）を主、既存Excelの変換を従**とし、横展開は「標準アセスメント＋共通テンプレート＋変換パイプライン」で1件あたりの人手を減らす。「全システムでL3」は目指さず、L3は価値と制約が揃う少数に絞る。

## 設計

### 1. 想定規模と段階定義（前提）

対象は 50〜200 システム（要検証・仮定）。AIが分析可能な形式とは、次の最小セットを指す。

| 成果物 | 形式 | 最小粒度 |
| --- | --- | --- |
| システム概要 | `system.md` | 目的・構成要素・依存先・担当・業務時間帯 |
| 構成情報 | `infra/*.md` + 可能なら YAML | ホスト/プロセス/ポート/接続先、実態から生成 |
| ランブック | `runbooks/*.md` | 症状→確認コマンド→判断→エスカレーション |
| 監視定義 | `monitoring/*.md` | アラート名・閾値・意味・過去の対応 |
| 障害履歴 | `incidents/*.md` | 症状・原因・対処（直近1〜2年分） |
| コード索引 | `code-map.md` | モジュール単位の責務・入出力・主要バッチ（L3のみ） |

| 段階 | 状態 | 得られる運用 |
| --- | --- | --- |
| L0 | 未着手 | なし（人手運用） |
| L1 | ログ/Zabbixアラートを集約、SLO草案、アラート整理 | AIによるアラート要約・重複排除・過去事例検索 |
| L2 | L1 + 構成逆生成 + ランブックのMarkdown化 | 一次切り分け支援（「どのコンポーネントを疑うか」の提示） |
| L3 | L2 + コード索引 + 設計書の構造化 + トレース相当の情報 | 原因分析の仮説提示、変更影響の推定 |

### 2. 具体プロセス

**P1 アセスメント（1システム 2〜3日、2名）**
- 入力: 契約・データ送信可否の確認、既存資料、担当者ヒアリング（60分×2）
- 手順: 標準スコアカード（データ送信制約 / 構成情報の有無 / 監視のエクスポート可否 / 障害頻度 / ビジネス影響 / 資料の質）で採点
- 出力: 目標段階（L1/L2/L3）と見積もり。送信制約が強い場合は閉域内LLM前提か「L1のみ」と判定
- 担当: アセスメント担当SRE

**P2 構成ディスカバリ（L2の中核）**
- 入力: 読み取り専用アカウント（顧客承認済）
- 手順: エージェントレス収集スクリプト（プロセス、ネットワーク接続、cron、systemd、パッケージ、設定ファイル）を実行し、LLMで要約・Markdown化。設計書との差分を「乖離リスト」として人に提示
- 出力: `infra/*.md`、乖離リスト
- 担当: 導入SRE。顧客側は乖離リストのレビューのみ

**P3 観測性の並走整備**
- Zabbix は置き換えず、API/エクスポートでメトリクスとアラート履歴を取得。OpenTelemetry Collector 等でログを新基盤へ並走送信（Zabbix停止は目標にしない）。トレースは**L3かつ改修許容のシステムのみ**
- 出力: アラート定義書、SLO草案（可用性・レイテンシの2〜3指標）

**P4 資料の変換パイプライン**
- Excel設計書: ①シート単位でPDF/画像化 ②マルチモーダルLLMで表・図を構造化 ③人が差分レビュー ④Markdownへ。レビューは「重要シート（構成図・IF定義・運用手順）のみ全数、他はサンプル」
- 工数目安（要検証）: 方眼紙形式Excel 1シートあたり 変換10分＋レビュー20〜40分。罫線表中心の表形式は半分程度。構成図のみの図形は構造化の精度が低く、全数人手確認
- ソースコード: 全量ではなくバッチ・IF境界・障害履歴に出たモジュールから索引化（地図優先、全理解は目指さない）

**P5 AI運用の段階導入**
1. シャドウ運用: 実障害でAIが出した一次切り分けを人の判断と並べて記録（4〜8週）
2. 助言運用: オペレータへ提示、人が採否を記録
3. 限定自動化: 読み取り専用の確認コマンド実行までを自動化。**変更系の自動修復はスコープ外**

### 3. マイルストン（組織全体、18か月の目安）

| 期間 | 成果物 | 完了判定 |
| --- | --- | --- |
| M0 0〜2か月 | 標準アセスメント、テンプレート、変換・ディスカバリの内製ツール試作、パイロット3システム選定 | 試作ツールが1システムで一周し、乖離リストが顧客レビューを通る |
| M1 3〜6か月 | パイロット3件をL2へ。シャドウ運用開始 | 直近の障害10件以上でAI一次切り分けを人手正解と照合、KPI測定可 |
| M2 7〜12か月 | 横展開第1波（10〜20システム）をL1〜L2。アセスメントの標準化 | 1件あたり導入工数がパイロット比で計測でき、目標内 |
| M3 13〜18か月 | 第2波。L3は価値と制約が揃う数システムに限定 | KPI基準を満たすシステムのみ助言運用へ昇格 |

### 4. 横展開の仕組みとコスト見立て（要検証）

比較対象は「各システムを新規導入プロジェクト並みに個別手作業で整備した場合」。減らせる工程は、構成調査（ディスカバリのスクリプト化）、資料のMarkdown化（パイプライン化）、ランブック雛形作成（テンプレート化）。減らせない工程は、顧客ヒアリング、乖離のレビュー、障害履歴の整理。仮説として、L2到達までの工数を個別手作業比で 40〜60%減（要検証。パイロットで実測して置き換える）。

### 5. KPI（c9）

- 一次切り分け正答率: 障害ごとに人が確定した原因コンポーネントを、AIの上位3候補が含む割合。目標: シャドウ運用で60%以上を助言運用昇格の閾値（仮置き）
- 危険な誤誘導率: 誤った確信的断定の割合（5%未満を仮置き）
- 切り分け所要時間の短縮、アラートの重複/不要率の低減
- 測定: 事後に人がラベル付けした障害台帳（`incidents/`）と照合。ラベル付けは月次で担当SRE

## 評価基準への適合

- c1: L0〜L3の段階定義表と、段階ごとの適用施策（P1〜P5）を示した。
- c2: M0〜M3の期間・成果物・完了判定を表にした。
- c3: 可能: L1〜L2の一次切り分け支援、構成の逆生成、アラート整理。不可能/非現実的: 全システムでの全量コード理解、変更系の自動修復、設計書Excelの無人変換、暗黙知のヒアリング抜きの復元。代替は段階制限と人のレビュー。
- c4: P1〜P5に入力・手順・出力・担当を記述した。
- c5: 比較対象と減らせる工程を明示したコスト低減の見立てを置いた（数値は要検証）。
- c6: 下記失敗モードに加え、データ送信制約→P1で判定し閉域/L1止め、AIの誤判断→シャドウ運用と助言止まり、体制不足→段階を絞る、を設計に組み込んだ。リスク表の独立節は設けていない。
- c7: 簡潔に、段階別の定額オンボーディング＋運用サブスクの2層を想定（詳細は未設計）。
- c8: 文書種別ごとの変換工数目安と、自動化が困難な箇所（図形主体の構成図、暗黙の運用ルール、コード）を示した。
- c9: 正答率・誤誘導率・所要時間・測定方法を示した。

## トレードオフ

- 全システムの均質な高水準化を捨て、段階制にしたため、L1止まりの顧客には「一次切り分けまで」が約束できない。
- 設計書Excelの全面変換を捨て、実態からの逆生成を優先したため、設計意図（なぜそうなっているか）は復元できず、ヒアリング依存が残る。
- Zabbix併用を許すため、高度な分析（分散トレース等）はL3の一部に限られる。
- 事業面（価格・提供形態）は薄い。

## 想定される失敗モード

1. **ディスカバリの権限が取れない**: 読み取りアカウントや委託契約上の権限が得られず、L2に進めないシステムが多数になる。P1でゲートを設けるが、多数がL1止まりになりうる。
2. **変換品質が低くレビュー工数が下がらない**: 方眼紙Excelの構造化精度が低く、レビューが再作成に近い工数になり、コスト低減が実現しない。M1の実測で早期に判明させ、計画を見直す。
3. **AIの切り分けが運用で信用されない**: 誤誘導が数回出ると現場が使わなくなる。シャドウ運用と閾値判定で昇格を管理するが、閾値自体が仮置き。
4. **パイロット3件が代表的でない**: 横展開時に想定外の構成（メインフレーム連携、パッケージ製品）が多数を占める。

## 前提と未確認事項

- 対象規模（50〜200）、18か月、工数目安、40〜60%の低減、正答率60%などの数値はすべて仮定であり、パイロットでの実測が必要。
- 組織の人員規模と既存のツール資産（既に内製ツールがあるか）が不明。M0の内製が可能かは未確認。
- 顧客が外部LLMへのデータ送信を許可する割合が不明。閉域内LLMを使う場合の精度・コストは未確認。
- Zabbixの版・保有データ期間・API利用可否は顧客ごとに異なり、確認していない。
- 価格・提供形態の市場受容性は検証していない。
