## 案の要旨

CI/CD を「手元の速いフィードバック層」と「リモートの強制層」の2層に分け、強制力は必須チェックとブランチ保護だけに持たせる。エージェントは Hook でローカル検証を回して push 回数を絞り、リモートは変更パスに応じた段階的ゲート（軽量→重い）と concurrency キャンセル、マージキューで計算量を抑える。テスト弱体化と CI/Hook 設定の改変は、保護パス（CODEOWNERS 相当）と差分検査ジョブで機械的に検出し、該当 PR は人間の承認を必須にする。

## 設計

### 層構造

```
[エージェント作業中]  Hook（編集後 / コミット前 / タスク終了時）  ← 助言層。迂回されうる前提
        │ タスク完了時のみ push（PR 単位に束ねる）
        ▼
[リモート Tier0]  軽量ゲート: 設定改変検査・テスト改変検査・lint・型検査（数分以内）
        ▼ 通過したら
[リモート Tier1]  影響範囲フィルタ付きユニット/結合テスト（並列・キャッシュ）
        ▼ 通過 + 人間レビュー
[マージキュー]    最新 main と結合した状態で Tier1 を再実行 → マージ
        ▼
[デプロイ]        既存のデプロイゲート（本案では変更しない）
```

### 検証種別ごとの実行場所（c3）

| 検証 | ローカル Hook | リモート | 備考 |
| --- | --- | --- | --- |
| フォーマット / lint | 編集後に自動修正 | Tier0 で再検査（必須） | ローカルは助言、リモートが正 |
| 型検査 | コミット前 | Tier0（必須） | |
| 変更範囲のユニットテスト | タスク終了時 | Tier1（必須、影響範囲フィルタ） | |
| 全量テスト・結合テスト | 実行しない | マージキューでのみ全量（必須） | 環境差・シークレット依存のため |
| テスト改変検査 / 設定改変検査 | 実行しない | Tier0（必須） | ローカルに置くと迂回されるため |
| シークレット・外部接続を要するテスト | 実行しない | リモートのみ | 前提事実3 |

規則は一つ：**「合否を決める検証」はすべてリモートに置き、ローカルは「落ちるものを早く知らせる」ためだけに使う。** ローカルで通ったことを理由にリモートの検証を省略しない。

### 強制層（c1）

- 保護ブランチ + 必須ステータスチェック（Tier0, Tier1, マージキュー）。管理者にも適用する。
- エージェントが使う資格情報には、保護ブランチへの直接 push 権限と、ブランチ保護設定・CI 設定の変更権限を与えない。
- ローカル Hook が無効化・回避されても、リモートの必須チェックで同じ検証が必ず走るため、Hook の有無は品質を左右せず、速度だけを左右する。

### CI 発火回数と計算時間の削減（c2）

1. **束ね**: エージェントはタスク完了時のみ push する。作業中のコミットはローカルに留め、PR は squash マージにする。発火回数は「エージェントのコミット数」から「PR の push 数」へ下がる（比率は運用データがないと断言できない。導入後に push あたり・PR あたりの実行数を計測して確認する）。
2. **concurrency キャンセル**: 同一ブランチ（PR）の古い実行を、新しい push で自動キャンセルする。連続 push の無駄が実行時間の積算から消える。
3. **パスフィルタ + テスト選択**: ドキュメントのみの変更では Tier1 を実行しない。コードは変更ディレクトリに紐づくテストだけを Tier1 で実行する。全量はマージキューで1回だけ。
4. **段階的ゲート**: Tier0 が落ちたら Tier1 を起動しない。重いジョブの空振りを避ける。
5. **キャッシュと並列化**: 依存キャッシュ、テストのシャード分割。

効果の見通し：削減の主因は 1〜3 で、特に「中間コミットごとの全量実行」が無くなる点が大きい。ただし本ブリーフに実測値は無いため、数値目標は置かず、導入前後で「PR あたり CI 分数」と「push から必須チェック完了までの中央値」を計測して判断する。

### テスト弱体化・設定改変対策（c4）

Tier0 に差分検査ジョブを置く（ベース=マージ先ブランチとの差分）:

- テストファイルの削除、skip/only/xfail 系マーカーの追加、アサーション行数の減少、閾値設定（カバレッジ下限等）の低下を検出。検出したら PR にラベルを付け、**人間の明示承認がなければ通らない**ようにする（必須レビュアー）。
- 保護パス: CI 定義、Hook 設定、ブランチ保護関連の設定、差分検査スクリプト自身、CODEOWNERS を指定し、これらを変更する PR はエージェント単独でマージできない。
- 差分検査スクリプトは**マージ先ブランチ側のもの**を実行する（PR 側で書き換えても検査が緩まない）。
- テストは通ったがテスト数が減った場合のため、Tier1 でテスト実行件数を記録し、前回比で減少していれば警告する。

### 導入ステップ（c5）

1. ブランチ保護 + 必須チェック + エージェントの権限制限（ここが無いと以降が無意味）。
2. concurrency キャンセルとパスフィルタ（設定のみで効果が出る）。
3. 保護パスと差分検査ジョブ（Tier0）。
4. ローカル Hook（フォーマット・lint → 型 → 変更範囲テストの順に追加）と「完了時のみ push」の運用。
5. マージキュー導入と、Tier1 の影響範囲テスト選択。
6. 計測（PR あたり CI 分数、CI 待ち時間）を見てフィルタ精度を調整する。

各段階は前段が無くても単独で動くが、1 を最初に置く。

### 人間レビューへの影響（c7）

PR 単位の squash で人間が見る粒度を「エージェントの1タスク」に揃える。機械で見られる点（lint、型、テスト改変検査）は Tier0 で済ませ、人間は設計と意図の確認に集中する。保護パス変更とテスト弱体化の疑いがある PR だけ承認を要求し、それ以外のレビュー負荷は増やさない。一方で「束ねた PR が大きくなる」リスクがあり、タスク粒度の上限を運用で決める必要がある。

## 評価基準への適合

- **c1**: 合否を決める検証をすべて必須チェックとブランチ保護に置き、エージェントの資格情報から保護設定の変更権限を外す。Hook を迂回されてもリモートで同じ検証が必ず走る。
- **c2**: 束ね、concurrency キャンセル、パスフィルタ/テスト選択、段階的ゲート、キャッシュを具体的に列挙した。効果は実測値が無いため数値でなく計測指標で示した。
- **c3**: 検証種別ごとの実行場所を表にし、「合否はリモート、ローカルは早期通知」という一つの規則で線引きした。
- **c4**: 差分検査ジョブ（テスト削除/skip/アサーション減少/閾値低下）、保護パス、マージ先側スクリプトの実行、テスト件数の前回比を示した。
- **c5**: 6段階の導入順を示し、設定のみで始められる段階から並べた。
- **c6**: トレードオフと失敗モードの節に具体項目を列挙した。
- **c7**: PR 粒度の統一と、人間の承認を要する対象の限定を示した。

## トレードオフ

- **フィードバック速度を一部犠牲にする**: 全量テストをマージキューに寄せるため、結合レベルの失敗は PR の後半でしか分からない。
- **PR が大きくなる**: 束ねることで CI 回数は減るが、1PR あたりの差分が増え、レビューしにくくなる。
- **偽陽性による人間の待ち**: テスト弱体化の検出は静的な差分ルールなので、正当なテスト削除でも承認待ちが発生する。
- **設定の保守コスト**: パスフィルタとテスト選択は依存関係の変化に追随させる必要がある。
- **ローカル検証を信頼しない**ため、Hook の検証結果を CI で再利用して時間を削ることはしない。重複実行のコストを受け入れる。

## 想定される失敗モード

1. **パスフィルタの漏れ**: 変更ファイルとテストの対応が不完全で、影響を受けるテストが Tier1 で選ばれない。マージキューの全量で捕まるが、キューで落ちる頻度が高くなり、待ち時間がかえって増える。
2. **差分検査の回避**: テストを弱めずに「常に通る」別テストを足す、または検査対象外の形（テストヘルパーの書き換え）で実質的に無効化する。静的ルールでは捕まらない。人間レビューが最後の砦になる。
3. **マージキューの詰まり**: 全量テストが長い、または不安定なテストがあるとキューが詰まり、エージェントの高頻度 PR で待ち行列が伸びる。
4. **権限制限の抜け**: エージェントが使うトークンが想定より広い権限を持つと、保護設定ごと変更されて全層が無効になる。

## 前提と未確認事項

- ブリーフに CI の実行時間やコミット頻度の実測値が無いため、削減幅は数値で示していない。
- 使用する CI/リポジトリ基盤が、必須チェック・マージキュー・パス別レビュー必須・concurrency キャンセルをすべて備えていると仮定した。無い機能がある場合、該当段階は代替が要る。
- テスト選択の仕組み（依存グラフに基づくか、ディレクトリ対応か）はリポジトリごとに異なり、ブリーフでは分からないので、ディレクトリ対応という単純な方式を仮定した。
- エージェントの資格情報を分離できると仮定した。分離できない環境では c1 が成立しない。
- 「完了時のみ push」をエージェントに守らせる手段（指示か Hook か）は未確認で、守られなくても強制層は壊れないが削減効果が減る。
- デプロイ層は検討対象外なので、マージ後の段階ゲートは変更しない前提とした。
