## 答え

**合否を決める検証はすべてリモートの必須チェックに置き、ローカル Hook は「落ちるものを早く知らせる」助言層に徹させる。**
CI は「PR 更新ごとの軽量・影響範囲チェック」と「マージキューでの完全検証 1 回」の二段にし、
エージェントは作業完了単位でだけ push する。発火回数は「コミット数」から「PR の push 数」へ下がる。
テスト弱体化と CI/Hook 設定の改変は、保護パスと差分検査で検出して人間承認を必須にする。
ただし静的な差分検査は巧妙な無力化を捕まえられないので、テスト件数の前回比と変異テストで補い、人間レビューの形骸化を抜き取りレビューで防ぐ。
導入は「ブランチ保護と権限制限 → 発火削減 → 差分検査 → Hook → マージキュー → 計測」の順に、設定だけで効くものから始める。

## 本論

### 1. 原則: 合否はリモート、ローカルは早期通知

ローカル Hook は設定次第で迂回・無効化され、エージェント自身が回避する可能性もある。環境差（OS・依存・シークレット・外部接続）もあるため、ローカルで通ったことは信頼の根拠にならない。
したがって強制力は、ブランチ保護（直接 push 禁止・管理者にも適用）と必須ステータスチェックだけが持つ。Hook の有無が左右するのは品質ではなく速度である。
2 つの帰結がある。

- ローカル Hook の検証結果を CI で再利用して時間を削らない。同じ検証を 2 回走らせるコストは意図的に受け入れる。
- エージェントが使う資格情報には、保護ブランチへの直接 push 権限と、ブランチ保護・CI 設定の変更権限を与えない。これが無いと以降の層はすべて無意味になる。

### 2. 何をどこで走らせるか

| 検証 | ローカル Hook | リモート | 備考 |
| --- | --- | --- | --- |
| フォーマット / lint | 編集後に自動修正 | Tier 0 で再検査（必須） | ローカルは助言 |
| 型検査 | コミット前 | Tier 0（必須） | |
| 変更範囲のユニットテスト | タスク終了時 | Tier 1（必須・影響範囲フィルタ） | |
| 全量・結合・E2E・ビルド | 実行しない | マージキューで 1 回（必須） | 環境差・重さのため |
| テスト改変 / 設定改変の検査 | 実行しない | Tier 0（必須） | ローカルに置くと迂回される |
| シークレットや外部接続を要する検証 | 実行しない | リモートのみ | |

リモートの段は 3 つ。

- **Tier 0 Policy Guard**: 全 PR 更新で必ず走る軽量層。設定・テスト改変検査、lint、型検査。ここは通常のパスフィルタで省略しない（検査対象が品質ゲートそのものだから）。
- **Tier 1 Impact Check**: 変更種別に応じた影響範囲だけを実行する。
- **Merge Gate（マージキュー）**: 最新 main と結合した状態で、全量テスト・結合・E2E・ビルドを 1 回だけ走らせる。

変更種別ごとの実行内容は次のとおり。最初は単純なパス対応表で始め、依存グラフが整ったらテスト選択を精密化する。

| 変更種別 | PR 更新時に走るもの |
| --- | --- |
| ドキュメントのみ | Tier 0 のみ |
| 単一パッケージのコード | Tier 0 + そのパッケージの lint・型・ユニット・ビルド |
| 共通ライブラリ | Tier 0 + 依存する全パッケージの対象テスト |
| テスト変更 | Tier 0 + 対応する本体のテスト + 弱体化検査（必要なら全量） |
| CI / Hook / テスト基盤の変更 | Tier 0 + 全量 + 保護パス承認 |

### 3. CI の発火回数と計算時間を減らす

1. **束ね**: エージェントは作業中に細かくコミットしてよいが、push はタスク完了時だけにする。PR は 1 つの論理変更に限り、squash でマージする。
2. **古い実行の自動キャンセル**: 同一 PR の連続 push では最後の実行だけが残る。
3. **パスフィルタとテスト選択**: ドキュメントのみなら Tier 1 を省く。コードは変更ディレクトリに紐づくテストだけ走らせ、全量はキューで 1 回。
4. **段階的ゲート**: Tier 0 が落ちたら Tier 1 を起動しない。重いジョブの空振りを避ける。
5. **キャッシュと並列化**、および draft PR では最小限だけ走らせること。

見通しは構造的な式で示せる。1 タスクあたりの CI 計算量は、従来「コミット数 × 全量」だったものが、「push 数 ×（Tier 0 + Tier 1）+ 1 ×（Merge Gate）」になる。
エージェントが 1 タスクで N 回コミットして 1 回だけ push するなら、PR 段階の発火は N 回から 1 回になり、全量は 1 回に集約される。N と全量・Tier 1 の所要時間は各リポジトリの実測でしか決まらないので、ここで削減率は主張しない。

効果の主因は 1〜3 で、特に「中間コミットごとの全量実行」が消える点が大きい。ただし**削減率を示す実測値は 3 者のいずれにも無い**。数値目標は置かず、導入前後で「PR あたり CI 分数」と「push から必須チェック完了までの中央値」を測って見通しを実測に置き換える。
合格基準の初期案は「どちらも導入前の中央値を下回ること」とし、下回らなければ該当段階（フィルタ精度、キューの混雑）を見直す。具体的な目標値は、導入前の計測値が得られてから決める。

### 4. 必須チェックの落とし穴を先に潰す

パスフィルタでジョブがスキップされると、必須チェックが「未報告」のまま残ってマージ不能になる（逆に、スキップを成功扱いにする設定だと素通りになる）。
必須チェックには個別ジョブではなく、**常に走って各ジョブの結果を集約する 1 つの判定ジョブ**を指定する。こうすればフィルタで何を省いても、必須チェックの名前と意味が変わらない。

### 5. テスト弱体化と設定改変への対策

検出する対象は、テストファイルの削除・大幅縮小、skip / only / xfail 系の追加、アサーション行の減少、カバレッジ下限など閾値の低下、CI・Hook・テストランナー・依存定義・CODEOWNERS・差分検査スクリプト自身の変更、必須チェック名の変更や失敗を無視する設定の追加である。

- 検出したら PR にラベルを付け、**人間の明示承認がなければ通らない**ようにする。エージェントの自己承認は承認と数えない。
- **差分検査スクリプトはマージ先ブランチ側のものを実行する**。PR 側で書き換えても検査は緩まない。CI 設定の変更 PR も、変更前の信頼できる定義で検証する。
- Tier 1 でテスト実行件数を記録し、前回比で減っていれば警告する。
- 静的ルールの限界（テストヘルパーの書き換え、常に真になるアサーション）に対しては、Tier 1 の後段で**変更されたテスト対象に絞った変異テストをサンプリング実行**し、「テストが通るのに何も検出できない」状態を検出する。これは 3 者の案に無かった補強である。

### 6. 人間のレビュー負荷

機械で判定できること（lint、型、改変検査）は Tier 0 で済ませ、人間は設計と意図の確認に集中する。人間の承認を求めるのは保護パスの変更とテスト弱体化の疑いがある PR に限り、それ以外のレビュー負荷は増やさない。
束ねた PR は大きくなるので、1 PR は 1 つの論理変更とし、CI・Hook 設定の変更は機能変更と混ぜず独立 PR にする。大きな変更はレビュー可能な中間 PR に分ける。タスク粒度の上限は運用で決める。
承認対象を絞ると、検知への過信から承認対象外の PR のレビューが形骸化する恐れがある。承認対象外の PR からも一定割合を抜き取ってレビューする。

### 7. 導入の順序

1. ブランチ保護、必須チェック（集約ジョブ）、エージェントの権限制限。**これを最初に置く。**
2. 同一 PR の古い実行のキャンセルとパスフィルタ（設定のみで効果が出る）。
3. 保護パスと差分検査ジョブ（Tier 0）。
4. ローカル Hook（フォーマット・lint → 型 → 変更範囲テストの順）と「完了時のみ push」の運用。PR テンプレートにテスト変更理由の欄を足す。
5. マージキュー導入と、重い検証の移送、Tier 1 の影響範囲選択。
6. 計測を見て、影響範囲マップと検出ルールを調整する。変異テストはここで試す。初期方針は、保護パスやテスト変更を含む PR だけを対象に、変更されたテスト対象のうち一部を実行するところから始める。実行頻度と時間は計測しながら決める。

各段階は前段が無くても単独で動くが、1 を最初にする。

### 8. トレードオフ

- **フィードバック速度を一部犠牲にする**: 結合レベルの失敗はマージキューまで分からない。
- **マージ待ちが伸びうる**: 重い検証を 1 か所に集めるため、キューが混むと最終マージまでの直列待ちが増える。
- **PR が大きくなる**: 束ねるとレビューしにくくなる。
- **偽陽性による人間の待ち**: 正当なテスト整理でも承認待ちが発生する。
- **重複実行**: ローカルを信頼しないので、同じ検証が 2 回走る。
- **維持コスト**: パスフィルタ、検出ルール、変異テストの対象選定は依存関係の変化に追随させる必要がある。
- **コミット単位の追跡性を失う**: どのコミットで壊れたかを CI ログだけから特定できない。キューで落ちた PR は、ローカルコミットを 2 分探索で切り分けるスクリプトを用意しておく（これは新規の提案で、3 案には無い）。

### 9. 失敗モード

1. **影響範囲マップの漏れ**: 必要なテストが Tier 1 で選ばれない。キューの全量で捕まるが、キューでの失敗が増えると待ち時間がかえって伸びる。
2. **無力化のすり抜け**: 静的ルールでは捕まらない改変が通る。最後の砦は人間レビューと変異テストだが、どちらも完全ではない。
3. **マージキューの詰まり**: 全量が長い、または不安定なテストがあると、高頻度の PR で待ち行列が伸びる。先頭の失敗が後続を巻き込む。
   対策の初期案: 失敗した PR はキューから外して後続を再構成する／全量を並列シャードに分ける／ジョブにタイムアウトを置く／不安定なテストは担当者を付けて修正する（テストを外して通すことはしない）。キューの待ち時間は計測指標に加える。
4. **権限制限の抜け**: トークンが想定より広い権限を持つと、保護設定ごと変更されて全層が無効になる。
5. **必須チェックの空洞化**: フィルタでスキップされたジョブが成功扱いになり、検証されないままマージされる（集約ジョブで防ぐ）。
6. **CI 設定変更 PR が検査自体を弱める**: 信頼できる側の定義で検証できない運用だと素通りする。

## 3者が一致した点

独立に書いた 3 つのモデルが、次の設計で一致した。**この答えで最も信頼できる部分である。**

- ローカル Hook は助言層で、迂回される前提で扱う。強制力はリモートの必須チェックとブランチ保護にだけ置く。
- CI は二段（PR 更新時の軽量・影響範囲チェック → マージ直前の完全検証）にする。
- 発火回数は、タスク完了単位の push と、古い実行の自動キャンセルで減らす。
- テスト改変と CI/Hook 設定の改変を差分検査で検出し、該当 PR は人間承認を必須にする。
- 3 者とも、最大の懸念に「静的な差分ルールでは巧妙なテスト無力化を捕まえられない」ことを挙げた（評価の `biggest_concern`）。

## 見解が割れた点

- **ローカル検証の結果をどう扱うか**: A は PR 本文への自己申告ログを許容しつつマージ条件にはしない。B は CI で再利用しない。C は触れていない。**B を採った。** 自己申告は形骸化しやすく（Claude の評価が A に挙げた懸念）、再利用すると迂回の入口になるためである。ただし重複実行のコストは残る。
- **PR 段階でどこまで走らせるか**: C は Fast CI を最小にして重い検証をすべてキューへ寄せる。A と B は影響範囲テストまで PR 段階で走らせる。**A・B を採った。** C の方式はキューの失敗が増え、先頭の失敗が全体を詰まらせる（Gemini 自身が C の最大の懸念に挙げた）。ただしどちらが良いかは、そのリポジトリのテスト時間と PR 頻度次第で、判断に必要な実測値は無い。
- **導入の細かさ**: A の 9 段階、B の 6 段階、C の 3 フェーズ。粒度の違いで、方針の対立ではない。B と C を統合して 6 段階にした。
- **承認対象の広さ**: A は PR 本文テンプレートの記載確認まで求める（Gemini は偽陽性による承認待ちの増加を懸念）。B・C は保護パスと検出された弱体化に絞る。**絞る側を採り**、抜き取りレビューで補った。偽陽性率は測定されていない。
- 評価者間の一致度は低く（Kendall W=0.361）、首位と次点の差もわずかだった。優劣は 3 案の間で付いていないため、「どの案が勝ったか」ではなく上記の論点ごとに判断した。

## 取り込まなかった要素

- **A の draft PR の扱い**（draft では最小チェックだけ走らせる）: 補足としては取り込んだが、必須の設計にはしなかった。draft を使うかどうかはチームの運用による。
- **A の PR 本文テンプレートの必須記載と Hook ログの貼り付け**: テンプレートにテスト変更理由の欄を足す部分だけ採用した。Hook ログの貼り付けは自己申告で、強制力が無く、形骸化の懸念が評価で指摘されたため外した。
- **A の CD の節**（保護ブランチ由来のコミットだけをデプロイする）: ブリーフの対象外（デプロイ先インフラ）に近く、3 案のうち A だけだったが、原則として自明なため本論には入れなかった。
- **B の Tier 0 の中の lint と型検査を必須とする細部**: 表の中で触れた。個別の設定は対象リポジトリ依存で、ここでは決められない。
- **C の「PR 段階では重い検証をしない」**: 上記の理由で採らなかった。

## 少数意見として残すもの

- Gemini: 「マージ先側のスクリプトで検出しても、すり抜けた場合に人間が検知を過信してレビューが形骸化する」。→ 抜き取りレビューとして取り込んだが、効果は未検証。
- OpenAI: 「影響範囲マップの初期精度が低いと、必要なテストが選ばれず、キューやリリース後に不具合が発覚する」。→ 失敗モード 1 と、計測による調整の段階に反映した。
- Claude: 「自己申告の Hook ログと PR テンプレートの運用が形骸化する」。→ 本論の方針（ログを根拠にしない）に反映した。

## この答えの限界

- Gemini と OpenAI は実行環境のファイル・コマンド・Web に触れていない。両者の案と評価は brief.md の記述のみに基づく。
- **削減効果を示す実測値は無い。** 「何がどれだけ減るか」は構造的な見通しに留まり、c2 は 3 者平均で 4.0〜4.3 にとどまった。
- 影響範囲テスト選択の具体ルール（パス→テストの対応、誤検出の許容率）と、集約ジョブの CI 設定例は、対象リポジトリと CI 基盤が決まらないと書けず、ここでは扱っていない。
- 対象リポジトリの言語・CI 基盤・テスト構成は不明で、影響範囲マップや検出ルールは方針としてしか書けていない。必須チェック、マージキュー、パス別承認、concurrency が使える基盤を仮定している。
- 変異テストと 2 分探索による切り分け、必須チェックの集約ジョブは、3 案に無い新規の提案で、独立に評価されていない（critique フェーズで検品する）。
- 批評（OpenAI）が 2 回目も REVISE だったため、残った指摘をここに記す（Gemini は 2 回とも PASS）:
  - 削減効果の定量的な期待値・目標値が無い（入力に実測が無く、数値を作ると根拠のない主張になるため置かなかった）。
  - 影響範囲テスト選択の具体ルール、マージキューの容量設計と優先度・再試行ポリシー、変異テストのサンプリング頻度とコスト見積、差分検査ルールの実装例が無い。
  - 各導入段階の成功条件（メトリクス閾値）とロールバック基準が無い。
