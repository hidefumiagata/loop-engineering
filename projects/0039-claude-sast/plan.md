# 0039 ClaudeのサブスクでSAST: 計画

## 目的（再定義）
Claude のサブスクリプション（Pro/Max/Team/Enterprise の利用枠）の範囲で、ソースコードの脆弱性検出（SAST 的用途）を行う場合に、現時点で本命となる手段を特定する。Anthropic 公式の手段（`/security-review`、Claude Code Security Review の GitHub Action、Claude Code の GitHub 連携・routine 等）を軸に、API 従量課金との違い、従来型 SAST との役割差を含め、採用/非採用の条件を判断できる状態にする。

## 用語の範囲
「SAST 的用途」= ソースコードを実行せずに読んで脆弱性を指摘するもの。コード全般のレビュー支援は、脆弱性指摘を目的とする機能のみ対象とし、一般的なレビュー機能は対象外。

## 受入基準
| ID | 重み | 基準 |
| --- | --- | --- |
| a1 | 3 | サブスク枠内で SAST 的用途に使える Anthropic 公式の手段を列挙し、各手段の提供形態・実行場所・認証/課金方式（サブスク枠か API 課金か）を公式出典 URL 付きで示している |
| a2 | 3 | 「本命」を1つ以上明示し、選定基準（精度・運用コスト・導入難易度の3軸を定性評価）と、採用条件・非採用条件（どの場合に別手段を選ぶか）を述べている |
| a3 | 3 | 公式が明記する制約（検出範囲、結果の非決定性、枠消費、対応言語、プラン要件など）を数値・条件付きで表にしている |
| a4 | 3 | サブスク枠内利用と API 従量課金利用について、コスト発生のトリガーと制限事項（レート制限等）を対比表にしている |
| a5 | 2 | 従来型 SAST（CodeQL・Semgrep 等）との役割差・併用方針を、公式記述と非公式知見を区別して記している |
| a6 | 2 | 非公式の構築事例・運用知見（誤検知、コスト、落とし穴）を、公開日・取得日付きで記している |
| a7 | 1 | 公式に記述が無い論点を「情報なし」または「非公式のみ」と明示している |
| a8 | 2 | すべての主張に取得日付き出典 URL が付き、公式と非公式が分けて列挙されている |

## 採用しなかった批評とその理由
- **a9 の「評価スコアの数値化」**: 数値スコアは根拠が主観的で第三者が再現できない。3軸という提案は a2 に取り込み、評価は定性（高/中/低と根拠）にとどめた。
- **a2 の「本命の定義が主観的」**: 指摘は採用し、選定基準を3軸として a2 に明記した（上記）。
