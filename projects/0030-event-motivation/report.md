## 一言で言うと
「選ばれて行く」を「行きたい人が先に手を挙げ、行った人が持ち帰って称賛される」循環に置き換える。予算ゼロで、業務時間と既存の社内の場だけを使う。

## 解こうとしている問題
80名のSRE/DevOps組織で、社外イベントへの参加・登壇が指名と半強制で回っている。指名されたメンバーは「やらされ感」を持ち、持ち帰りも薄くなる。それ以外のメンバーは、機会があること自体に気づかない。

## どう動くか
運用責任者は「イベント係」1名。現場リード1名が補佐し、3か月ごとに交代する。

**具体例（開始から最初の成果まで約5週間）**
1. 第1週: イベント係が、無料参加できるオンライン／近隣のSRE・DevOps系イベントと、登壇募集（CFP）の締切を1枚の共有表にまとめる。出典は各イベントの公式サイトとし、毎月1回見直す。
2. 第1週: 部門長が「業務時間内参加の許可」を宣言する。月に1人1日、承認は不要で事後報告のみとする。これが外発的動機の核になる。
3. 第2週: メンバー自身が、共有表の「行きたい」欄に名前を書く。理由は1行でよい。指名はしない。
4. 第3〜4週: 参加者は参加後1週間以内に、既存の定例会の冒頭10分で持ち帰りを共有する。
5. 第5週: 参加者が自分で書く「持ち帰りメモ」を社内wikiに置き、部門長が全体の場で名前を挙げて称賛する。評価面談で提示できる実績として残す。

**入口の段階設計**

| 段階 | 参加 | 登壇 |
| --- | --- | --- |
| 入門 | オンラインの無料イベントを業務時間内に視聴する | 社内定例会で10分のLT（持ち帰り共有）をする |
| 中級 | 国内の近隣開催イベントに参加し、持ち帰りメモを書く | 社内でCFP提出前のリハーサル（ドライラン）を受ける |
| 上級 | 他メンバーを誘う「引率役」になる | CFPを提出し、採択されたら社内で壮行会とリハーサルを行う |

**内発的動機の仕組み**
- 持ち帰りメモを書くことで、自分の学びが他人の役に立つ実感が得られる（有能感）。
- 登壇の入口を社内LT→ドライラン→CFPと刻むことで、小さな成功体験を積める。
- 同僚と一緒に参加する「相乗り」を共有表に書けるようにし、関係性の動機づけとする。

**外発的動機の仕組み**
- 業務時間内参加の許可（月1人1日、事後報告のみ）。
- 評価面談で「社外発信・学習」を実績として扱えると、部門長が明示する。評価制度そのものは変えず、既存の面談の観点に載せるだけにする。
- 全体の場での称賛と、社内wikiへの名前入りの掲載。

**運用負荷の見積もり（イベント係、週あたり）**

| 作業 | 週あたり |
| --- | --- |
| 共有表の更新（月1回2時間を週換算） | 0.5時間 |
| 「行きたい」の受付と日程の調整 | 1時間 |
| 持ち帰り共有の場の進行 | 0.5時間 |
| ドライランの調整（月2件・各1時間を週換算） | 0.5時間 |
| 月次の振り返りと部門長への報告（月1時間を週換算） | 0.25時間 |
| 合計 | 約2.75時間（上限5時間に収まる） |

この見積もりは筆者の想定であり、実測ではない。1か月の試行で実測し、5時間を超えたら作業を削る。

**必要な資源（すべて既存）**: 業務時間（月1人1日の許可）、既存の定例会の10分枠、社内wiki、共有スプレッドシート、無料で参加できるイベント。有償のチケットや交通費に依存しない。

## なぜ今まで誰もやっていないのか
似た仕組みは既にある。登壇前のドライランを社内で行う取り組みは、[Why we host conference talk dry runs](https://sophiebits.com/2018/10/19/conference-talk-dry-runs) など複数の記事で紹介されている。社内カンファレンスで人材を育てる例もある（[The power of an internal conference](https://medium.com/bridgeable/the-power-of-an-internal-conference-34f9ce6f7dcd)）。取得日はいずれも2026-10-06で、本文の閲覧はしておらず、検索結果の要約から判断している。

したがって「誰もやっていない」わけではない。この案の違いは、(1) 指名を止めて手挙げに一本化すること、(2) 参加と登壇を同じ入口の段階にまとめること、(3) 予算を前提にせず許可と称賛だけで回すことにある。流行らない理由として考えられるのは、許可だけでは動機にならず、結局は一部の積極的な人しか動かないことだ。これは実測していない推測である。

## 壊れる条件
1. **業務時間内参加の許可が実際には使えない。** 繁忙で上長が嫌な顔をすると、許可は形だけになる。兆候: 最初の1か月で「行きたい」欄の記入が2件未満。
2. **称賛が形骸化する。** 同じ人ばかりが称賛され、他の人は冷める。兆候: 参加者の3か月累計で、同一人物が過半を占める。
3. **イベント係が燃え尽きる。** 週5時間の上限を超え、特定の個人に負荷が集まる。兆候: 係の実測工数が2週連続で週4時間を超える。
4. **持ち帰り共有が義務化し、「半強制」に戻る。** 共有の場が負担になり、手挙げが減る。兆候: 「行きたい」の記入が減り、共有会で「行かされた」という声が出る。
5. **無料で参加できるイベントが、組織のミッションと合致しない。** 共有表の候補が使われなくなる。兆候: 「行きたい」欄の理由が「他に無いから」ばかりになる。

## 一番小さく試す方法
**1か月の試行（1チーム10名程度）。**
- 第1週に共有表を作り、部門長が許可を宣言する。
- 判定指標（試行開始時点で記録しておく）:
  - 成功: 「行きたい」の自発的な記入が4件以上、持ち帰り共有の実施が2回以上、イベント係の実測工数が週5時間以内。
  - 失敗: 記入が2件未満、または工数が週5時間を超える。
  - 中間: 上記の間は、壊れる条件のどれに当たるかを特定して手直しする。
- 閾値（4件・2件）は試行チームの規模から置いた仮の値で、根拠のある数字ではない。試行後に見直す。

## 捨てた派生案
- **指名制を残して称賛だけ足す案。** 目的の「半強制をやめたい」に反するため捨てた。
- **社内ポイント制や表彰制度。** 運用負荷が高く、運用に予算か作り込みが要る。ゼロ予算の前提に合わない。
- **イベントの参加を全員必須の年1回とする案。** 強制になるため捨てた。
- **外部のスポンサー枠や招待枠を獲得する案。** 有償または交渉が要り、再現性が低い。将来の拡張として残す。
- **登壇者を先に決めて逆算する案。** 手挙げの趣旨に反する。
