## 案の要旨

第4回を「講義」ではなく「その場で作って、AIに攻撃させて、直す」ワークショップに作り替える。参加者は持ち込んだ実在の資料テーマで、AIにスライドを作らせ、別のAI（別セッション・別人の相互レビュー）に敵対的レビューさせて直す。この「作る側とレビューする側を分ける」構造がそのまま Loop Engineering の中核なので、紹介は説明ではなく体験の延長として置き、主催者が事前に走らせた合議の結果（今回の議論自体）を素材にする。

## 設計

### 減少の原因仮説（c3）

| ID | 仮説 | 根拠 |
| --- | --- | --- |
| H1 | 初歩の使い方は既知になり、新規性が消えた | 現在はAI利用が当たり前（ブリーフ） |
| H2 | 第3回が第2回の再演で、「また同じ」と思われた | 第2回と第3回はほぼ同内容 |
| H3 | 座学中心で受け身。自分の仕事に直結する成果が残らない | 仮説（ブリーフ記載） |
| H4 | 参加しても翌日の仕事が変わらず、次回に来る動機がない | 推測 |

### タイムテーブル（合計120分、挨拶〜撤収）

| 分 | 内容 | アイデア |
| --- | --- | --- |
| 0–5 | 挨拶・今日のゴール提示 | — |
| 5–15 | 主催者デモ: 「AI一発スライド」の悪い例を見せ、何が問題かを参加者に言わせる | 1 |
| 15–50 | ワーク1: 各自が持ち込んだ実在テーマで、構成案→スライドを作る（35分） | 2 |
| 50–75 | ワーク2: 作った資料を隣の人の資料と交換し、別のAIセッションに「敵対的レビュー」させて指摘を直す（25分） | 3 |
| 75–80 | 休憩 | — |
| 80–100 | Loop Engineering紹介: ワーク2で手でやったことを自動化した仕組み。事前に走らせた合議（今回の議論）のPRを実物で見せる | 4 |
| 100–112 | 持ち帰りカード作成: 自分の業務で使うプロンプト・レビュー観点を1枚にまとめ、共有フォルダに置く | 5 |

### アイデア別の詳細

**1. 「悪いスライド」から始める診断デモ（10分）**
- 当日: 主催者が「テーマだけ渡してAIに一発で作らせたスライド」を投影し、見た目は整うが中身が薄い点を参加者が指摘する。指摘を黒板に集約し、これが後のレビュー観点になる。
- 体験: 欠陥を探す側に回る / 持ち帰り: 「中身が薄いスライド」の典型パターン一覧
- 対処する仮説: H1, H3 / リスク: 例が作り物に見える → 実際に社内で見かける型を使う / 準備: 小（主催者、30分）

**2. 持ち込みテーマ制の実務ワーク（35分）**
- 当日: 事前に「近日中に実際に作る資料のテーマ」を各自1行で決めてもらい、当日それを使う。AIには「聴き手・目的・伝えたい1文」を先に渡させ、構成案→本文→スライド化の順で作る。
- 体験: 自分の実案件がその場で形になる / 持ち帰り: 聴き手と目的を先に固定する指示の書き方
- 対処する仮説: H3, H4 / リスク: 機密情報を入力する → 「社外に出せる範囲に丸めたテーマ」で行うルールを冒頭で明示 / 準備: 小（開催案内に1行追加）

**3. 相互・別モデル敵対的レビュー（25分）**
- 当日: 2人1組で成果物を交換し、作成者とは別のAIセッション（使えるなら別のAI）に「この資料の最も弱い点を3つ、引用付きで指摘せよ。最も強い点も1つ」と指示する。指摘を受けて各自が直す。「正しい指摘は直す／当たらない指摘は直さず理由を書く」を守る。
- 体験: 自分の資料が他者とAIに批評される / 持ち帰り: 作成とレビューを分けるレビュープロンプト
- 対処する仮説: H1, H2 / リスク: 別モデルが使えない参加者がいる → 別セッションでも可とし、効果は落ちると明示 / 準備: 中（レビュープロンプト雛形、主催者）

**4. Loop Engineering を「ワーク2の自動化」として紹介（20分）**
- 当日: ワーク2を「人間がやった反復」と位置づけ、IssueからPRまでの流れ、レビュアーを別モデルにする理由、停止条件を実物のPRで示す。今回の議論の成果物（answer.md、寄与比率、攻撃に耐えた主張／崩れた主張）を見せる。当日の実行はしない（1ラウンド約USD 1.44のため）。
- 体験: 自分たちの手作業が仕組みになる様子を見る / 持ち帰り: 反復作業にレビュー役と終了条件を付ける設計の考え方
- 対処する仮説: H1, H2 / リスク: 抽象的で聞き流される → ワーク直後に置き、実物のPRを見せる / 準備: 中（デモ用PRの整理、主催者）

**5. 持ち帰りカードと共有置き場（12分）**
- 当日: 各自が「自分の業務で明日使うプロンプトとレビュー観点」を1枚にまとめ、社内の共有場所に置く。次回冒頭でその使われ方を共有する。
- 体験: 他者のカードを読んで盗む / 持ち帰り: すぐ使えるテンプレート集と、次回に来る理由
- 対処する仮説: H4 / リスク: 置かれても読まれない → 次回冒頭に「使ってみた人」の枠を設ける / 準備: 小

**6. 次回の題材をその場で募る（8分）**
- 当日: 付箋かフォームで「次回やってほしいこと／持ち込みたい悩み」を集める。
- 体験: 自分の悩みが次回の題材になる / 持ち帰り: なし（運営のため） / 対処する仮説: H2, H4 / リスク: 要望が散る → 上位1〜2件だけ扱う / 準備: 小

### 費用ゼロの根拠
参加者が日常的に使っているAIアカウントと社内の既存ツールのみで行い、追加購入・環境構築・ローカルLLMは使わない。Loop Engineering部分は事前に走らせた結果を見せるだけで、当日のAPI実行はない。

## 評価基準への適合

- **c1**: アイデアは6つあり、すべてに「当日」の進め方を書いた。
- **c2**: タイムテーブルは合計120分。追加費用ゼロの根拠を明記し、当日はAPIを呼ばない。
- **c3**: 仮説 H1〜H4 を表にし、各アイデアに対処仮説を付けた。
- **c4**: 各アイデアに「体験」「持ち帰り」を1行ずつ書いた（アイデア6の持ち帰りは運営目的のため「なし」と明記）。
- **c5**: 新規性は「作る→別AIに攻撃させる→直す」という、AI利用が当たり前の人でも普段やっていない工程にある。Loop Engineering はその自動化として接続した。
- **c6**: 各アイデアにリスクと準備量・担当を書いた。

## トレードオフ

- 初歩的な使い方を教える時間を捨てている。初心者が置いていかれる可能性がある。
- 講義時間を削ってワークに寄せたため、Loop Engineering の技術的な詳細は浅くなる。
- 持ち込みテーマ制は、機密を理由に参加者が題材を出せない場合に成立しにくい。
- 集客施策は対象外なので、告知の弱さが原因なら本案では解けない。

## 想定される失敗モード

1. ワーク1で時間を使い切り、ワーク2が圧縮されて「攻撃させて直す」体験が薄くなる。
2. ペア作業が気まずく、交換を拒む参加者が出る（匿名の資料交換にすれば緩和するが、持ち込み制の利点が減る）。
3. 参加者の使えるAIが揃わず、「別モデルでレビュー」が成立しない人が出る。
4. 80分以降の Loop Engineering 紹介が、疲れた状態の聞き流しになる。

## 前提と未確認事項

- 開催形態（対面/オンライン）が不明。ペア交換は両方で可能と仮定したが、対面前提の運営が混ざっている。
- 参加者全員が複数のAIセッションを使えるかは不明。使えない場合の代替は「別セッション」としか書けていない。
- スキル分布が不明。初心者向けの補助は設計していない。
- 参加者が減った原因は仮説であり、アンケート等の実測はない。
- 社内の共有場所（フォルダ等）があるかは未確認。
- 1人35分で実用品質のスライドが作れるかは未検証。
