## 案の要旨

第4回を「講義」ではなく「その場で作って、AIに攻撃させて、直す」ワークショップに作り替える。参加者は丸めた実在テーマでAIにスライドを作らせ、別のAIセッションと隣の人の目で敵対的レビューをかけて直す。「作る側とレビューする側を分ける」構造がそのまま Loop Engineering の中核なので、紹介は説明ではなく体験の延長に置き、主催者が事前に走らせた合議の結果（今回の議論自体）を素材にする。

改稿で、(1) スライド化の出力手段を固定、(2) 時間が溢れたときの削る順序を明記、(3) 開催形態・機密・共有場所の前提を条件分岐として明示、(4) アイデア6を独立アイデアとして数えるのをやめ、アイデアは5つに整理した。

## 設計

### 減少の原因仮説（c3）

| ID | 仮説 | 根拠 |
| --- | --- | --- |
| H1 | 初歩の使い方は既知になり、新規性が消えた | 現在はAI利用が当たり前（ブリーフ） |
| H2 | 第3回が第2回の再演で、「また同じ」と思われた | 第2回と第3回はほぼ同内容 |
| H3 | 座学中心で受け身。自分の仕事に直結する成果が残らない | 仮説（ブリーフ記載） |
| H4 | 参加しても翌日の仕事が変わらず、次回に来る動機がない | 推測 |

### 前提の固定（未確認事項を条件で潰す）

- **出力手段**: スライド化は「AIに、1枚1メッセージの見出し＋本文＋話すこと（ノート）をスライド単位のMarkdownで出させる」までを必須とする。PowerPointへの流し込み（各自の使える変換手段・貼り付け）は「できた人だけ」の任意ステップとし、評価は**スライド構成の中身**で行う。ツール依存で詰まる人を出さないため、見た目の仕上げはこの回の対象外とする。
- **開催形態**: 対面ならペアで画面またはテキストを見せ合う。オンラインなら、チャットにテキストを貼って相手に渡す（ファイル授受は不要）。奇数人数は3人組にする。
- **機密**: 題材は「社外に出せる範囲に丸めたテーマ」。さらに、**隣の人に見せる内容も同じ線引き**とし、冒頭で明示する。丸めて具体性が落ちた場合は、翌日に自分の環境で実データへ差し替える前提とする。
- **AI環境**: 使えるなら別のAI、無理なら別セッション。使えない人は、隣の人のアカウント画面で同席して実施する。

### タイムテーブル（合計120分、挨拶〜撤収）

| 分 | 内容 | アイデア |
| --- | --- | --- |
| 0–5 | 挨拶・今日のゴール提示 | — |
| 5–15 | 主催者デモ: 「AI一発スライド」の悪い例を見せ、何が問題かを参加者に言わせる | 1 |
| 15–50 | ワーク1: 持ち込みテーマで、構成案→スライド単位Markdownを作る（35分） | 2 |
| 50–75 | ワーク2: 相手に渡して別AIに敵対的レビューさせ、指摘を取捨選択して直す（25分） | 3 |
| 75–80 | 休憩 | — |
| 80–100 | Loop Engineering紹介（ワーク参加つき・下記） | 4 |
| 100–112 | 持ち帰りカード作成 | 5 |
| 112–120 | 次回の題材募集・アンケート・撤収 | 5 |

**時間が溢れたときの削る順序**: ①ワーク1は30分で打ち切り（残りは翌日の宿題）→ ②持ち帰りカードを12分から8分へ → ③Loop Engineering紹介を20分から15分へ。**ワーク2（攻撃させて直す）は削らない。** この回の新規性の核だから。

### アイデア別の詳細

**1. 「悪いスライド」から始める診断デモ（10分）**
- 当日: 主催者が「テーマだけ渡してAIに一発で作らせたスライド」を投影し、中身が薄い点を参加者が指摘する。指摘を集約し、後のレビュー観点にする。
- 体験: 欠陥を探す側に回る / 持ち帰り: 「中身が薄いスライド」の典型パターン一覧
- 対処する仮説: H1, H3 / リスク: 例が作り物に見える → 実際に社内で見かける型を使う / 準備: 小（主催者、30分）

**2. 持ち込みテーマ制の実務ワーク（35分）**
- 当日: 事前に「近日中に作る資料のテーマ」を各自1行で決めてもらい、それを使う。AIには「聴き手・目的・伝えたい1文」を先に渡させ、構成案→本文→スライド単位Markdownの順で作る。
- 体験: 自分の案件がその場で形になる / 持ち帰り: 聴き手と目的を先に固定する指示の書き方
- 対処する仮説: H3, H4 / リスク: テーマが出ない人が多い → 当日に主催者が用意した例題3つから選べるようにする（その場合の実務直結度は落ちると明示） / 準備: 小（開催案内に1行追加＋例題3つ、主催者）

**3. 相互・別モデル敵対的レビュー（25分）**
- 当日: 2人1組で成果物を渡し、作成者とは別のAIセッションに「この資料の最も弱い点を3つ、引用付きで指摘せよ。最も強い点も1つ」と指示する。**指摘は当たっていないこともあるので、「正しい指摘は直す／当たらない指摘は直さず理由を書く」を守らせる**（誤指摘をそのまま採用する事故を防ぐ。参加者が見極めに迷う場合は、隣の人と2人で判断する）。
- 体験: 自分の資料が他者とAIに批評される / 持ち帰り: 作成とレビューを分けるレビュープロンプト
- 対処する仮説: H1, H2 / リスク: 別モデルが使えない人がいる → 別セッションでも可、効果は落ちると明示 / 準備: 中（レビュープロンプト雛形、主催者）

**4. Loop Engineering を「ワーク2の自動化」として紹介（20分）**
- 当日: ワーク2を「人間がやった反復」と位置づけ、IssueからPRまでの流れ、レビュアーを別モデルにする理由、停止条件を実物のPRで示す。今回の議論の成果物（answer.md、寄与比率、攻撃に耐えた主張／崩れた主張）を見せる。**受け身を避けるため、途中で2回、2分の隣人ワークを入れる**（「このPRで、あなたならどの主張を疑うか」「自分の業務で、レビュー役と終了条件を付けるならどこか」）。当日の実行はしない（1ラウンド約USD 1.44のため）。
- 体験: 自分たちの手作業が仕組みになる様子を見て、自分の業務に当てはめる / 持ち帰り: 反復作業にレビュー役と終了条件を付ける設計の考え方
- 対処する仮説: H1, H2, H3 / リスク: 抽象的で聞き流される → ワーク直後に置き、隣人ワークを挟む / 準備: 中（デモ用PRの整理、主催者）

**5. 持ち帰りカード・共有置き場・次回題材募集（20分）**
- 当日: 各自が「自分の業務で明日使うプロンプトとレビュー観点」を1枚にまとめる。置き場は**事前に主催者が1か所作って権限を開けておく**（作れない場合は、会の終了後に主催者が集約するため、チャットへの貼り付けで代替する）。最後に付箋かフォームで「次回までに試したいこと」を集める。次回冒頭で「使ってみた人」の枠を設ける。
- 体験: 他者のカードを読んで盗む / 持ち帰り: すぐ使えるテンプレート集と、次回に来る理由
- 対処する仮説: H4 / リスク: 置かれても読まれない → 次回冒頭に共有枠 / 準備: 小（置き場の作成と権限設定、主催者、前日までに）
- 旧アイデア6（次回題材の募集）は、今回テーマの持ち帰りに寄与しないため独立アイデアから外し、この5の締めに畳んだ。

### 費用ゼロの根拠
参加者が日常的に使っているAIアカウントと社内の既存ツールのみで行い、追加購入・環境構築・ローカルLLMは使わない。主催者側のLoop Engineering部分は事前実行の結果を見せるだけで、当日の主催者側API実行はない。参加者側のAI利用は、各自が既に持つアカウントの範囲に限る。使えない人は同席ペアで対応する。

## 評価基準への適合

- **c1**: アイデアは5つで、すべてに「当日」の進め方を書いた。
- **c2**: 合計120分。追加費用ゼロの根拠と、時間が溢れたときの削る順序を明記した。
- **c3**: 仮説 H1〜H4 を表にし、各アイデアに対処仮説を付けた。
- **c4**: 5アイデアすべてに「体験」「持ち帰り」を1行ずつ書いた。
- **c5**: 新規性は「作る→別AIに攻撃させる→直す」という、AI利用が当たり前の人でも普段やっていない工程にある。Loop Engineering はその自動化として接続した。
- **c6**: 各アイデアにリスクと準備量・担当を書いた。

## トレードオフ

- 初歩的な使い方を教える時間を捨てている。初心者が置いていかれる可能性がある。
- スライド化をMarkdown出力までに絞ったため、「仕事で使えるPowerPointの見た目」の仕上げは扱わない。
- Loop Engineering の技術的な詳細は浅くなる。
- 持ち込みテーマ制は、機密を理由に題材が出せない人には成立しにくい（例題で代替するが、実務直結度は落ちる）。
- 集客施策は対象外なので、告知の弱さが原因なら本案では解けない。

## 想定される失敗モード

1. ワーク1で時間を使い切る → 削る順序に従い、ワーク2は守る。
2. ペア作業が気まずく交換を拒む人が出る → 匿名の資料交換にすると緩和するが、持ち込み制の利点が減る。
3. 使えるAIが揃わず「別モデルでレビュー」が成立しない人が出る。
4. 80分以降の紹介が、疲れた状態の聞き流しになる → 隣人ワークで緩和するが、完全には防げない。

## 改稿で変えた点

1. **スライド化の手順を固定した。** 「スライド単位のMarkdown」までを必須、PowerPoint流し込みを任意にして、ツール依存で詰まる人が次工程に進めない問題を潰した。
2. **時間が溢れたときの削る順序を追加した。** ワーク2は守り、ワーク1・カード・紹介を削る。
3. **開催形態・機密・AI環境の前提を条件分岐として本文に入れた。** オンライン時の受け渡し、奇数人数、隣人に見せる線引き、AIが使えない人の同席を書いた。
4. **アイデア6を独立アイデアから外し、アイデア5に畳んだ。** c4の「持ち帰りなし」問題と、今回テーマに寄与しない指摘の両方を解消した。アイデア数は6から5になった。
5. **Loop Engineering紹介に隣人ワークを2回入れた。** 自案が挙げる仮説H3（座学で受け身）との矛盾を直した。

## 反論

- **「スライド化の具体的なツールが定義されていない」** のうち、特定ツール（VBA等）を指定すべきという部分は受け入れなかった。参加者の環境が不明なため、特定ツールを指定すると別の依存を作る。代わりにMarkdown出力に絞った。
- **「当日はAPIを呼ばない」が参加者側のAI利用と矛盾する** という指摘は半分だけ受け入れた。主催者側のAPI実行がないという意味に限定する文言に直したが、参加者が日常的に使うアカウント内で完結するという費用ゼロの根拠は変えていない。
- **「準備の担当が書かれていない」** は、アイデア1〜5の担当を明記して対応した。争点は残っていない。
- **「ワーク1で時間が足りず次工程に進めない」** は、案を直した。ただし、35分という枠そのものは変えていない。打ち切りと宿題への切り替えで吸収できる範囲だと判断した。
