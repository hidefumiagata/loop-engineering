## 案の要旨

第4回は「AIでスライドを作る会」ではなく、「業務品質のスライドを作るために、仕様化・生成・レビュー・改稿の小さなLoopを体験する会」として設計する。PowerPointは1枚の実用スライドに絞り、Loop Engineeringはその考え方をスライド作成にも転用できる型として紹介する。参加者は、完成デッキよりも「明日から使えるプロンプト、受入基準、レビュー観点、作業手順」を持ち帰る。

## 設計

### 全体コンセプト

結論は、**「1枚スライドを題材にした、人間参加型のミニLoop」**にする。

```
業務目的
  ↓
スライド仕様書
  ↓
AIへの生成依頼
  ↓
レビュー観点で赤入れ
  ↓
改稿
  ↓
PowerPoint化
  ↓
自分の業務への転用メモ
```

参加者全員が有料APIやLoop Engineering本体を回すのではなく、主催者が事前に用意した素材を使う。これにより、追加費用ゼロ、2時間以内、開催形態不明でも成立する構成にする。

### 事前に主催者が用意するもの

追加費用をかけず、既存の社内ツール・既存のAI利用環境・手元資料だけで作る前提。

1. **題材スライド**
   - テーマ例：この第4回そのものを説明する「Claude勉強会 第4回の企画提案」1枚
   - または、社内で機密性の低い一般的な業務テーマ1枚
   - 「AIが作りがちな薄いBefore版」と「レビュー後のAfter版」を用意する

2. **スライド仕様書テンプレート**
   - 聴衆
   - その人に取ってほしい行動
   - 1枚で伝える主張
   - 根拠・制約・使ってはいけない表現
   - 成功条件、受入基準

3. **プロンプト雛形**
   - 仕様を質問させるプロンプト
   - スライド構成を出させるプロンプト
   - PowerPoint貼り付け用に、タイトル・メッセージ・箇条書き・図解案・発表者ノートを分けて出させるプロンプト
   - レビュー専用プロンプト

4. **レビュー観点シート**
   - 目的に合っているか
   - 読み手が次に何をすればよいか分かるか
   - 根拠があるか
   - 1スライド1メッセージになっているか
   - ありがちなAI臭さ、抽象語、既視感が残っていないか
   - PowerPointとして視線誘導できるか

5. **Loop Engineering紹介用の静的資料**
   - GitHub Issueに目的を書く
   - 受入基準を作る
   - ワーカーが作業する
   - 別モデルがレビューする
   - 反復してPRにする
   - という流れを、スクリーンショットまたは図で見せる  
   - 当日は参加者全員にAPI実行させない

### 参加者減少の原因仮説

| 仮説ID | 仮説 |
|---|---|
| H1 | AI利用が当たり前になり、初歩的な使い方紹介だけでは新鮮味が落ちた |
| H2 | 第2回と第3回が近い内容で、再演感が出た |
| H3 | 座学中心だと受け身になり、参加後の変化を感じにくい |
| H4 | AI出力が「それっぽいが薄い」ため、業務品質にする方法への関心が残っている |
| H5 | Loop Engineeringは面白いが、技術基盤の説明だけだと自分の業務への転用が見えにくい |

### 具体アイデア

#### アイデア1：Before/After投票で「AIスライドの物足りなさ」を言語化する

- **当日何をするか**  
  主催者が、AIで作ったようなBeforeスライドと、レビュー後のAfterスライドを見せる。参加者は「どちらを上司・顧客・チームに出せるか」「Beforeのどこが弱いか」を投票または挙手で答える。

- **体験内容**  
  見た目ではなく、目的・主張・根拠・次アクションの有無でスライドを見る。

- **持ち帰り要素**  
  AIスライドをそのまま使わず、業務品質にするための評価観点。

- **対処する仮説**  
  H1、H4。

- **リスク**  
  Beforeが露骨に悪すぎると学びが浅くなる。Afterが立派すぎると「自分には無理」と感じられる。

- **事前準備量・担当**  
  主催者がBefore/After各1枚を作る。準備は中程度。

#### アイデア2：スライド仕様書を書く

- **当日何をするか**  
  3〜4人の小グループで、題材スライドについて「聴衆」「取ってほしい行動」「1枚の主張」「根拠」「受入基準」を埋める。発表は各グループ30秒程度に絞る。

- **体験内容**  
  AIに投げる前に、スライドの成功条件を人間が定義する。

- **持ち帰り要素**  
  明日から使える「AIに依頼する前の入力仕様」の型。

- **対処する仮説**  
  H1、H3、H4。

- **リスク**  
  議論が抽象化しすぎると時間を使う。テンプレートの項目が多すぎると埋めるだけになる。

- **事前準備量・担当**  
  主催者がA4一枚または共有ドキュメント一枚のテンプレートを作る。準備は小〜中。

#### アイデア3：プロンプト駅伝で「作らせ方」を分解する

- **当日何をするか**  
  各グループが仕様書をもとに、AIへの依頼文を作る。依頼は一発生成ではなく、以下の順に分ける。  
  1. 不足情報を質問させる  
  2. スライドの主張と構成案を出させる  
  3. PowerPoint貼り付け用に、タイトル・本文・図解案・発表者ノートを分けさせる  
  4. 自己レビューさせる

- **体験内容**  
  「よい感じのスライドを作って」ではなく、業務用の成果物に分解して依頼する。

- **持ち帰り要素**  
  PowerPoint作成に使えるプロンプトの順番と雛形。

- **対処する仮説**  
  H1、H2、H3、H4。

- **リスク**  
  参加者全員がAIを実行できない可能性がある。そこで、当日はプロンプト作成までを必須にし、実行結果は主催者の事前出力を使う。

- **事前準備量・担当**  
  主催者がプロンプト雛形と事前出力を用意する。準備は中程度。

#### アイデア4：レビュー赤入れで「受入基準」を使う

- **当日何をするか**  
  主催者がAI出力例を配る。参加者はレビュー観点シートを使い、「このまま業務に出せない理由」と「AIに返す改善指示」を書く。最後に主催者が、赤入れを反映した改稿版を見せる。

- **体験内容**  
  生成AIを作業者として扱い、人間がレビュアーになる。

- **持ち帰り要素**  
  AI出力をレビューするチェックリストと、改善指示の書き方。

- **対処する仮説**  
  H3、H4。

- **リスク**  
  批評だけで終わると楽しいが実務に戻らない。必ず「AIへの返し方」まで書かせる。

- **事前準備量・担当**  
  主催者がレビュー観点シートと出力例を用意する。準備は小〜中。

#### アイデア5：Loop Engineeringを「スライド作成の型」として紹介する

- **当日何をするか**  
  Loop Engineeringそのものを長く説明するのではなく、次の対応関係で紹介する。  
  - GitHub Issueの目的 = スライド仕様書  
  - 受入基準 = スライドのレビュー観点  
  - ワーカーLLM = 初稿作成  
  - 別モデルレビュー = 赤入れ  
  - 反復 = 改稿  
  - PR = 使える成果物

- **体験内容**  
  Loop Engineeringを、技術基盤ではなく「AIに仕事を任せるときの運用設計」として見る。

- **持ち帰り要素**  
  自分の業務でも、AI作業に目的・受入基準・別視点レビューを入れるという考え方。

- **対処する仮説**  
  H2、H5。

- **リスク**  
  GitHubやPRの話に寄りすぎると非エンジニアが置いていかれる。画面は最小限にし、構造を図で説明する。

- **事前準備量・担当**  
  主催者が既存のLoop Engineering実行結果、または今回の議論の生成物を静的資料にする。準備は中程度。追加API実行はしない。

#### アイデア6：人間ミニLoopを1回だけ回す

- **当日何をするか**  
  1つのグループ内で、作成役・レビュー役・統合役を決める。作成役がスライド案を1分で説明し、レビュー役が敵対的に弱点を指摘し、統合役が最終版のメッセージにまとめる。

- **体験内容**  
  複数エージェントの合議・レビュー・統合を、人間で短時間に体感する。

- **持ち帰り要素**  
  AIに複数役割を与えるときの設計、特に「作る役」と「見る役」を分ける重要性。

- **対処する仮説**  
  H3、H5。

- **リスク**  
  レビューが人格批判のように見えると場が冷える。対象は人ではなく成果物である、と冒頭に明示する。

- **事前準備量・担当**  
  主催者が役割カードを3種類用意する。準備は小。

#### アイデア7：明日使う宣言カードを作る

- **当日何をするか**  
  最後に各自が、自分の業務で使うテーマを1つ選び、次の3行を書く。  
  1. 作りたいスライド  
  2. 読み手に取ってほしい行動  
  3. AIに最初に投げる依頼文

- **体験内容**  
  勉強会の題材から、自分の業務テーマへ置き換える。

- **持ち帰り要素**  
  翌日にそのまま使える最初のプロンプト、またはIssueの種。

- **対処する仮説**  
  H3、H4、H5。

- **リスク**  
  時間切れで雑になる。終了8分前には必ず始める。

- **事前準備量・担当**  
  主催者が1枚の記入フォーマットを用意する。準備は小。

## 評価基準への適合

**c1：実行可能なアイデアが5つ以上あり、具体的な進め方があること**  
アイデア1〜7の7件を提示し、それぞれに「当日何をするか」を明記した。各アイデアは投票、仕様書作成、プロンプト作成、レビュー、Loop紹介、ミニLoop、転用カードという実施単位に分かれている。

**c2：制約を満たし、2時間以内に収まること**  
120分のタイムテーブルに全アイデアを入れた。参加者全員が有料APIやローカルLLMを使う構成ではなく、主催者の事前資料と既存環境で進めるため、追加費用ゼロを前提にできる。

**c3：参加者減少の原因仮説とアイデアの対応**  
H1〜H5として、初歩ネタの陳腐化、再演感、受け身化、AIスライドの薄さ、Loopの転用しにくさを仮説化した。各アイデアに、どの仮説へ対応するかを明記した。

**c4：体験内容と業務で使えるスキル・知見**  
各アイデアに「体験内容」と「持ち帰り要素」を1行ずつ記載した。持ち帰りは、プロンプト雛形、仕様書、レビュー観点、Loopの役割分担、自分の業務への最初の依頼文にしている。

**c5：PowerPoint作成とLoop Engineering紹介を活かし、新規性があること**  
PowerPoint作成は、単なる生成ではなく「業務品質にするための仕様・レビュー・改稿」に焦点を置いた。Loop Engineeringは別テーマとして切り離さず、スライド作成にも使える作業設計として接続するため、AI利用が当たり前になった参加者にも新しい見方を提供する。

**c6：リスクと事前準備の量・担当**  
各アイデアに失敗しやすい点と、主催者が準備するものを記載した。準備量は小〜中に抑え、当日のライブ実行に依存しない設計にした。

## トレードオフ

この案は、参加者全員がその場でAIを動かして完全なPowerPointデッキを作る体験を犠牲にしている。代わりに、1枚スライドに絞り、仕様化・レビュー・改稿の型を持ち帰ることを優先する。

また、Loop Engineeringの技術的な深掘りは抑える。GitHub routine、他社LLMレビュー、PR生成の詳細実装よりも、「目的、受入基準、別モデルレビュー、反復」という運用思想の理解を優先する。

さらに、集客そのものを増やす施策は扱わない。告知文や社内広報ではなく、参加した人が「次も何か持ち帰れそう」と感じる会の構造に限定している。

## 想定される失敗モード

1. **ライブAI実行や画面投影がうまくいかない**  
   当日のネットワーク、AI利用権限、会場設備が不明なため起こりうる。事前出力、PDF、スクリーンショットで進行できるようにする。

2. **参加者のスキル差で一部の人が黙る**  
   AIに慣れた人だけが話す可能性がある。仕様書係、レビュー係、統合係など役割を分け、AI操作ではなく判断に参加できるようにする。

3. **Loop Engineering紹介が技術説明に寄りすぎる**  
   GitHubやPRの話が長くなると、PowerPoint作成テーマとの接続が弱くなる。説明は20分以内にし、スライド作成のLoopとの対応表で見せる。

4. **題材スライドが参加者の業務から遠い**  
   題材に関心が持てないと、学びが抽象化する。最後に必ず自分の業務テーマへ置き換える時間を取り、転用カードを完成させる。

## 前提と未確認事項

- 開催形態が対面、オンライン、併用のどれかは不明である。そのため、紙でも共有ドキュメントでも成立する設計にした。
- 参加者がClaude、PowerPoint、その他AIツールを当日使えるかは不明である。全員がツールを実行できる前提にはしていない。
- 主催者が既存のAI利用環境で事前にスライド例やプロンプト出力を用意できるかは未確認である。追加費用を避けるため、既に使える範囲で作る前提にしている。
- 会場に投影設備、ホワイトボード、共有ドキュメント環境があるかは不明である。最低限、画面共有またはPDF配布ができる前提を置いた。
- 題材にできる社内情報の機密レベルは不明である。実施時は、機密性の低い題材か、この勉強会企画そのものを素材にする必要がある。
- 参加人数は第3回実績の約8人から、第1回相当の約30人まで変動しうる。小グループ数を変えれば成立する想定だが、30人を超えた場合の進行負荷は別途調整が必要である。
