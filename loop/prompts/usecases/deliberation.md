# 用途: 合議（panel モード）

3つのAIエージェント（Claude / ChatGPT / Gemini）が議論して、1つの結論を出す。

```
1. propose     3者がそれぞれ意見を出す
2. challenge   自分以外の案を敵対的にレビューする
3. revise      指摘を受けて各自が自分の案の精度を高める
4. synthesize  Claude の別エージェントが3つの回答をまとめ、3LLMとしての結論を出す
```

**採点はしない。** 評価の役割は敵対的レビューが担う。
点数は「どれが良いか」しか言わないが、敵対的レビューは「どこが壊れるか」を言う。
後者のほうが、改稿にも統合にも使える。

成果物は `answer.md`。**読む場所は PR である。Issue に成果物を貼らない。**

```
projects/NNNN-slug/
  brief.md  criteria.json
  proposals/
    .authors.json           対応表。攻撃者・改稿者・統合役には渡さない
    A.md  B.md  C.md        初稿
    A.v2.md B.v2.md C.v2.md 改稿後。統合役はこちらを読む
  challenges/by-claude.json by-gemini.json by-openai.json
  answer.md  provenance.json  synthesis-check.json
  journal/
```

## brief.md — 共有ブリーフ（Claude が書く）

**これが議論の土台である。**
Gemini と OpenAI はこの実行環境のファイルもコマンドもWebも触れない。
Claude だけが事実を知っている状態で議論させると、Claude の案が有利になるだけで議論にならない。

```
---
title: <議論したいこと>
issue: <番号>
round: <ラウンド番号>
updated: <YYYY-MM-DD>
---

## 議論したいこと
（1段落。何について結論を出したいのか）

## 制約
（変えられない条件）

## 前提事実
（★最重要。Claude が調べた・読んだ事実をここに展開する。
  関連コードの抜粋、ドキュメントの引用（出典URL付き）、実測値。
  ここに無いことは他の2者には存在しない）

## 評価基準
| ID | 基準 | 重み | 満たしたと判断する根拠 |
| --- | --- | --- | --- |
| c1 | ... | 3 | ... |

（重み: 3=これが無ければ失敗 / 2=重要 / 1=あれば良い。重み3は 2〜4 件）

## 検討の対象外
（今回は決めないこと）
```

基準は `criteria.json`（`[{"id","text","weight"}]`）にも書き出す。
**敵対的レビューは「どの基準を満たせなくなるか」で攻撃する。** 基準が曖昧だと攻撃も曖昧になる。

## 1. propose — 3者が意見を出す

順序の規律を守る。git 履歴が独立性の証跡になる。

1. Claude が自案を `proposals/claude.md` に書き、**それだけを単独でコミットして push する**
2. その後で `gemini:propose` と `openai:propose` を呼ぶ
3. 3案を A/B/C に**ランダム割り当て**して匿名化。対応表は `.authors.json` に分離
4. 匿名化前のファイルは削除する。`*.meta.json` は一緒にリネームして残す

**3案揃わなければ続行しない**（`min_proposers: 3`）。
敵対的レビューは「自分以外の2案を攻撃する」形なので、2案だと各自が1案しか攻撃できず、
攻撃の重なりが消えて検証にならない。

## 2. challenge — 自分以外を敵対的レビュー

**各者には「自分が書いた案を除いた2案」だけを渡す。**
自分の案を攻撃させると、自己批判か自己弁護のどちらかになり、どちらも議論にならない。
どれが本人の案かは `.authors.json` で呼び出し側が特定する。**本人には伝えない。**

`loop/prompts/roles/challenger.md` と `challenge` スキーマを使う。攻撃の規律:

- **引用のない攻撃は無効。** `claim` に案の記述を引用し、`why` に反例・条件・見落としを書く
- **`strongest_point` は必須。** 攻撃対象であっても最も強い点を認めさせる。
  全否定は批評の放棄であり、統合役が「何を残すべきか」を判断できなくなる。
  攻撃者自身も案を書いた当事者なので、他案を一律に潰す動機を構造的に持っている。
  それが出力に現れていないことをこの欄で示させる
- `severity` は `致命的` / `要修正` / `軽微`。全案を同じにしない

攻撃者が欠けても**停止しない**。欠けた事実を記録して進む。
提案と違い、攻撃の欠落は議論を無効にしない（その案への攻撃が1件減るだけ）。

## 3. revise — 指摘を受けて各自が改稿

**各者には「自分の案」と「自分の案への指摘」だけを渡す。他案は渡さない。**
他案を見せると寄せにいってしまい、3つの独立した答えという前提が崩れる。
誰の指摘かも伏せ、`批評者1` `批評者2` として示す。

`loop/prompts/roles/reviser.md` を使う。スキーマは使わず、改稿後の案を Markdown で返させる。

**迎合させない。** 指摘は当たっていないこともある。改稿者には3通りの扱いを課している。

| 判断 | やること |
| --- | --- |
| 正しい | 案を直す。前提が崩れているなら設計ごと変える |
| 部分的に正しい | 成り立つ範囲を明示して条件付ける |
| **誤り** | **直さない。**「反論」節に、なぜ当たらないかを根拠付きで書く |

改稿が取得できなかった案は、初稿をそのまま `.v2.md` にコピーする。
欠けたままにすると統合役の入力が揃わない。コピーした事実を `journal` に書く。

## 4. synthesize — 別エージェントが結論をまとめる

**Claude 本体は書かない。** `panel-synthesizer` サブエージェントを起動する。

3案のうち1つは本体が書いている。本体が統合すると自案を土台にする動機が構造的に残る。
サブエージェントは**独立した文脈で起動され、どれが本体の案かを知らない**。
`.authors.json` は渡さず、示唆する発言もしない。知らないまま読むことがこの工程の価値である。

渡すもの: `brief.md` / `proposals/*.v2.md`（**改稿後**）/ `challenges/by-*.json` / 出力先パス。
このサブエージェントには Web ツールを与えていない。入力に無いことは書かせない。

### answer.md の必須節

| 節 | なぜ必須か |
| --- | --- |
| 結論 / 本論 | 成果物の主体 |
| **3者が一致した点** | 独立に書かれ、互いに攻撃され、それでも残った合意。最も確度が高い |
| **攻撃に耐えた主張** | 指摘されても改稿で反論され残った主張。議論を経た証跡 |
| **攻撃で崩れた主張** | 何が否定されたかは、何が残ったかと同じだけ価値がある |
| **見解が割れた点** | 最後まで一致しなかった論点。**無理に一本化しない** |
| **この結論の限界** | どの案も触れていない論点、他社2者が環境に触れていないこと、warnings 全件 |

### 偏りの機械的な確認

`node loop/bin/synthesis-check.mjs --dir projects/<n>-<slug>` を実行する。
統合役が宣言した `provenance.json`（結論の要素 → 由来する案）から寄与比率を算出し、
均等配分の1.6倍を超えたら警告する。

**警告が出たら、サブエージェントに差し戻して書き直させる。**
本体が自分で直してはならない。直した時点で別エージェントである意味が消える。

## 終了条件

- `answer.md` ができ、偏りの警告が無ければ完了
- **PR を作る。** PR 本文に結論の要旨・寄与比率・severity を載せ、
  マージする人が「何が結論か」「偏っていないか」「どの案が攻撃に耐えたか」を
  PR 画面だけで判断できるようにする
- **Issue に結論を貼らない。** Issue は目的と状態の置き場
- **マージはしない。** main に入れるかどうかは人間が決める
- 人間が Issue に追加の論点や反証を書き `loop:go` を付けたら、
  次の run がそれを `brief.md` の「前提事実」に取り込んで propose からやり直す

`require_human_decision` は `false`。承認待ちで止めない。
