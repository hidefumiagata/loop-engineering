# 用途: 技術調査

成果物は `report.md`。過程は `findings/` と `journal/`、出典は `sources.md`。

**調査は3段構成で行う。公式情報と非公式情報を別々に集め、第三者が突き合わせる。**

```
1. あなた（loop-engine 本体）    公式サイト・公式ドキュメントだけを調べる
                                  → findings/official.md
2. サブエージェント research-community   公式以外（ブログ・実装例）だけを調べる
                                  → findings/community.md
3. サブエージェント research-reconcile   1と2を突き合わせてレポートを書く
                                  → report.md
```

## なぜ分けるのか

1人のエージェントが公式と非公式を同時に読むと、両者が頭の中で混ざる。
「公式に書いてあった気がするが、実はブログの記述だった」という取り違えが起き、
しかも**後から検証できない**。文脈を分けておけば、突き合わせる相手が残る。

3番目のエージェントには **Web を引く手段を与えていない。** これは意図的で、
突き合わせ役が追加調査で穴を埋めてしまうと、1と2の結果を照合する意味が消えるため。

---

## 段階1: 公式情報の調査（あなたが行う）

**公式サイト・公式ドキュメントだけを見る。** ブログや第三者の記事は読まない。

公式とみなすもの:
- 製品・サービスの提供元が運営するドキュメントサイト、価格表、リリースノート、ステータスページ
- 提供元の organization が持つ GitHub リポジトリ、その README と仕様
- 提供元が出した公式ブログ・アナウンス（ただし「公式ブログ」であることを明記する）
- RFC、標準化団体の仕様書

公式でないもの（ここでは読まない）:
- 個人・他社の技術ブログ、Qiita・Zenn・Medium などの投稿
- Q&Aサイト、フォーラム
- 第三者が書いた解説記事・まとめサイト

`projects/<slug>/findings/official.md` に書く。

```markdown
# 公式情報の調査結果

## 調査した範囲と限界
（どの公式サイトを見たか。探したが公式には記述が無かった論点もここに書く）

## 見つかったこと

### <論点1>
- **記述**: （公式が何と言っているか。数値は数値のまま。必要なら短く引用する）
- **出典**: [タイトル](URL) — 取得日 YYYY-MM-DD
- **種別**: ドキュメント / 価格表 / リリースノート / 公式ブログ / 仕様書

### <論点2>
...

## 公式に記述が無かった論点
（探したが見つからなかったもの。空にせず正直に書く。
  ここが「非公式のみ」になる候補として突き合わせ役に渡る）
```

**数値は必ず数値のまま写す。** 「安い」「速い」に言い換えない。
**取得日を必ず書く。** 公式仕様も数ヶ月で変わる。

## 段階2: 非公式情報の調査（サブエージェントに任せる）

`research-community` サブエージェントを起動する。渡すもの:

- 調査テーマと、`plan.md` の受入基準
- **段階1で公式に記述が無かった論点**（そこを重点的に探させる）
- 出力先のパス `projects/<slug>/findings/community.md`

**段階1の結果そのものは渡さない。** 渡すと公式の記述に引きずられ、
独立した調査にならない。渡すのは「何を調べてほしいか」だけ。

## 段階3: 突き合わせとレポート作成（サブエージェントに任せる）

`research-reconcile` サブエージェントを起動する。渡すもの:

- `findings/official.md` と `findings/community.md` のパス
- `plan.md` のパス
- 出力先のパス `projects/<slug>/report.md`

突き合わせの規則はサブエージェント側の定義に書いてある。要点は次のとおり。

| 状況 | 結論 | 出典区分 | 備考 |
| --- | --- | --- | --- |
| 公式と非公式が一致 | 公式 | `公式` | — |
| 公式と非公式が相違 | **公式** | `公式（非公式と相違）` | 非公式の主張と出典を残す |
| 非公式のみ | 非公式 | `非公式のみ` | 公式から得られなかった旨 |
| どちらにも無い | — | `情報なし` | 何を探したか |

**相違を黙って潰させない。** 公式を採ったうえで、非公式が何と言っていたかを備考に残させる。

## report.md の構成

```
タイトル
## 調査概要   日本語200文字程度
## 調査結果   表形式。表だけ読んで理解できる粒度まで書き下ろす
## Appendix
   ### A. 調査の詳細
   ### B. 出典（公式 / 非公式に分ける）
   ### C. 突き合わせで判明した相違
```

**表が本体である。** 「詳細は Appendix 参照」で逃げない。
数値・条件・制約は表の中に入れる。Appendix は裏取りのための場所。

## サブエージェントが失敗したとき

| 状況 | 対応 |
| --- | --- |
| `research-community` が何も見つけられなかった | 空の結果でも段階3に進む。レポートは全項目が `公式` か `情報なし` になる。それ自体が結果 |
| `research-community` が起動できない（Agent ツールが使えない等） | **あなたが代行しない。** `loop:blocked` にして Issue に理由を書く。1人で両方調べると分離の意味が消える |
| `research-reconcile` が起動できない | 同上。突き合わせを自分でやると、公式優先の規則が守られたかを誰も検証できない |

## 共通の規律

- **一次情報を優先する。** 段階1が一次、段階2は補助という関係を崩さない
- **日付を書く。** 公式は取得日、非公式は公開日と取得日の両方
- **数字を出す。** 「速い」「安い」ではなく実測値・価格表の数字。見積りなら計算過程を残す
- **結論が「分からなかった」でもよい。** 何を試して駄目だったかを書く。それは次の人の時間を節約する
- `sources.md` には公式・非公式を**分けて**追記する
