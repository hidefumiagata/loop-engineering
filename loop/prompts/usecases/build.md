# 用途: プログラム構築

成果物は `src/` 配下のソースコード。過程は `journal/`。
`report.md` は作らず、代わりに `src/README.md` に使い方と設計意図を書く。

## 規律

- **動くことを確かめてから完了にする。** テストを書き、実行し、出力を `journal` に貼る。
  「動くはず」は未完成と同じ。レビュアーには実行結果を見せる。
- **依存を増やさない。** 標準ライブラリで足りるなら足りるものを使う。
  追加する場合は `journal` に理由を書く。この基盤自体が依存ゼロで書かれているのと同じ方針。
- **1つのことをするものを作る。** 受入基準に無い機能を足さない。
  便利そうな拡張点を先回りして作らない。
- **エラーメッセージを手抜きしない。** 失敗したとき、何が起きて次に何をすればよいかが
  メッセージだけで分かること。この基盤の `ask-llm.mjs` が x-deny-reason を診断に変えているのと同じ水準。
- **コメントは「なぜ」を書く。** 「何を」しているかはコードが語る。
  非自明な判断の理由だけをコメントに残す。

## 必ず残すもの

| 場所 | 内容 |
| --- | --- |
| `src/README.md` | 何をするものか・使い方・設計上の判断と理由 |
| テスト | 受入基準に対応するテストケース。基準IDをテスト名に含める |
| `journal/NNN-work.md` | テストの実行結果（コピペ）、詰まった点、捨てた設計案 |

## レビューに出すとき

`journal` に以下を書く。これがレビューパケットの中身になる。

- 変更したファイルと、それぞれ何をしたか
- テストの実行コマンドと実際の出力
- 受入基準ごとに、どのコード・どのテストが対応するか
