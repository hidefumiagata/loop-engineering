# synthesizer（Claude 自身が従う指示）

このファイルは Claude が synthesize フェーズで従う手順である。他社LLMへは渡さない。

## 目的

3者が独立に出した案と、3者による相互評価を全部読み、**テーマに対する最良の答えを1つ書く**。

案を選ぶのではない。**作り直す。**
「案Bを推奨する」は答えではない。読者が知りたいのはテーマへの答えであって、どの案が勝ったかではない。

## 入力

| 入力 | 何に使うか |
| --- | --- |
| `brief.md` | テーマ・制約・前提事実・評価基準。答えが満たすべき条件 |
| `proposals/A.md` `B.md` `C.md` | 3つの独立した答え。素材 |
| `evaluations/by-*.json` | 各案のどこが強く、どこが弱いと見られたか |
| `scores.json` の `unmet_criteria` | **どの案も満たせなかった基準。統合答案が解決すべき宿題** |
| `scores.json` の `warnings` | 評価そのものの信頼性に関する注意 |

## 書く手順

1. **3案を通読し、一致している部分を特定する。**
   独立に書いた3者が同じ結論に達した部分は、単独モデルの主張より確度が高い。
   ここが答えの骨格になる。
2. **割れている部分を特定し、どちらが正しいかを根拠で判断する。**
   多数決で決めない。2対1でも、1の側の根拠が強ければそちらを採る。
   判断できないなら「割れた論点」として両論を残す。**無理に一本化しない。**
3. **`unmet_criteria` を見る。** どの案も満たせなかった基準があれば、
   そこは3者とも見落としている箇所である。自分で埋めるか、埋められないなら
   「この答えの限界」に明記する。素材に無いからといって黙って落としてはならない。
4. 答えを書く。構成は `loop/prompts/usecases/deliberation.md` の `answer.md` に従う。
5. **`provenance.json` を書く。** 答えの主要な要素ごとに、どの案に由来するかを記録する。
   ```json
   [
     { "element": "強制力はリモートの必須チェックに集約する", "from": ["A","B","C"], "note": "3者一致" },
     { "element": "変更種別ごとの実行マトリクス", "from": ["A"], "note": "A固有。採用した" },
     { "element": "段階的ロールアウト手順", "from": ["C"], "note": "C固有。採用した" },
     { "element": "Hook検証結果のCI再利用を禁じる", "from": [], "note": "新規。3案に無いが必要と判断した" }
   ]
   ```
   `from` が空なら新規。要素は 8〜20 件に収める。細かすぎると寄与比率が意味を失う。

## 自分が参加者でもあることの扱い

**あなたは3案のうち1つを自分で書いている。** どれが自案かは文体で分かってしまう。
だから「知らないふり」はしない。代わりに次の規律で縛る。

- **自案を土台に据えない。** 骨格は「3案が一致した部分」から組む。自案の構成をなぞらない
- **他案固有の要素を最低1つずつ取り込む。** 取り込めないなら、なぜ不要かを
  「取り込まなかった要素」に理由付きで書く。黙って落とすのが最も疑わしい
- `provenance.json` の寄与比率は `loop/bin/synthesis-check.mjs` が機械的に算出する。
  自案に偏っていれば警告が出る。**警告が出たら答えを書き直す。** 言い訳を添えて通さない

## 禁止事項

- **「案Xを推奨する」で終わらせること。** 答えを書く
- 3案の要約を並べること。要約は素材であって答えではない
- 割れた論点を多数決で潰すこと
- どの案も満たせなかった基準を黙って落とすこと
- 自分の案の文章をそのまま貼ること。統合した結果として書き直す
- `scores.json` の数値を書き換えること

## 長さ

本体（「答え」+「本論」）で 1500〜3500 語。
素材が3本あるからといって3倍にしない。統合とは短くすることでもある。
