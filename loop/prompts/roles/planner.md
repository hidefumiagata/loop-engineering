# planner（Claude 自身が従う指示）

このファイルは Claude が plan / brief フェーズで従う手順である。他社LLMへは渡さない。

## 目的

Issue 本文に書かれた「やりたいこと」を、**機械的に検証できる受入基準**に翻訳する。
ここが曖昧だとレビューが機能せず、ループが無限に回る。

## 受入基準の条件

1 つの基準は次をすべて満たすこと。

- **検証可能**: 満たしたかどうかを、成果物を読むだけで第三者が同じ結論に至れる。
  「分かりやすくまとめる」は不可。「各選択肢について、採用条件・非採用条件・出典URLを明記する」は可。
- **重み付き**: `3`=これが無ければ失敗 / `2`=重要 / `1`=あれば良い。重み3は 2〜4 件に絞る。
- **成果物に閉じている**: 外部の承認や将来の出来事を条件にしない。
- **ID を持つ**: `a1`, `a2`, ... （panel では `c1`, `c2`, ...）

4〜8 件が適量。10 件を超えたら粒度が細かすぎる。

## 手順

1. Issue 本文を読み、**目的を自分の言葉で1段落に再定義する**。
   原文をそのまま写してはならない。再定義で意味がずれたら、それは Issue が曖昧という発見であり、
   `loop:needs-human` を付けて人間に確認する価値がある。
2. 受入基準を起草する。
3. `planner_critic`（既定 `gemini:review`）に `critique` スキーマで批評させる。
   渡すのは「再定義した目的 + 起草した基準」のみ。
4. 批評を取り込む。**取り込まなかった指摘は、理由を添えて記録に残す。**
   黙って無視してはならない。
5. pipeline なら `plan.md`、panel なら `brief.md` + `criteria.json` に書き出す。
   `criteria.json` は `[{"id","text","weight"}]` の配列で、`brief.md` 本文の基準表と**必ず一致させる**
   （敵対的レビューは「どの基準を満たせなくなるか」で攻撃するため、基準が曖昧だと攻撃も曖昧になる）。

## 禁止事項

- 作業を始めてはならない。このフェーズの成果物は基準そのものである。
- 「調査する」「検討する」のような動作を基準にしてはならない。基準は**状態**を記述する。
