## 3. Tapo ライブラリが TP-Link の TPAP プロトコルに対応

- **元記事**: [Tapo now speaks TP-Link's TPAP protocol](https://mihai.dinculescu.dev/posts/tapo-speaks-tpap/) — mihai.dinculescu.dev — HN 107点 / コメント45件
- **HN**: <https://news.ycombinator.com/item?id=49978563>

TP-Link の Tapo 機器はファームウェア 1.4.0 以降、「Third-Party Compatibility」スイッチの導入で新プロトコル TPAP を使うようになった。Rust/Python 製 Tapo ライブラリ v0.11.1 はこれに対応し、スイッチがオフでも機器を制御できる。従来の KLAP はハッシュ交換のため通信を記録されるとオフライン攻撃が可能だったが、TPAP は SPAKE2+ を採用し、記録からの攻撃やセッション鍵経由の過去通信の復号ができない。H200/H500 ハブの録画取得、プラグのスケジュール／日の出・日没オフセット、AIエージェント向けMCPサーバーの拡張も入った。

**議論の要点**: LLM とリバースエンジニアリングツールでクローズドなプロトコル解析が容易になったという感想と、記事が背景説明に乏しいという不満が出た。

## 4. Berthd

- **元記事**: [Berthd](https://berthd.app/) — berthd.app — HN 6点 / コメント1件
- **HN**: <https://news.ycombinator.com/item?id=49982735>

自分の開発マシン上で Claude Code や Codex などのコーディングエージェントを動かすためのツール。エージェントは手元のボックス側で動くので、ノートPCを閉じても処理が続く。⌘N で指示を出すとワークツリーを作ってエージェントを起動し、各ステップをライブで確認でき、編集は diff で見られる。2つのワークツリーを並べて比較する機能もある。macOS アプリ＋各ボックスに berthd を入れる構成で、オープンソース・無料とされる。

**議論の要点**: コメントは1件のみで、「Codex/Claude cloud や Modal の別バージョンか」という疑問が出ている。

## 5. Benchmark in Milliseconds

- **元記事**: [Benchmark in Milliseconds](https://matklad.github.io/2026/10/05/benchmark-milliseconds.html) — matklad.github.io — HN 98点 / コメント22件
- **HN**: <https://news.ycombinator.com/item?id=49967427>

マイクロベンチマークは実行時間を約300ミリ秒に調整すべきだという主張。理由は4つ。ミリ秒なら1〜999の整数で小さな改善も見えて読みやすい。10ms未満だとインタプリタ起動などの固定コストに歪められる。数百ミリ秒なら人間が直感的に時間を感じられる。1秒以上だと反復が遅くなる。ベンチマークの目的は精密測定より、最適化の判断のための直感を作ることだと結論する。

**議論の要点**: 絶対値より信頼区間や比較対象が要る、自作せず BenchmarkDotNet などの確立した枠組みを使うべきだという反論が目立った。

## 6. Gleam は Erlang ソースを生成しなくなった

- **元記事**: [Gleam doesn't compile to Erlang source anymore](https://gleam.run/news/gleam-doesnt-compile-to-erlang-source-anymore/) — gleam.run — HN 251点 / コメント103件
- **HN**: <https://news.ycombinator.com/item?id=49975619>

Gleam v1.19.0 から、Erlang ソースコードではなく Erlang コンパイラ内部の中間表現「抽象形式」を直接生成する。理由はコンパイル性能の向上、行番号がGleamソースに正しく対応するメタデータの正確化、コンパイラ構造の現代化。100モジュール×100関数の測定で v1.17.0 から大幅に高速化したと報告している。デバッガ対応にも道が開く。BEAM バイトコード直接生成を選ばなかったのは、Erlang の進化への追従コストを考えたためで、Elixir も同じ方式を採る。

**議論の要点**: 抽象形式の解説や Gleam への好意的な声が多く、Rust/Go など別ターゲットへの対応を望む声もあった。

## 7. 地熱エネルギーの数学

- **元記事**: [Mathematics of Geothermal Energy](https://www.ebsco.com/research-starters/power-and-energy/mathematics-geothermal-energy/) — ebsco.com — HN 55点 / コメント24件
- **HN**: <https://news.ycombinator.com/item?id=49977819>

EBSCO の入門解説。地熱勾配（深さに応じた温度上昇）を熱源とし、地熱ヒートポンプによる冷暖房と、蒸気タービンによる発電（最初の施設は1904年イタリア・ラルデレッロ）を紹介する。低排出で安定したベース電力が利点だが、良質なサイトが限られ初期費用が高いため普及が遅れている。2005〜2010年に世界の地熱発電量は20%増えた。タイトルの「数学」に見合う数式的な内容は、取得できた範囲ではほぼ無かった。

**議論の要点**: 分野の実務者が「『数学』は釣りタイトルで内容は浅く当てにならない」と指摘し、データセンター電源としての地熱への期待も語られた。

## 9. Smalltalk の初期の歴史（1993）

- **元記事**: [The Early History of Smalltalk](https://worrydream.com/EarlyHistoryOfSmalltalk/) — worrydream.com — HN 74点 / コメント34件
- **HN**: <https://news.ycombinator.com/item?id=49979845>

Alan Kay による回想論文。Sketchpad の「マスターインスタンス」と Simula のプロセスモデルに着想を得て、「計算機を多数の小さな計算機に分割する」発想がオブジェクト指向になった。Dynabook 構想の下、1972年に「1ページのコード」で言語を実装できるかという賭けから Smalltalk-72 が生まれ、Dan Ingalls が実装した。1973年からは子どもたちとの実験を重ね、子どもがツールを自作するようになった。（本文約15万字のうち前半10万字のみ読了。）

**議論の要点**: NeXTSTEP や Objective-C への影響、Smalltalk で「プログラムの中に住む」体験が忘れられないという思い出話が多い。

## 10. 3SUM の準二次時間アルゴリズムと APSP の準三次時間アルゴリズム

- **元記事**: [Subquadratic 3SUM and Subcubic APSP](https://arxiv.org/abs/2610.06783) — arxiv.org — HN 60点 / コメント23件
- **HN**: <https://news.ycombinator.com/item?id=49977437>

Josh Alman と Virginia Vassilevska Williams（2026-10-05 投稿）が、3SUM を O(n^1.9992)、全点対最短路（APSP）を O(n^2.9995) で解くと報告した。どちらも長年の仮説（3SUM 仮説・APSP 仮説）を覆す多項式的改善で、核は「薄い行列積」と、疎な三部グラフでの三角形検出の真の準二次時間化。Exact Triangle 仮説や Zero-Weight k-Clique 仮説にも波及するという。

**議論の要点**: あるコメントは、論文の謝辞に「アルゴリズムは Claude が発見した」と書かれていると引用している（アブストラクトページからは確認できず、HN コメント経由の情報）。数学へのLLM活用に食傷する声もある。
